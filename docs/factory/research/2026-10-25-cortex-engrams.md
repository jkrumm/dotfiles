# Cortex: platform, AI features, and engrams on DBOS (research-gateway, 2026-10-25)

Query: how Cortex (cortex.io) is built, its concepts, and its DBOS usage. Status ok, 60 citations kept. Plus the primary source read in full: "A software factory is just a durable workflow", Nikhil Unni, builders.cortex.io, 2026-10-22.

## Bottom line

- **Data model:** everything in Cortex is a **catalog entity** described by an OpenAPI-3 "Cortex entity descriptor" (`cortex.yaml`, `x-cortex-*` keys inside `info`); ownership is `x-cortex-owners` (team groups or emails) with `APPEND`/`FALLBACK`/`NONE` inheritance; **Scorecards** are entities + CQL rules + either levels or weighted points, re-evaluated every 4 hours; **Initiatives** attach a Scorecard level or rule set to a due date with reminders 7 days and 1 day out; **Workflows** are graphs of Core/Cortex/Integration blocks (including a Manual approval block) with a mustache state object; Scaffolder is a Core Workflow block; plugins are CQL-targeted. There is no separate "severity" object — tiers *are* levels.
- **Ingestion:** pull-by-default over vendor APIs with documented per-integration cadences (GitHub repo/PR syncs restart within 10 min of the previous completion; Datadog monitors lag up to 30 min, incidents every 15 min), push only for GitHub PR webhooks, ArgoCD, the deploys API and custom webhooks; Eng Intelligence (DORA, Data Explorer) is computed from that ingested data.
- **AI:** Cortex ships an MCP server (`ghcr.io/cortexapps/cortex-mcp`, remote `https://mcp.cortex.io/mcp`, personal-access-token auth) with tools mapping ~1:1 onto REST endpoints, a read-only AI chat that explicitly cannot take action, and **no first-party agent that drafts fixes or opens PRs** — "remediation" is MCP quick-win lists plus Initiatives plus Workflows. Context is supplied by live per-call tool/API retrieval, not embeddings.
- **DBOS:** yes — Cortex's open-source software factory **engrams** runs on DBOS, and its blog says the OpEx Review product also used it; embedded in the TypeScript plane on Bun, `dbos` schema next to Drizzle tables, **one** `AutomationRunWorkflow` interpreting a block graph stored as data. No quantitative results, no Temporal migration claimed, and Cortex is not on DBOS's customer-stories page.
- **Borrowables:** automations-as-data plus one tiny interpreter workflow, one run id = one mailbox, deterministic side-effect ids with attach-or-start, dedup by *joining the in-flight run*, owner routing, and per-project health as a level ladder driven by deadlines.

## 1. Data model and platform objects

**Entities.** Default entity types are **Services** (the default), **Domains**, **Teams** and **Cloud resources** (AWS/Azure/GCP); custom types are unlimited via UI or API (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview). Every entity is a **Cortex entity descriptor** — "Cortex YAML"/`cortex.yaml` — which is a compliant **OpenAPI 3** spec extended with `x-cortex-*` blocks that **must sit inside `info`**; required: `title`, `x-cortex-tag`, `x-cortex-type` (plus `x-cortex-definition` for custom types) (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/yaml.md). There are two identifiers: the mutable `x-cortex-tag` (editing it creates a *new* entity) and the **Cortex ID (CID)**, an 18-character immutable id used in the API, CQL, app URLs and the AI Assistant. Registration paths: UI/YAML editor, REST API, GitOps (`.cortex/domains`, `.cortex/teams`), the Terraform provider, and integration import (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities). Other blocks: `x-cortex-groups` (segmentation, required `tag`), `x-cortex-link`, `x-cortex-custom-metadata`, `x-cortex-dependency`, `x-cortex-parents`/`x-cortex-children`, `x-cortex-relationships`, `x-cortex-team`.

**Ownership.** `x-cortex-owners` entries are either `type: group` (required `name` + `provider`, `CORTEX` meaning a Cortex-defined team) or `type: email`; documented providers include AD, Azure DevOps, BambooHR, GitHub, GitLab, Google, Okta, Opsgenie, ServiceNow, Workday (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/yaml.md). Three layers: **assignment** (ML "ownership recommendations", UI, YAML, API, IdP/Git/HR sync, cloud tags `owner: <x-cortex-tag>`, inheritance), **propagation** (per-owner mode `APPEND`/`FALLBACK`/`NONE`, default `NONE`; entity hierarchy inherits, team hierarchy never adds owners), and **effect** (gates Scorecard/Initiative notifications, data verification, the Mine tab, team entity editing, Workflow run restrictions, Eng Intelligence grouping) (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/ownership.md). Teams are themselves entities (`x-cortex-type: team`, `x-cortex-team` block with linked IdP `groups` and/or `members`, plus parent/child hierarchy; membership syncs daily) (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/adding-entities/teams.md).

**Scorecards.** Four parts: entities (by type, narrowed by groups or CQL), **rules**, **levels or points**, and an evaluation window whose default is **every 4 hours**; each rule carries a failure message, scheduled start date, filter and exemption. With points, each rule has a weight and the score is the sum of passes; with levels, an entity reaches a level only after passing every rule in it and below — a rule can't repeat across levels but its threshold can rise, and points can be nested in levels (https://docs.cortex.io/standardize/scorecards). **CQL** is `data source function quantifier` over entity metadata, integrations, `custom("key")` and `customMetrics(...)`, e.g. `dependencies.in().length`, `jira.numOfIssues()`, `customMetrics(key="error-rate", lookback=duration("P30D")).map((m) => m.value).average()`, with JQ support, `AND`/`OR`/`!`, and `context.entity.id` inside rule descriptions (https://docs.cortex.io/standardize/cql). Rule exemptions, rule filters and "Scorecards as code" exist as separate documented pages (https://docs.cortex.io/_llms/product-docs.txt).

**Initiatives.** Must attach to a **published** Scorecard; the goal is a Scorecard **level** or specific **rules**; plus a due date and an entity-type scope refined by groups/CQL. Drafts are hidden and trigger nothing. Notifications go to owning users, owning teams, or the entity's Slack channel; reminders fire **7 days and 1 day before the due date** (the first at the next 3 p.m. UTC after creation), and custom intervals with reply-to addresses can be set at creation; they surface as Action items on the Engineering homepage (https://docs.cortex.io/improve/initiatives).

**Workflows.** Steps are **blocks** in three families: **Core** (Asynchronous HTTP request, Branch, Data transformation (JQ), HTTP request, JavaScript, Manual approval, Run workflow, Scaffolder, Set variable(s), User input), **Cortex** (create/update entity, add custom data, list deployments, get Scorecard scores) and **Integration** (GitHub, PagerDuty, ServiceNow, Slack, Jira, Jenkins, …). A run produces a state object with `context` (`context.entity` including the full descriptor, `context.initiatedBy`, `context.secrets`), `actions.<slug>.outputs` and `variables`, referenced with `{{mustache}}` (https://docs.cortex.io/streamline/workflows). Approvals are a Core "Manual approval" block that awaits asynchronous human approval (optionally restricted to specific team members); blocks run **as the initiating user**, so a block fails if that user lacks permission, and who may run a Workflow is governed by access controls and the `Edit Workflows` / `Execute Workflow Runs` permissions (https://docs.cortex.io/streamline/workflows/blocks). Workflows are CRUD-able via the API and declarable as code ("Workflows as code", block configuration reference in the docs index).

**Scaffolder and plugins — thin.** Scaffolding is verified only as a Core Workflow block ("Scaffolder – Run a scaffolder template") (https://docs.cortex.io/streamline/workflows, medium), and the docs index lists "Registering a Scaffolder template", advanced usage and a Cookiecutter conversion guide. Plugins are verified only at title level, plus the fact that **CQL decides which entities a plugin appears on** (https://docs.cortex.io/_llms/product-docs.txt, medium). Both detail sets were unread this run — see unverified.

## 2. Integrations, ingestion and Eng Intelligence

Cortex's documented default is **pull**: it "connects to each tool via its official API, pulling live data directly from your systems", and its rate limiter exists to keep "background syncs to pull data from integrations" under vendor limits, with the caveat that "integration sync times vary and are subject to scheduling overrides and timing variance" (https://docs.cortex.io/ingesting-data-into-cortex/integrations). Integrations are grouped **Essentials** (version control, team/ownership, on-call, project management, communication, code quality) and **Extended** (CI/CD, cloud, error tracking, feature flags, incidents, observability, security, ITSM), plus SSO (Entra ID, Google, Okta, OIDC) and SCIM (Entra ID, Okta) (https://docs.cortex.io/ingesting-data-into-cortex/integrations.md).

**Push is the exception, and it is documented per case:** GitHub PR webhooks (optional but recommended — the Cortex GitHub app receives them by default and Cortex "cross-references" them against API data) (https://docs.cortex.io/ingesting-data-into-cortex/integrations/github); ArgoCD notification webhooks calling the Cortex deploy REST endpoint; the deploys API; **custom webhook integrations** that accept arbitrary JSON by POST with "no authentication headers or Cortex entity tags required", using an "Entity tag JQ" to extract the tag and a "Key" to store it — a 400 is returned if the tag matches no existing entity (https://docs.cortex.io/ingesting-data-into-cortex/integrations/webhook); and Axon Relay for internally hosted tools. For Jira, PagerDuty, Slack and Teams, polling-vs-webhook is **not stated in the docs**.

**Cadence, documented examples:** GitHub identities daily at 9 a.m. UTC and repository/PR syncs that "start within 10 minutes of the previous sync's completion" (data normally ≲10 min old), with homepage PRs/issues refreshed every 2 minutes (https://docs.cortex.io/ingesting-data-into-cortex/integrations/github); Datadog monitors/SLOs may "lag live Datadog by up to 30 minutes", incidents sync every 15 minutes (full refresh, not incremental), schedules/shifts every 30 minutes, dependencies daily at 12 a.m. UTC with a manual "Sync dependencies" button (https://docs.cortex.io/ingesting-data-into-cortex/integrations/datadog/using-the-integration-for-datadog); ownership syncs per source — Azure DevOps/Bitbucket/GitLab 10 a.m., GitHub/Google/ServiceNow/Workday 9 a.m., BambooHR/Entra ID/AWS/Azure Resources 6 a.m., Okta 3 p.m. UTC (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/ownership/ownership-sources); AWS dependencies daily at 8:00 a.m. UTC, all others at 12:00 a.m. (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/adding-entities/dependencies). **No plan-tier sync differences are documented**; the only edition-scoped note found is that integration error logs are "available in Cortex cloud" (https://docs.cortex.io/ingesting-data-into-cortex/integrations.md).

**Mapping and custom data.** Third-party data attaches through descriptor blocks (`x-cortex-git`, `x-cortex-owners`, `x-cortex-oncall`, `x-cortex-custom-integration-mappings`); PagerDuty discovery "best guesses" the vendor service from the Cortex tag/entity name. Custom data has three entry points — descriptor `x-cortex-custom-metadata`, `POST /api/v1/catalog/{tag}/custom-data` (bulk `PUT`, `DELETE` with `key`), and custom webhooks — with **YAML winning over API/webhooks unless `force=true`**, and forced values overwritten on the next descriptor reprocess (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/custom-data). **Custom metrics** are a separate time series, provided via API or "via a CQL query that is evaluated by Cortex every 12 hours" (https://docs.cortex.io/improve/eng-intelligence/custom-metrics).

**Eng Intelligence.** The DORA dashboard defines Cycle time = first commit → merge (not supported for Azure DevOps or Bitbucket), Deployment frequency = deployments over a period, Change failure rate = rollbacks / deployments created (best practice under 15%), Time to resolution = resolution − opened (https://docs.cortex.io/improve/eng-intelligence/dora-dashboard). Data Explorer publishes the catalogue by source: Deployment (Cortex deploys API — change failure/deployment/rollback frequency), Incident (PagerDuty — incident frequency, time to resolution), Project management (Jira — story points completed, work item lead time, work items completed/created), Version control (ADO/Bitbucket/GitHub/GitLab — cycle time, PR counts, comments per PR, unique authors, reviews, PR size, success rate, time to approve/first review/merge/open), AI tools (GitHub Copilot — AI adoption rate = active users / total seats) (https://docs.cortex.io/improve/eng-intelligence/data-explorer/available-metrics-in-data-explorer). Surfaces: DORA/Velocity/AI-impact/Custom dashboards, Data Explorer, entity custom-metrics panel, All Metrics (legacy), and Scorecards via `customMetrics()`; permissions are `View Eng Intelligence` and `Configure Eng Intelligence` (https://docs.cortex.io/improve/eng-intelligence).

## 3. AI features and how they get context

**MCP server.** "Cortex MCP" is officially "a Model Context Protocol server that brings your engineering data into the tools your team already works in" (https://docs.cortex.io/get-started/cortex-ai-assistant/mcp). Two deployments: local Docker image `ghcr.io/cortexapps/cortex-mcp:latest` over stdio with `CORTEX_API_TOKEN`, or remote streamable HTTP at `https://mcp.cortex.io/mcp` (US) and `https://mcp.eu.cortex.io/mcp` (EU); self-managed workspaces also set `CORTEX_API_BASE_URL`, and the remote mode "requires a personal access token, not an API key" (https://docs.cortex.io/get-started/cortex-ai-assistant/mcp/configuring-cortex-mcp). Tools map ~1:1 onto REST endpoints: catalog/entities (`searchCatalog`, `getEntityDescriptor`, `createOrUpdateEntity`, …), custom data & events, dependencies, Scorecards (`listScorecardScores`, `getScorecardNextStepsForEntity`, exemption request/approve/deny), Initiatives, verifications, metrics (`queryTraceEvents`, `queryPointInTimeMetrics`), teams/on-call, deploys, Workflows (`runWorkflow`, `getWorkflowRun`), plugins, scaffolder, CQL (`createQuery`), plus `query_docs` and `get_more_tools`. It **cannot** delete data, run bulk operations, create teams/relationships/OpenAPI docs, or manage workspace administration, and it "acts as the user who owns your personal access token" (https://docs.cortex.io/get-started/cortex-ai-assistant/mcp/using-cortex-mcp). The server repo is `cortexapps/cortex-mcp`, MIT, labelled "Research Preview" (https://github.com/cortexapps/cortex-mcp/blob/HEAD/README.md). **Name collision:** PyPI `cortex-mcp` (1.1.20, syab726/cortex) and npm `cortex-mcp` (3.2.0) are unrelated projects (https://pypi.org/project/cortex-mcp/).

**AI chat.** "Ask Cortex AI" (⌘J) is a Research Preview gated by an `Enable AI Chat` permission and "can't take action on your behalf. It won't create or edit Scorecards, Initiatives, Dashboards, or Workflows". It reaches the catalog, Scorecards, Initiatives, Workflows, Eng Intelligence and docs — but not dependencies, on-call, custom data, custom events or doc/runbook links. It grounds questions in "what you're looking at" on an entity or Scorecard page, and the docs warn that "Cortex AI is not limited to the entities you can see" (https://docs.cortex.io/cortex-ai-chat.md).

**Agents that act — the honest answer.** No Cortex-shipped agent that drafts fixes or opens PRs is documented. Documented remediation for failed scorecard rules is: use the **MCP** for a prioritized "quick wins" list (read), create an **Initiative** assigning rules to teams with a deadline and auto-created Jira/GitHub/ClickUp/Azure DevOps tickets, or fix the **Workflow/Scaffolder** template for systemic gaps (https://docs.cortex.io/solutions/ai-readiness/in-action). The one agent described in engineering detail is the **OpEx Review Agent**: Triage on Haiku → Evidence gathering and Synthesis on Sonnet → Grounding critique on Opus → deterministic code validation, with citation checks that reject claims citing a query that never existed; that validation "is also used by our AI chat functionality" (https://builders.cortex.io/blog/trustworthy-agents-for-opex-reviews/). Marketing positions agents as *consumers*: "Cortex maps your stack into a live Context Graph and exposes it through the Cortex MCP, so agents pull accurate context instead of guessing" (https://www.cortex.io/solutions/agents). The Context Graph page describes the substrate as a graph plus AI-generated metadata that "fills gaps, resolves conflicts", with AI ownership suggestions — **no embeddings or vector index are documented anywhere** (https://www.cortex.io/products/context-graph). The MCP launch post described three initial areas — Entities, Scorecards, Initiatives — and said the goal was assistants that "step into action" (https://www.cortex.io/post/mcp-server).

**AI readiness scorecards.** The docs carry an AI Readiness scorecard template and a distinct AI Governance template; the version verified in this run is a simplified **nine-rule** table — Bronze: ownership, runbook, on-call rotation; Silver: SLOs, CI/CD, dependency inventory; Gold: AI model security scanning, test coverage, DORA metrics (https://docs.cortex.io/solutions/ai-readiness). That table is less specific than the fuller CQL rule lists in the AI-excellence guide pages, which could not be read here; the two official presentations do not line up in detail.

## 4. Architecture and engineering: Cortex on DBOS

Cortex's own engineering blog states it plainly in "A software factory is just a durable workflow" (Nikhil Unni, co-founder & Chief Architect): *"We chose DBOS as our durable workflow engine because it is a simple, lightweight, and reliable engine that is easy to run in your own cloud… the appeal of 'all you need is Postgres' without the operational burden that its open source competitors suffer from."* It also notes prior organisational use — *"we had recent organizational experience dabbling with DBOS for our newly launched OpEx Review product"* — so **two** Cortex subsystems: **engrams** automations and **OpEx Review** (https://builders.cortex.io/blog/software-factory-automations/).

**How it is deployed:** DBOS runs inside the TypeScript product plane **on Bun**, with system tables in a `dbos` schema beside the Drizzle tables; the config shown is `DBOS.setConfig({ name: 'engrams-orchestrator', systemDatabaseUrl, systemDatabaseSchemaName: 'dbos', executorID: <pod>, runAdminServer: false })` followed by `await DBOS.launch()` before the HTTP server serves. **What runs as durable workflows:** a single registered `AutomationRunWorkflow` that interprets a block graph *stored as data*, so every built-in and customer-authored automation shares one workflow, triggered by cron, manual or webhook, with filter/branch/loop primitives and a JS block in QuickJS-on-WASM. **What it replaced:** Cortex's own hand-written automations — "we replaced both hand-written workflows with a single registered workflow". The rejected alternatives are enumerated: a request handler can't hold a days-long wait; a job queue that retries "from the top" re-sends the prompt, re-posts the comment and re-opens the PR; "cron and a status column turn into a hand-built state machine — every new step is another state, another transition, another edge case when two events race"; deploys land mid-flight; and webhook retries deliver every input twice. **No Temporal migration is claimed anywhere.**

**Results are architectural, not numerical.** A parked workflow is "just a row in the DBOS system tables — no socket, no lock, no VM", with one mailbox per run keyed by workflow id `autorun:<automationId>:<deliveryKey>`, and effectively-once side effects via deterministic ids (VM exec id plus a journal written inside the guest with attach-or-start semantics; prompt id; webhook delivery id and cron occurrence epoch). **No throughput, latency, cost or migration-effort figures are published**; the two claimed guarantees are that "every run resumes where it was, and every side effect happens once." **Lessons:** a PR-review `git clone` inside a DBOS step was killed by a microVM snapshot mid-clone and completed with nowhere to put its result — fixed by making VM operations behave like steps (deterministic exec ids, in-VM journal, attach-or-start); determinism rules require pinning the automation definition as the first checkpointed step, naming steps by graph position (`step:<framePath>:<attempt>`), evaluating branch/loop conditions *inside* steps, never calling `Date.now()` in control flow, retrying in the engine with a permanent-error flag, and a snapshot test on the ordered step names gated by an `ENGINE_STEP_CONTRACT` constant — because DBOS versions an application by the source of its registered workflow functions.

**Relationship status:** DBOS hosts a Cortex talk of the same title at its User Group on 22 October 2026 (https://www.dbos.dev/webcast/cortex-software-factory) — the page carries a one-line description and an on-demand player, no transcript — and Cortex is **not** on DBOS's customer-stories page, which lists Walmart, Notion, Roche, Yutori, Luma AI, Orderful and others (https://www.dbos.dev/customer-stories). So: first-party engineering post + user-group talk + OSS usage, not a published case study or partnership. engrams itself is described as "an open source platform for running Claude Code, Codex, or your own agent in your cloud" (https://builders.cortex.io/).

## 5. What a solo "software factory" should borrow

- **Automations as data, one interpreter workflow.** Store your intake→dedupe→queue→watch graph as rows (blocks + edges) and register a single workflow that interprets it. Editing automations then never rotates the workflow version, which is exactly the DBOS versioning trap Cortex engineered around (snapshot-tested step names + `ENGINE_STEP_CONTRACT`) (https://builders.cortex.io/blog/software-factory-automations/).
- **Run id = mailbox = dedup key.** One deterministic id per delivery (`autorun:<automationId>:<deliveryKey>`) gives you idempotent intake *and* dedup for free: "if the same error fires again, it joins the run already in flight, so work is deduped" (https://builders.cortex.io/blog/introducing-engrams/). For your signal sources, make the delivery key the upstream event id (webhook delivery id, cron epoch, PR number + head SHA).
- **Parked work must hold nothing.** A queued Claude Code session waiting on capacity or a human should be a row, not a blocked process: no socket, no lock, no VM. That is the concrete answer to DBOS-vs-plain-Postgres: DBOS gives you the parked-state model and exactly-once side effects; with tables + ticker you write the state machine and its idempotency yourself, and Cortex's own enumeration of how that goes wrong (retry-from-top, racing events, mid-flight deploys) is the argument for the former (https://builders.cortex.io/blog/software-factory-automations/, https://docs.dbos.dev/why-dbos).
- **Every external side effect gets a deterministic id + journal with attach-or-start** — twice, if the side effect lives in a sandbox/VM you don't control (their `git clone` lesson).
- **Health as a ladder, pressure as a deadline.** Cortex's Scorecard levels (pass every rule in the level and below) plus Initiatives (level or rule set + due date + 7-day/1-day reminders) are a ready template for per-project health: rules = machine-checkable facts about each repo, levels = Bronze/Silver/Gold, initiative = "reach Silver by date", reminder cadence = the push (https://docs.cortex.io/standardize/scorecards, https://docs.cortex.io/improve/initiatives).
- **Route signals by ownership.** Cortex's rule that ingested data attaches to the *entity that owns the code* (and that ownership gates every notification) is the primitive that makes "watch" per-project instead of per-system (https://docs.cortex.io/ingesting-data-into-cortex/entities-overview/entities/ownership.md; engrams' "codebase that owns the profile" pattern in https://builders.cortex.io/blog/introducing-engrams/).
- **Human escalation as a first-class branch**, and autonomy "earned, not enabled" — grant the factory more trust as its PRs pass review (https://builders.cortex.io/blog/software-factories-are-operating-models/).
- **Caveat on durable workflows:** Stonebraker's own post notes a workflow may hold locks for its whole duration or need compensating transactions across committed steps, and "a simple application can be considered a degenerative workflow" (https://www.dbos.dev/blog/applications-are-dead-long-live-workflows). With one operator and a Mac mini, keep the workflow surface to the genuinely long-lived waits (queued sessions, approvals, watches) and leave short CRUD as ordinary queries.

## 6. Gaps and disagreements

- **Scaffolder and plugin internals** (template declaration, plugin types, development reference) are title-level only here.
- **Workflow triggers and the Workflow YAML schema** were not read; only the block model, run-state object, approvals and permissions are verified.
- **AI Readiness / AI Governance rule lists:** the simplified nine-rule table and the fuller CQL lists do not agree, and the fuller lists are unverified in this run.
- **DBOS operational limits** (system-table growth, Postgres-outage behaviour, production checklist, running cost) are not established.
- **AI model providers** for Cortex's chat are not stated in any page read; only the OpEx Review Agent's pipeline models (Haiku/Sonnet/Opus) are documented.
