### Keep mechanics

Deduplication is two-mode: **partial** (group alerts that match chosen fingerprint fields, with a pre-built rule per provider) and **full** (discard exact duplicates, excluding explicitly ignored fields). Pipeline order is ingest → enrich → deduplicate, and **topology correlation is the stage after dedup**. Correlation is manual rule-writing: AND/OR conditions over alert attributes that produce either a full incident or an **"Incident-candidate" requiring manual approval**, with dynamic incident naming via `{{ alert.attribute }}` templates. Non-Kubernetes ingestion is real — the provider index lists Sentry, Grafana, Webhook, HTTP, Loki and OnCall — but **ClickHouse is listed only as a database-interaction provider**, so HyperDX/OTel alerts must arrive through the generic Webhook provider.

**Concept worth copying:** the alert-to-incident promotion gate (candidate first, incident on approval) plus rule predicates over alert attributes — you get PagerDuty's event-orchestration shape without the vendor. **Main weakness:** a 668-issue backlog and a generic-webhook path that needs you to supply real fingerprint fields yourself.

Operational specifics of Keep's topology processor (enable flag, interval, lookback window), its fingerprint-field defaults, maintenance-window suppression, its Alertmanager/Sentry provider parameters and its workflow YAML schema are carried in `unverified` — those doc pages were not confirmed in this run, so plan around Keep's features by reading them directly before committing.

### Sentry vs GlitchTip grouping

Sentry's per-project **Issue Grouping → fingerprint rules** use `matcher:glob -> value`, first matching rule wins, with matchers including `error.type`, `error.value`, `logger`, `level`, `message`, `stack.abs_path`, `stack.function`, `stack.module`, `stack.package`, `tags.<name>`, `app:yes/no` and `family:native`. Crucially, including `{{ default }}` **refines** rather than replaces default grouping, and `title=` renames the resulting issue. **Concept worth copying:** express overrides as refinements of a sane default, so a rule can be one line rather than a full grouping spec. GlitchTip is the credible lightweight stand-in (MIT, Django/PostgreSQL, ~512 MB RAM, PostgreSQL 14+), but a third-party comparison describes its alerting only as per-project **frequency rules** to email/webhook and says nothing about Sentry-style fingerprint control — its grouping overrides are unverified.

## 2. AI root-cause and remediation outside Kubernetes

**HolmesGPT** is Apache-2.0 under the `HolmesGPT` GitHub org, presented as a CNCF Sandbox project ("HolmesGPT a Series of LF Projects, LLC"), latest release **0.45.0 (2026-10-15)**. It has an explicit *"No Kubernetes Required"* path — skip `kubectl apply` and run `holmes ask "what Prometheus alerts are currently firing and why?"` — installable via `brew tap robusta-dev/homebrew-holmesgpt`, `pipx install holmesgpt`, source, or Docker, with Anthropic, OpenAI, Azure, Bedrock, Gemini, Vertex and Ollama providers. **Coroot** is Apache-2.0 and very active (v1.28.1, 2026-10-21). eBPF collection genuinely supports non-orchestrated hosts — "Standalone containers: Docker, Containerd, CRI-O" plus systemd units — on Linux kernel 4.16+ (CO-RE profiling wants Ubuntu 20.10+/Debian 11+/RHEL 8.2+), with no Docker-in-Docker, no WSL1, and **no documented macOS support**, so the Mac mini can run only the server side. Measured footprint is modest: 200m CPU (20% of one core) at 10,000 requests/second with latency inside measurement error. **But the edition split is decisive:** Community includes eBPF metrics, tracing, logs, continuous profiling, service map, SLOs, alerting and "Agentic-ready Observability (MCP)"; **AI-powered RCA and agentic anomaly detection are Enterprise-only at $1 per monitored CPU core/month** (their own example: 10 nodes × 4 vCPU = 40 cores = $40/month). **Concept worth copying:** SLO tracking and deployment tracking driven off eBPF with no instrumentation. **Main weakness:** the feature you actually want is the paid one, and it wants its own storage stack.

## 4. Per-repo descriptors and maturity scorecards

**Backstage.** The catalog descriptor envelope is `apiVersion` + `kind` + `metadata` + `spec`, file conventionally `catalog-info.yaml`, with kinds `Component`, `Template`, `API`, `Group`, `User`, `Resource`, `System`, `Domain`, `Location` (`Template` is `backstage.io/v1beta2`, the rest `backstage.io/v1alpha1`). A `Component` requires `spec.type` (well-known: `service`, `website`, `library`), `spec.lifecycle` (`experimental`, `production`, `deprecated`) and `spec.owner` — and the docs warn `owner` is "for display purposes, not to be used by automated processes". Annotations that actually exist and matter for a solo repo: `github.com/project-slug` (`owner/repo`), `backstage.io/source-location`, `backstage.io/techdocs-ref` (`dir:.`), `sentry.io/project-slug`, `sonarqube.org/project-key`, `backstage.io/code-coverage`; `backstage.io/github-actions-id` is deprecated in favour of `github.com/project-slug`, and no `kubernetes-id` key appears on that (explicitly non-exhaustive) page. **Concept worth copying:** `spec.type` + `spec.lifecycle` + a repo-slug annotation — four fields that make 30 repos filterable. **Main weakness:** Backstage itself is a platform, not a file format; consume the YAML headlessly rather than adopting the portal.

**Score** (Apache-2.0, `0.4.1` published 2026-05-25, last push 2026-09-07 — maintained but slow) uses schema `score.dev/v1b1` with `metadata` (name + free-form annotations), required `containers`, optional `service`, and `resources` each carrying `type`, optional `class`, `id`, `metadata.annotations` and `params`, with `${resources.<name>.<output>}` interpolation; `score-compose` renders docker-compose.yaml and `score-k8s` renders manifests.yaml. **Concept worth copying:** `${resources.db.host}`-style interpolation so one file renders per environment. **Main weakness:** the payoff is platform-team templating; a solo dev hand-writing compose gets overhead.

**OpsLevel** organises an org-wide **Rubric** (Checks → Levels) that drives the overall maturity level, while **Scorecards** are team-scoped lighter rubrics that explicitly do *not* affect overall maturity, are an "Advanced feature", and are driven via UI, GraphQL, Terraform provider or `opslevel create scorecard`. Cortex uses the same vocabulary (rules organised into Bronze/Silver/Gold-style levels, continuously evaluated, with rule exemptions) but only from search snippets here. Both are commercial SaaS; pricing and free tiers are unverified. **Main weakness for one person:** a scorecard product to maintain 30 repos is more work than the scorecard.

**OpenSLO** v1 uses `apiVersion: openslo/v1` with kinds `SLO`, `SLI`, `Service`, `DataSource`, `AlertPolicy`, `AlertCondition`, `AlertNotificationTarget` — a good vocabulary to borrow, but the repo's licence and release status are unverified.

**Recommended minimal manifest** (one `catalog-info.yaml` per repo): `kind: Component`; `metadata.name`; `spec.type`; `spec.lifecycle`; `spec.owner` (your GitHub login); annotation `github.com/project-slug`; `metadata.links` for runbook and dashboard. Add `backstage.io/techdocs-ref` only where mkdocs really exists. Skip `System`/`Domain`/`Group` hierarchies, `dependsOn`, `providesApis`, SaaS scorecards, and `score.yaml` unless a pipeline consumes it. Encode maturity as a 5–8 item checklist inside the same file; add an OpenSLO `SLO` object only for repos with a real user-facing objective.

**Renovate vs Dependabot.** Renovate is **AGPL-3.0-only** (npm registry `renovate` 44.176.2; GitHub metadata `AGPL-3.0`). Its automerge waits for required status checks and merges at most one branch per target branch per run; the documented non-major pattern is `matchUpdateTypes: ['minor','patch']` with `matchCurrentVersion: '!/^0/'` to exclude pre-1.0 deps; `automergeType: branch` pushes without a PR but is incompatible with branch protection. `minimumReleaseAge` (renamed from `stabilityDays`) is a duration with repo/packageRule/manager/updateType scopes, and Renovate's own guidance recommends `"14 days"` when automerging third-party dependencies. Merge Confidence badges run on Mend's private algorithm over only the go/npm/maven/pypi/nuget/packagist/rubygems datasources, and Merge Confidence *workflows* ("only raise a PR at High confidence") are gated to paying Mend customers or OSS Cloud. Dependabot's `groups` supports `patterns`, `exclude-patterns`, `dependency-type`, `update-types`, `applies-to: version-updates|security-updates` and `group-by: dependency-name`, and it now applies a default **3-day `cooldown` to version updates only** (security updates exempt), tunable via `default-days`/`semver-major-days` (30)/`semver-minor-days` (7)/`semver-patch-days` (3) in a 1–90 range.

**Solo policy that follows:** automerge patch+minor for non-0.x dependencies behind required CI; `minimumReleaseAge` or Dependabot `cooldown` at 7–14 days; majors get their own PR and human review; group devDependencies; prefer Renovate (AGPL, self-hosted Docker, no per-seat price) unless the estate is already GitHub-only. Dependabot's auto-merge behaviour and plan limits remain unverified.

## 5. Evaluation methods

**Grouping quality.** The dominant pitfall is measuring with pairwise precision on a hand-built benchmark: it is systematically optimistic (often near 1.0 while true precision is far lower) and feeding it into F1 causes **rank reversals** between systems. The fix is an entity-centric protocol: sample alerts (uniform record sampling ≈ probability-proportional-to-size cluster sampling), recover the **whole** true group around each sample while recording over-clustering (intruders) and under-clustering (missing members) errors, then estimate pairwise, B-cubed and cluster precision/recall from those per-cluster counts. In simulation, bias was under 0.4% with PPS cluster sampling at n ≥ 400, and estimator accuracy ranked **B-cubed > cluster metrics > pairwise** (pairwise RMSE ~4.7% at n=200 and 2.4% at n=800 for a 91%-precision system).

Know the degenerate arithmetic before trusting any number: an all-singletons prediction has precision 1 for every element (recall = share of true singletons), and a single-giant-cluster prediction has recall 1 for every element with mean precision Σ(|c|²−|c|)/(|E|²−|E|) — so "many tiny groups" maxes precision and "one giant group" maxes recall. **B-cubed can never reach 0** (each element is always in its own intersection; a 2-element fully-wrong partition scores 0.66); the paper's ELM repair scores 0.80 vs B-cubed 0.83 on a real clustering. B-cubed is also the only family satisfying all four of Amigó's constraints (homogeneity, completeness, rag-bag, cluster-size-vs-quantity) — plain pairwise F1 fails at least one. Practical rule: judge grouping by precision *and* recall against labelled incidents, never by alert-compression ratio; one lab found a time-window rule compressing alerts 5.5× while merging unrelated incidents.

**Level- vs edge-triggered.** Kubernetes' controller model is the template: a `spec` holds desired state, controllers only move current toward desired, they "never reach a stable state" by design, they report observed state back so other loops can react, and labels scope ownership because several controllers may write the same kind. Transposed to your estate: store desired remediation state as a declarative record per repo; re-derive current state (git/CI/health) and *rewrite* toward desired instead of reacting once to an event; write observed state onto the same record so the human digest reads one field; make every reconcile idempotent so crash-replay is harmless. Edge-triggered alerts then only *schedule* a reconcile. (The `observedGeneration`/resync specifics of the SIG-API-Machinery doc are unverified.)

**DORA** is now **five** metrics, not four, and MTTR is gone: change lead time (commit → production), deployment frequency, **failed deployment recovery time**, change fail rate and **deployment rework rate** (unplanned deployments caused by a production incident). Page last updated 2026-01-05. **`dora-team/fourkeys` is archived** (last push 2024-01-23, v1.0.2 from 2023-05-04) — do not build on it; compute the five keys yourself from commit→deploy timestamps, deploy counts, rework deploys and recovery intervals.

**Fault injection.** Pumba (Apache-2.0, 1.2.1 released 2026-08-23, pushed 2026-10-21) is the container-native choice; Toxiproxy (MIT, v2.13.0, 2026-10-14) is a TCP proxy, so its fault surface is network-level only — it can validate remediation triggered by network degradation, not container death or CPU/memory exhaustion. Chaos Toolkit ships `chaostoolkit/chaostoolkit:latest` (Alpine, no extensions) and `:basic` (Ubuntu, with extensions), i.e. Docker support comes through the extension/driver model; the Docker driver's maintenance status and the project licence are unverified.
