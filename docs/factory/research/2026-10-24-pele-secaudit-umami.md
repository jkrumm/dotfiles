## Bottom line

- **Pele** (`obsidianmd/pele`) is a small, synchronous, zero-dependency **renderer that consumes Mermaid 12.1.0 syntax and emits SVG** — it is not a new diagram language and not a general charting library: at v1.10.0 (npm `pele@1.10.0`, published 2026-10-24) out of a repo created 2026-10-05, it is roughly three weeks old at the time of writing, fast-moving and not battle-tested. It runs outside Obsidian as an npm ES module or browser global, but **ships no CLI** and documents no Node/SSR recipe; versus Mermaid it is far smaller and faster (its own bench: 230 kB gzip vs 1.6 MB, 0.05–0.3 ms vs 6–82 ms), but has no arbitrary HTML labels, no Mermaid themes, no bundled KaTeX, its own layout, and only Mermaid's chart set (`xychart`, `pie`, `quadrantChart`, `radar-beta`, `treemap-beta`, `sankey`) — so it suits architecture/flow/state diagrams in Obsidian notes and standalone HTML, not real data charts.
- **`cloudflare/security-audit-skill`** is an **agent-neutral coding-agent skill** (installed with `npx skills add … --skill security-audit`, not a CI tool) that runs a six-phase audit — recon, coverage-led hunting, adversarial validation, schema-validated findings, independent verification, reporting — producing `findings.json` plus `REPORT.md` / `FINDINGS-DETAIL.md` / `NEEDS-VALIDATION.md`. **No GitHub Actions/CI path is documented**; it fits a recurring sweep over many small repos via the `quick` profile, per-repo output directories and an agent-invocation budget cap, but it is token-expensive and one run finds "roughly half" of what repeated runs find, so plan repeat passes rather than a single gate.
- **Umami** self-hosted v3 is released (latest **v3.4.1, 2026-10-23**, MIT) and self-hosting includes custom events with event data, goals, funnels, journeys, retention, UTM, revenue, attribution, segments (v3.0+), boards/session replay (v3.1+), heatmaps (v3.2+), MCP (v3.4+, off by default) and API access; only email reports are Cloud-only. The read API gives per-site stats, pageviews, event series, metric breakdowns and realtime, but **no anomaly-detection or alerting endpoint exists in the documented insight suite** — you compute anomalies yourself from `/stats` and `/events/series`. React/TanStack integration is one `<script data-website-id>` in the root layout (History API route changes are auto-tracked) plus `umami.track()` or `data-umami-event*` attributes for custom events.

## 1. Pele — Mermaid syntax in, SVG out

**Purpose and scope.** Pele "renders Mermaid diagrams to SVG. It is small, synchronous, has no runtime dependencies, and uses CSS variables for colors and fonts", and it "supports every diagram type built into Mermaid 12.1.0". Entry points are `pele` (core + all diagrams), `pele/core` with `register()`, `pele/diagrams/<type>`, `pele/lazy` (`renderAsync()`) and `pele/global` (a `dist/pele.global.js` loadable from jsDelivr) ([README](https://github.com/obsidianmd/pele/blob/HEAD/README.md)).

**Syntax.** There is no Pele syntax to learn: input is Mermaid 12.1.0 source. Mermaid's own themes/`themeVariables` do not apply — colours and fonts come from CSS variables — and layout is Pele's own, so output differs visually from Mermaid. Labels "use SVG text… Arbitrary HTML labels are not supported", KaTeX is not bundled (you pass a `math` resolver), and ZenUML/external Mermaid plugins are unsupported ([compatibility notes](https://pele.run/compatibility)).

**Rendering target.** SVG only — the library returns SVG strings/markup, not canvas, PNG or HTML. `render(source, options)` returns `{svg, width, height, type, mermaidType, links}` synchronously; defaults cap input at 50,000 source characters, output at 4,000,000 characters and 5,000 edges. `mount(el, text)` handles browser containers with responsive/zoom behaviour, reads fonts from CSS, auto-prefixes SVG IDs, and in Obsidian context internal links contain note names in `href` ([API docs](https://pele.run/api)).

**Maturity.** Repo created 2026-10-05, last push 2026-10-24, 3,369 stars, latest release 1.10.0 published 2026-10-24, not archived; npm `pele@1.10.0` has **zero dependencies/peerDependencies** and declares `engines: node >=20` ([repo](https://github.com/obsidianmd/pele), [npm](https://www.npmjs.com/package/pele)). One inconsistency worth knowing: GitHub's licence detection reports `NOASSERTION` while the README and npm both state MIT. Treat the version as moving fast — three weeks of history means no long tail of production reports.

**Outside Obsidian?** Yes for rendering, no for CLI. The npm package is a standard ES module plus a browser global, so it drops into a standalone HTML report or a bundler. But the published `package.json` has **no `bin` field** and exports only `.`, `./core`, `./lazy`, `./diagrams/*`, `./global` — there is no executable ([package.json](https://github.com/obsidianmd/pele/blob/HEAD/package.json)). No documented Node/SSR recipe exists either; the one hint is that `render()` uses a canvas measurer in browsers but "a built-in width table elsewhere", which suggests headless use works but is unproven in the docs ([API docs](https://pele.run/api)).

**Versus Mermaid, per Pele's own homepage table:** 230 kB gzip vs 1.6 MB, render time 0.05–0.3 ms vs 6–82 ms, 0 vs 23 direct dependencies; it describes itself as "developed for Obsidian to render diagrams quickly and match your theme" ([pele.run](https://pele.run)). These are vendor benchmarks — directionally useful, not independently verified.

**For architecture/flow/state diagrams and charts:** coverage is Mermaid's, and working examples exist for `flowchart`, `stateDiagram-v2`, `architecture-beta`, `sequenceDiagram`, `C4*`, `pie`, `xychart`, `quadrantChart`, `radar-beta`, `treemap-beta` and `sankey` ([examples](https://pele.run/examples)). That is enough for C4-style architecture, flow and state diagrams. It is **not** a chart library: no general bar/line/xy beyond `xychart`, no data binding, no axis/animation tooling. Practical split: use Pele for diagram-heavy Obsidian notes and self-contained HTML reports where bundle size and instant render matter and you accept Mermaid-syntax fidelity with different visuals; keep Mermaid (or a charting library) where you need HTML labels, KaTeX maths in labels, theme parity with existing Mermaid output, or real data charts. For a Node build step that pre-renders SVGs, no CLI exists, so you'd call `render()` from a script and confirm the headless path yourself.

## 2. cloudflare/security-audit-skill — an agent workflow, not a CI scanner

**What it audits.** A six-phase pipeline: recon → coverage-led hunting → adversarial candidate validation → `findings.json` validated by `report-schema.json` → independent record verification → report generation. Hunting is organised by attack-class companions covering web, client, cloud, supply chain, memory safety, LLM and data-isolation classes ([README](https://github.com/cloudflare/security-audit-skill/blob/HEAD/README.md)).

**How it runs.** It is a coding-agent skill, installed with `npx skills add https://github.com/cloudflare/security-audit-skill --skill security-audit` (optionally `--global`), activating on prompts like "security audit this codebase". It requires a coding agent with tool use and parallel sub-agents, Node.js for the zero-dependency validators, and an OS-enforced sandbox (no external network, allowlisted env, resource limits, scratch-only writes) — without the sandbox, leads stay `needs_validation` ([README](https://github.com/cloudflare/security-audit-skill/blob/HEAD/README.md)). Despite the Claude Code-shaped install path, `SKILL.md` is explicitly agent-neutral (it speaks of "Parent", "Task tool", "subagent_type"), defaults to guidance mode and only runs the full six phases on an explicit audit/pen-test request; **no CI or GitHub Actions invocation is described anywhere** — execution is a local agent under a sandbox ([SKILL.md](https://github.com/cloudflare/security-audit-skill/blob/HEAD/skills/security-audit/SKILL.md)).

**Output.** `run-metadata.json`, `architecture.md`, `coverage-ledger.json`, `findings.json` (validated against `report-schema.json` by `validate-findings.cjs`), plus derived `REPORT.md`, `FINDINGS-DETAIL.md` and `NEEDS-VALIDATION.md`. Verdicts are `confirmed` (severity permitted), `needs_validation` (no severity) and `rejected` ([README](https://github.com/cloudflare/security-audit-skill/blob/HEAD/README.md)).

**Suitability for recurring audits across many small repos.** Fits, with caveats. Runs are **additive** — prior ledgers and findings are reused — and "a single run found roughly half of the vulnerabilities that repeated runs found in total", so cadence matters more than depth per run. The `quick` profile is "a bounded pass for small targets, re-runs, or a fast first look" with one hunter wave and one critic pass, and budgets are counted as agent invocations with a hard stop that sets `run_status: "incomplete"` ([SKILL.md](https://github.com/cloudflare/security-audit-skill/blob/HEAD/skills/security-audit/SKILL.md)). Combine `quick` with a per-repo output directory (`~/security-audit-skill/<repo>/run-<N>`) to keep the additive ledger separated per project. Two constraints to budget for: cost scales with coverage units (roughly one hunter per unit, so token-expensive across many repos), and because there is no CI entry point you need an agent harness to drive it on a schedule — it won't sit in a pipeline by itself.

## 3. Umami self-hosted (v3)

**Version and feature set.** Latest release **v3.4.1, published 2026-10-23**, MIT, 39,635 stars ([repo](https://github.com/umami-software/umami)). The v3 docs cover custom events, journeys, session replay, heatmaps, segments, cohorts, retention, goals, funnels, attribution, revenue, boards, sharing, API and an official MCP server; revenue works by attaching values to events ([docs](https://docs.umami.is/docs)). The self-hosted vs Cloud table marks funnels, goals, journeys, retention, UTM, revenue, attribution and API access as included self-hosted, plus segments "v3.0 or later", boards and session replays "v3.1+", heatmaps "v3.2+", MCP "v3.4 or later, disabled by default"; only **email reports are Cloud-only** ([cloud comparison](https://docs.umami.is/docs/cloud)) — relevant if your alerting plan depended on scheduled emails. The documented insight suite is exactly Compare, Breakdown, Funnel, Retention, UTM, Goals, Journey, Revenue, Attribution, with "Goals – Track your goals for pageviews and events" ([insights](https://docs.umami.is/docs/insights)).

**Read API.** Base is `http://<instance>/api`, bearer-authenticated: `GET /websites` (`includeTeams=true`), `/websites/{websiteId}/stats`, `/websites/{websiteId}/active` (last 5 minutes), `/websites/{websiteId}/pageviews`, `/websites/{websiteId}/events/series`, `/websites/{websiteId}/metrics?type=path|referrer|browser|os|device|country|event`, `/metrics/expanded`, and `/realtime/{websiteId}` (last 30 minutes). `startAt`/`endAt` are millisecond epoch timestamps and every call needs `Authorization: Bearer <token|api-key>` ([common endpoints](https://docs.umami.is/docs/api/common-endpoints)). Prefer **API keys** — long-lived and individually revocable; the alternative on self-hosted is `POST /api/auth/login`, and with 2FA enabled that returns a partial token you must finish via `POST /api/2fa/verify` ([authentication](https://docs.umami.is/docs/api/authentication)).

**Anomalies.** No anomaly-detection or alerting insight is listed among the nine documented insights ([insights](https://docs.umami.is/docs/insights)), and self-hosted has no email reports ([cloud comparison](https://docs.umami.is/docs/cloud)). Provisionally, anomaly detection is **not built in**: you derive it yourself by polling `/websites/{id}/stats` and `/events/series` on ms-epoch windows and comparing against a rolling baseline. The caveat on that negative: the full docs index could not be read, so a dedicated alerting page cannot be positively ruled out (see open items). Revenue's mechanics beyond "values attached to events" are likewise not established here.

**Tight React/TanStack integration.** The documented pattern is a **single script tag in the root layout/index.html** with `data-website-id`; the tracker watches History API `pushState`/`replaceState` and `popstate`, so TanStack Router client-side navigations are recorded automatically with no per-route code. Fire custom events either declaratively with `data-umami-event` / `data-umami-event-*` attributes on elements, or imperatively with `umami.track(name, data)` (plus `umami.identify()` for sessions). Do **not** call `umami.track()` bare inside a `useEffect` on mount — that produces duplicate pageviews; use `data-auto-pageview="false"` to suppress automatic pageviews while keeping the tracker, `data-auto-track="false"` to disable initialisation entirely, and `data-exclude-hash="true"` for hash routing ([SPA guide](https://docs.umami.is/docs/guides/track-single-page-apps), [tracker functions](https://docs.umami.is/docs/tracker-functions)). Attribute events are always stored as strings; `umami.track()` data can carry strings, numbers, booleans, arrays and objects, with event-data limits of 4-decimal numbers, 500-character strings/arrays and 50 object properties, all browsable on the Events page Properties tab ([event data](https://docs.umami.is/docs/event-data)). Wrap `umami.track()` in a small typed helper (guarding against `window.umami` being undefined pre-load) rather than sprinkling string literals, since no official React binding was confirmed.
