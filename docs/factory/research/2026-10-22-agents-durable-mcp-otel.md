## Bottom line

- **beads / `bd`**: the backend today is **Dolt**, not JSONL — *embedded* (default, single-writer) or `--server` (multi-writer) — with `.beads/issues.jsonl` demoted to "an export … not the source of truth". Latest release **v1.3.1 (2026-09-30)**, npm `@beads/bd` **1.3.1** (2026-10-01), MIT; the one concept to copy is `bd ready`.
- **Gas Town**: MIT, `gastownhall/gastown`, latest tag **v1.2.1 (2026-06-06)** while main kept moving (~4.5 months with no release); roles and the git-worktree "hook" are real and documented, cost and non-convergence under model upgrades are the failure modes, and whether it has been formally retired is unverified.
- **StrongDM's factory**: holdout scenarios stored outside the agent-visible codebase, a Digital Twin Universe of behavioural clones of *third-party* services, and correctness judged only from externally observable behaviour — with **no published delivery metrics**.
- **Shapiro's five levels**: useful as a bottleneck diagnostic (constraint migrates typing → review → spec/verification), weak because Level 5 has no acceptance criteria and so cannot be falsified.
- **Durable execution**: no engine in the list is SQLite-native; **Absurd** (0.5.1, Apache-2.0, Postgres) and **DBOS Transact** (5.3.0, MIT, Postgres) fit one Mac mini best, **Restate** single-node is the only zero-database option (server is BUSL-1.1), and **Temporal** / **Trigger.dev** are the worst fit.
- **MCP vs CLI**: Anthropic's own numbers show tool-definition bloat is the real cost (150,000 → 2,000 tokens; ~77K → ~8.7K), so the winning pattern is deferred/code-mode tool surfaces rather than dropping tools; every hard number is vendor-internal and no independent A/B was verified.
- **Claude Code OTel**: metrics and log events are documented and stable-ish, **traces are beta** behind `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1`, and spans are named `claude_code.*` with only a handful of borrowed `gen_ai.*` attributes — a real divergence from the GenAI semantic conventions.

## 1. beads / `bd`

**What it is.** "Distributed graph issue tracker for AI agents, powered by Dolt" — a dependency-aware issue graph that replaces markdown plans. Repo `gastownhall/beads` (formerly `steveyegge/beads`), MIT, created 2025-10-12, 28,091 stars, pushed 2026-10-22 ([repo](https://github.com/steveyegge/beads)).

**Storage.** Embedded Dolt is the default (`bd init`, in-process, data in `.beads/embeddeddolt/`, single writer; `database is locked` errors); `--server` mode points at an external `dolt sql-server` with data in `.beads/dolt/` and multiple concurrent writers ([README](https://github.com/gastownhall/beads/blob/HEAD/README.md), [architecture/dolt](https://beads.gascity.com/architecture/dolt)). An HTTP backend (`bd serve` / `bd connect <url> --expect-project-id`, `"backend": "http"` in `.beads/metadata.json`) is experimental and carries a divergence ledger. JSONL is explicitly "an export for viewers and interchange, not the source of truth or a backup"; cross-machine sync is `bd dolt push`/`pull` against `refs/dolt/data` on the git remote. Embedded↔server conversion uses `bd backup init/sync/restore` and preserves full Dolt commit history.

**Migration history:** the docs' "Migrate from SQLite (Legacy)" section states `bd migrate --to-dolt` "was removed in v0.58.0", that pre-0.50 JSONL installs need a migration script, and that the old DB survives as `beads.backup-pre-dolt-*.db` — establishing **JSONL → SQLite → Dolt** ([architecture/dolt](https://beads.gascity.com/architecture/dolt)). beads pins the Dolt CLI to **2.2.0** because 2.3.x regressed `DOLT_RESET('--hard')` (3/60 fresh databases broken on 2.3.0 and 3/60 on 2.3.1 vs 0/60 on 2.2.0).

**CLI surface (relevant to a factory).** `bd ready` / `bd list --ready`, `bd dep add`/`dep tree`, `bd update --if-assignee`/`--if-status` (compare-and-set, exit code 13 on guard mismatch), `bd heartbeat`, `bd reclaim --older-than`, `bd unclaim`, `bd sync` (one pull/conflict-detect/recompute-`is_blocked`/push verb), `bd export`, `bd backup`, `bd prune`, `bd purge`, `bd dolt push/pull`, `bd federation add-peer|sync|status`, `bd init --contributor`, and **`bd serve`** — 41 OpenAPI operations across 35 paths (ready, claim, claimNext, release, close, batchApply, sweep, casMetadata, dependency add-remove, events, memories, `GET /v0/beads/context`) with RFC 9457 problem+json errors and keyset cursors ([releases](https://github.com/gastownhall/beads/releases)).

**Ready queue.** `bd ready` = open issues with no active blocker, excluding `in_progress`, `blocked`, `deferred` and `hooked`; `bd dep add issue-2 issue-1` means issue-2 depends on issue-1 and disappears from ready until closed ([cli-reference/ready](https://beads.gascity.com/cli-reference/ready)). Edge types: `blocks` is hard ordering and affects ready work, `parent-child` blocks structurally (a blocked parent blocks children), `related`/`discovered-from` do not block ([core-concepts](https://beads.gascity.com/core-concepts)). v1.3.1 fixed a genuine correctness bug: closing two blockers of one dependent at once could leave the dependent `is_blocked=1` and absent from `bd ready`; every blocker-removing write now rechecks dependents after commit ([releases](https://github.com/gastownhall/beads/releases)).

**Molecules / formulas / wisps.** Molecules are work graphs — epics whose children flow through `bd ready` in dependency order; formulas are TOML definitions (`[[steps]]` with `needs = [...]`) compiled into molecules (`bd cook`, `bd mol pour`); wisps are ephemeral beads with their own storage plane, either root-only (steps materialised at runtime) or poured (sub-wisps with checkpoint recovery) ([Gas Town README](https://github.com/gastownhall/gastown/blob/HEAD/README.md)). v1.3.1 added `bd purge --wisps-plane --older-than 168h --force`, and `bd purge` never deletes a closed bead a live bead still depends on (`live_dependent_skipped`).

**Multi-repo / cross-project.** Five axes: cross-repo dependencies via `external:` refs resolved against each client's `external_projects` (an unsatisfied external ref keeps the issue out of `bd ready`); contributor auto-routing (`bd init --contributor`) to a repo like `~/.beads-planning`; `BEADS_DIR` as authoritative pointer; shared server mode (one Dolt server at `~/.beads/shared-server/`, port 3308, one DB per project with unique prefixes); and peer-to-peer `bd federation` with AES-256-encrypted credentials ([README](https://github.com/gastownhall/beads/blob/HEAD/README.md)).

**Version and cadence.** Stable **v1.3.1 (2026-09-30)**, "no schema migration" from v1.3.0 ([releases](https://github.com/gastownhall/beads/releases)); npm `@beads/bd` 1.3.1 published 2026-10-01T00:24Z, MIT, zero dependencies ([npm](https://www.npmjs.com/package/@beads/bd)). Cadence is roughly monthly minors with a full RC series each — but note the trap: v1.2.1 (2026-08-11) "shipped by accident, without release testing" and auto-migrated local databases to schema v54–v65; v1.2.2 was a recovery release re-cutting the tested v1.1.2 tree; v1.3.0 landed 2026-09-15; v1.3.2-rc.1/rc.2 are newer pre-releases, and stable channels deliberately do not serve RCs.

**Copy this:** `bd ready` — one blocker-aware query that drives *all* orchestration, recomputed on every blocker-removing write. **Main weakness:** backend and schema churn plus lockstep version coupling (a schema guard, and one release that migrated databases to a schema no supported binary understood).

## 2. Gas Town

**What it is / status.** MIT, repo `gastownhall/gastown` (formerly `steveyegge/gastown`), created 2025-12-16, 18,468 stars, 508 open issues, pushed 2026-10-21 — but **latest release v1.2.1, 2026-06-06**, i.e. ~4.5 months of main-only commits ([repo](https://github.com/steveyegge/gastown), [releases](https://github.com/gastownhall/gastown/releases)).

**Roles.** Mayor (primary AI coordinator, a Claude Code instance; `gt mayor attach`), Town/HQ (`~/gt`), Rigs (project containers wrapping a git repo, each with a beads prefix), Crew Members (your own workspace), **Polecats** ("worker agents with persistent identity but ephemeral sessions"), **Hooks** (git-worktree persistent storage), **Convoys** (bead bundles; `mountain`-labelled convoys get stall detection and smart skip), **Witness** (per-rig lifecycle manager detecting stuck polecats and triggering recovery), **Deacon** (cross-rig supervisor on continuous patrol cycles), **Dogs** (infrastructure workers, e.g. Boot for triage), **Refinery** (per-rig Bors-style bisecting merge queue), plus Daemon (Go process, 3-min heartbeat), Overseer (top of escalation) and Scheduler ([README](https://github.com/gastownhall/gastown/blob/HEAD/README.md)).

**How it coordinates sessions.** tmux 3.0+ is the session substrate for all tmux-backed roles; hooks are git worktrees; the beads ledger is the work state; `gt sling <bead-id> <rig>` dispatches work; Claude gets hooks in `.claude/settings.json` for mail injection and startup, while non-hook runtimes fall back to `gt prime` plus optional `gt mail check --inject`.

**Propulsion principle.** "Gas Town uses git hooks as a propulsion mechanism. Each hook is a git worktree with: Persistent state — work survives agent restarts; Version control; Rollback capability; Multi-agent coordination — shared through git," with lifecycle Created → Active → Suspended → Active → Completed → Archived ([README](https://github.com/gastownhall/gastown/blob/HEAD/README.md)). This maps directly onto a herdr/multiplexer factory: the hook, not the session, owns the work.

**Failure modes.** Operationalised in `gt feed --problems` at 20–50+ agents, grouping agents as "GUPP Violation" (hooked work with no progress for an extended period), "Stalled", "Zombie" (dead tmux session), Working, Idle — with `n` to nudge, `h` to hand off; troubleshooting covers `gt hooks repair` (agents losing connection), `gt convoy refresh` (stuck convoys) and an unresponsive Mayor ([README](https://github.com/gastownhall/gastown/blob/HEAD/README.md)). v1.2.0 pinned dependencies and fails fast: "Dolt 2.0.7 or newer is required. Beads bd v1.0.4 is the supported version for this release… fails fast if it detects a newer unsupported bd version" ([releases](https://github.com/gastownhall/gastown/releases)).

**Cost.** One third-party estimate puts Gas Town at roughly **10x standard Claude Code token cost and about $100/hour of parallel work**, with monthly estimates from $5,000 to $72,000 — estimates of varying rigour, not vendor figures ([echofold.ai](https://echofold.ai/articles/gas-town-multi-agent-orchestrator-claude-code)).

**Copy this:** the hook — per-agent worktree holding work state, so a respawned session resumes without re-prompting. **Main weakness:** cost and convergence (regression when the underlying model changed).

## 3. StrongDM's software factory

**What it is / status.** A public writeup at `factory.strongdm.ai` describing a 3-person AI team (Justin McCarthy, Jay Taylor, Navan Chauhan) founded **2025-07-14**, first described publicly ~2026-02-06/07. Charter: "Code must not be written by humans. Code must not be reviewed by humans," plus the heuristic "If you haven't spent at least $1,000 on tokens today per human engineer, your software factory has room for improvement" ([factory.strongdm.ai](https://factory.strongdm.ai/)). StrongDM was acquired by Delinea (announced 2026-01-15, completed 2026-03-05) ([rywalker.com](https://rywalker.com/research/strongdm-factory)).

**Architecture.** Seed (spec/PRD/screenshot) → validation harness → feedback, and "the loop runs until the holdout scenarios pass (and stay passing)", with validation end-to-end, "as close to the real environment as possible" ([principles](https://factory.strongdm.ai/principles)). Only *fully specified* work runs non-interactively ("shift work"). Code is treated "analogously to an ML model snapshot: opaque weights whose correctness is inferred exclusively from externally observable behavior" ([techniques](https://factory.strongdm.ai/techniques)).

**Scenario holdouts.** "Scenario" was repurposed to mean an end-to-end user story "often stored outside the codebase (similar to a 'holdout' set in model training)", because an in-repo test "can be lazily rewritten to match the code"; success is a probabilistic "satisfaction" score over observed trajectories ([factory.strongdm.ai](https://factory.strongdm.ai/)). Willison glosses it as scenarios "used to evaluate the software but not stored where the coding agents can see them" — a simulated external-QA team ([Willison](https://simonwillison.net/2026/Feb/7/software-factory/)).

**Digital Twin Universe.** Behavioural clones of *third-party* services — Okta, Jira, Slack, Google Docs/Drive/Sheets — replicating "APIs, edge cases, and observable behaviors", validated against the live service "until we stop finding behavioral differences"; fidelity target is 100% compatibility with popular official SDK client libraries. It buys thousands of scenarios/hour with no rate limits, abuse detection or API cost, plus deterministic replay ([techniques/dtu](https://factory.strongdm.ai/techniques/dtu)).

**What replaces review.** Gates = satisfaction threshold + holdouts staying green + twin behavioural diffing + automated repair. Shapiro's eyewitness account adds **CXDB** (observability over every interaction) and **Healer** (clusters bad behaviour into diagnoses, spawns investigation agents that locate the code and write a prescription) — "No human filed the bug report. No human triaged it. No human wrote the fix" ([Shapiro](https://www.danshapiro.com/blog/2026/02/you-dont-write-the-code/)). Tooling shipped: **Attractor** as an nlspec only, Apache-2.0, ~1.3k stars ([repo](https://github.com/strongdm/attractor)), and **CXDB**, Apache-2.0 ([repo](https://github.com/strongdm/cxdb)). Model routing is published as a per-role "Weather Report" with entries through 2026-09-28 ([weather-report](https://factory.strongdm.ai/weather-report)).

**Reported metrics: none for delivery.** No outcome or throughput data has been published — "The weather-report has a few sparse updates between February and June" ([dex/HumanLayer](https://x.com/dexhorthy/article/2080697380379427275)); Willison: "the 'dark factory' thing is basically unproven right now… I'm not ready to say that it's a good idea or that it's demonstrated to work outside of a demo I saw for an hour" ([HN](https://news.ycombinator.com/item?id=46739117)). Economics are the real number: ~$20k/month/engineer implied by the $1,000/day heuristic ([Willison](https://simonwillison.net/2026/Feb/7/software-factory/)).

**Weaknesses.** No published throughput/quality data; the opacity argument gives no fast oracle for maintainability (models "cannot maintain codebase quality" because RL has "no penalty for eroding… maintainability", so review agents "raise the floor… don't move the ceiling") ([dex](https://x.com/dexhorthy/article/2080697380379427275)); domain is unusually API-shaped and twin fidelity is "a design claim… not proven prevention"; the "no humans" framing hides heavy human work in specs, scenario curation, twin fidelity and routing ([rywalker](https://rywalker.com/research/strongdm-factory)).

**Copy this:** holdout discipline — validation artefacts live outside agent-writable scope and are scored on behaviour, not asserted truth. **Main weakness:** zero published evidence that it produces maintainable software.

## 4. Dan Shapiro's five levels / "dark factory"

**What it is.** "The Five Levels: from Spicy Autocomplete to the Dark Factory", published **2026-01-23**, modelled on NHTSA's 2013 driving-automation levels and told as car analogies ([post](https://www.danshapiro.com/blog/2026/01/the-five-levels-from-spicy-autocomplete-to-the-software-factory/)): L0 parents' Volvo ("not a character hits the disk without your approval"); L1 lane-keeping + cruise control, offloading discrete tasks to "your AI intern"; L2 highway Autopilot, a "junior buddy", "where 90% of 'AI-native' developers are living"; L3 Waymo with a safety driver — "you are a manager… your life is diffs", and "almost everyone tops out here"; L4 robotaxi — "you're a PM", write and argue the spec, craft skills "for Claude Code", review plans, leave "for 12 hours, and check to see if the tests pass"; L5 — "it's not really a car any more… your software process isn't really a software process any more. It's a black box that turns specs into software."

**Dark factory.** From the Fanuc lights-out plant: "it's dark, because it's a place where humans are neither needed nor welcome"; the doers are "small teams, less than five people". Note the label set ("Spicy autocomplete / coding intern / junior developer / developer / engineering team / dark software factory") comes from Willison's relay, not the post text ([Willison](https://simonwillison.net/2026/Jan/28/the-five-levels/)) — treat 0–4 labels as unconfirmed wording.

**What he says is required.** Not a checklist: a role transformation — stop being the best coder, stop reviewing (you are the bottleneck), then own "who understands it / how do you know it works / is it getting better", and convert every manual check into an automated rule ("Why am I doing this?") ([2026-02-13](https://www.danshapiro.com/blog/2026/02/you-dont-write-the-code/)). The engine, per 2026-03-11: "AI gets better when you do more of it", via *slot-machine development* (ask three models, take the best) and *the trycycle* (define → plan → retry until the plan is perfect → implement → loop); he ships `danshapiro/trycycle` and `danshapiro/kilroy` ([post](https://www.danshapiro.com/blog/2026/03/dark-factories-rise-of-the-trycycle/)).

**Weaknesses.** Level 5 is left undescribed for humans — critics note he "didn't even describe what a human would still do at level 5 nor why it would be desirable"; the ladder is descriptive, implies monotonic progress, and has no entry criteria, cost, governance or safety dimension; the driving analogy is weak (NHTSA levels classify vehicle capability with defined ODDs, not a human's job title); and the author is an interested party ([HN](https://news.ycombinator.com/item?id=46739117)).

**Copy this:** the ladder as a *bottleneck diagnostic* — at each level the binding constraint migrates (typing → review → spec + verification throughput), and the "L2 trap" (it feels terminal but is not) is the real risk. **Main weakness:** it names destinations without acceptance criteria, so L5 cannot be falsified.

**Key mechanisms.** DBOS: "There's no separate orchestration server and no infrastructure required besides Postgres"; PENDING workflows recover automatically at startup in single-node deployments, while cross-executor recovery expects DBOS Conductor (paid control plane, dashboards, retention) ([architecture](https://docs.dbos.dev/architecture)); deterministic workflows, checkpointed step outputs, database-stored wakeup times, workflow ID as idempotency key ([tutorial](https://docs.dbos.dev/typescript/tutorials/workflow-tutorial)); the MIT core ships with a peerDependency on `@dbos-inc/dbos-enterprise` ([npm](https://www.npmjs.com/package/@dbos-inc/dbos-sdk)). Absurd: the entire engine is one `absurd.sql` schema — "no extra services, no message brokers, no coordination layer" — steps are checkpoints whose return values persist, tasks `sleep` or `awaitEvent` with "first emit wins" ([docs](https://earendil-works.github.io/absurd/)); published as `absurd-sdk` 0.5.1, Apache-2.0, repo described as "An experiment in durability" ([npm](https://www.npmjs.com/package/absurd-sdk)). Restate: single node persists to an embedded store with fsync before ack; durability defined by the disk ([server overview](https://docs.restate.dev/server/overview)); its LICENSE is Business Source 1.1, "not an Open Source license", while the SDK is MIT ([LICENSE](https://github.com/restatedev/restate/blob/HEAD/LICENSE)). Inngest's server is SSPL-1.0 with an Apache-2.0 future grant while the SDK is Apache-2.0 — a genuine SDK/server licence discrepancy ([LICENSE.md](https://github.com/inngest/inngest/blob/HEAD/LICENSE.md), [npm](https://www.npmjs.com/package/inngest)). Mastra's dist-tags show libSQL/SQLite storage adapters and persisted-approval fixes in the 1.x line ([npm](https://www.npmjs.com/package/@mastra/core)). XState declares no storage of any kind, so state persistence is yours ([npm](https://www.npmjs.com/package/xstate)).

**Fit.** Best: **Absurd** (one SQL file, no service, `awaitEvent` is literally your approval inbox) and **DBOS** (library, checkpoints in the same Postgres as your ledger). **Restate** single-node is the only zero-DB option but BUSL. **XState** is best if "await human" is pure state and you accept writing persistence, timers and scheduling. Worst: **Trigger.dev** and **Temporal** (multi-service footprint plus a replay-determinism tax on inherently non-deterministic LLM steps), then **Inngest**/**Hatchet** (server + database for one user).

**Copy this:** Absurd/DBOS — *checkpoint the step result in the same transaction as your own domain write*, so "approved" and "resumed" can never diverge. **Main weakness:** Absurd is a 0.5.x experiment; DBOS requires Postgres; Restate's server is BUSL; Temporal is heavy; XState ships no scheduler.

## 6. MCP servers vs plain CLIs

**Anthropic's position is not "drop MCP" but "stop injecting every definition".** *Code execution with MCP* (2025-11-04) reports a Google-Drive→Salesforce task dropping tool-definition tokens from **150,000 to 2,000 (98.7%)**, and notes a 2-hour transcript can add ~50,000 tokens of intermediate results; progressive disclosure is offered two ways — MCP tools as files the agent reads on demand, or a `search_tools` tool with a detail level ([post](https://www.anthropic.com/engineering/code-execution-with-mcp)). The same post warns code execution "introduces its own complexity": sandboxing, resource limits and monitoring are "operational overhead and security considerations that direct tool calls avoid."

**Numbers that matter for a factory.** Tool Search Tool / `defer_loading: true` (2025-11-24): **~77K → ~8.7K tokens**, "preserving 95% of context window", "an 85% reduction", with 191,300 vs 122,800 tokens cited; Anthropic's internal definitions once consumed **134K tokens**; a 5-server survey (GitHub, Slack, Sentry, Grafana, Splunk) totals 58 tools ≈ 55K tokens. Accuracy on MCP evals: Opus 4 **49% → 74%**, Opus 4.5 **79.5% → 88.1%**. Programmatic Tool Calling: **43,588 → 27,297 tokens (37%)**; Tool Use Examples: **72% → 90%** parameter accuracy. Anthropic itself says search "adds a search step before tool invocation" and pays off mainly above ~10K tokens of definitions or 10+ tools ([post](https://www.anthropic.com/engineering/advanced-tool-use)).

**Skills.** "Folders of reusable instructions, scripts, and resources"; adding a `SKILL.md` "creates a structured skill" ([post](https://www.anthropic.com/engineering/code-execution-with-mcp)). Skills are first-class in Claude Code telemetry (`skill_name` on the tool span).

**The CLI-first counterargument** is made in practitioner write-ups framing schemas as an ambient "token tax" on tools the agent never calls, and in a reported benchmark of 75 CLI-vs-MCP tests ("10–32x cheaper per run", "100% reliable versus 72%", 1,400 vs 44,000 tokens) — both seen only as search snippets, not read ([nardit](https://max.nardit.com/articles/the-token-tax-of-agent-tools), [summary](https://www.linkedin.com/posts/victor-ugochukwu_clis-are-quietly-winning-the-agentic-workflow-activity-7437829984435482624-w4gD)). Treat circulating MCP-vs-CLI reliability and latency multipliers as unverified secondary reporting; no rigorous public A/B was verified.

**Copy this:** a *token budget for the tool surface* — defer everything, keep 3–5 hot tools resident, let the agent read definitions on demand. **Main weakness:** every strong number is vendor-internal, and code-mode buys context with a sandbox you must operate.

## 7. Claude Code OpenTelemetry, late 2026

**Status.** Docs page dated **2026-10-21**: metrics over the metrics protocol, events over logs, and "optionally distributed traces", with tracing off by default and requiring both `CLAUDE_CODE_ENABLE_TELEMETRY=1` and `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1` plus `OTEL_TRACES_EXPORTER` (`console` | `otlp` | `none`) ([docs](https://code.claude.com/docs/en/monitoring-usage)). `OTEL_EXPORTER_OTLP_PROTOCOL` accepts grpc, http/json, http/protobuf — "Claude Code has no default protocol".

**Metrics:** `claude_code.session.count`, `.lines_of_code.count`, `.pull_request.count`, `.commit.count`, `.cost.usage` (USD), `.token.usage` (tokens), `.code_edit_tool.decision`, `.active_time.total`.

**Events/logs:** `claude_code.user_prompt`, `assistant_response`, `tool_result`, `tool_decision`, `api_request`, `api_error`, `api_refusal`, `api_request_body`, `api_response_body`, `permission_mode_changed`, `auth`, `mcp_server_connection`, correlated by `prompt.id` and `event.sequence`.

**Traces (beta).** Per prompt a root `claude_code.interaction`; children `claude_code.llm_request` and `claude_code.tool`; each tool span splits into `claude_code.tool.blocked_on_user` (permission wait) and `claude_code.tool.execution`; subagent spans nest under the parent's `claude_code.tool`; `claude_code.hook` only under detailed beta tracing. Tool attributes: `tool_name` + `tool_name_safe` (unknown MCP tools collapse to `mcp_other`), `bash_command_class`, `bash_argv0`, `tool_use_id`, `duration_ms`, `result_tokens`, with `file_path`/`full_command`/`skill_name`/`subagent_type` gated behind `OTEL_LOG_TOOL_DETAILS`.

**Divergence from GenAI semconv.** Claude Code borrows only `gen_ai.system` (always `"anthropic"`), `gen_ai.request.model`, `gen_ai.response.id`, `gen_ai.response.finish_reasons`, `gen_ai.tool.call.id`; span names stay `claude_code.*` with a mirroring `span.type` attribute — there is no documented `gen_ai.operation.name` or `gen_ai.tool.name` attribute, and `gen_ai.agent.*` attribute names could not be confirmed. Counters that cost you visibility by default: `OTEL_LOG_USER_PROMPTS`, `OTEL_LOG_ASSISTANT_RESPONSES`, `OTEL_LOG_TOOL_CONTENT`, `OTEL_LOG_RAW_API_BODIES`.

**Copy this:** the tool span split into permission-wait vs execution, plus `CLAUDE_CODE_PROPAGATE_TRACEPARENT` and TRACEPARENT injected into Bash/PowerShell subprocesses (and into outbound MCP HTTP unless routed via a third-party `ANTHROPIC_BASE_URL`) so your scripts join the same trace — that is exactly the attribution a multi-session factory needs. **Main weakness:** vendor-private span names plus content gates defaulting to off, so cross-vendor tooling must straddle two vocabularies.
