# Research: 2026-10-21-review-tools

research-gateway job `3df55f39-5009-45c4-aa10-17f3110907b7` · finished 2026-10-21 11:40 UTC · status `ok` · 70 citations

**Query:** Self-hosted tools (as of late 2026) for reviewing and commenting on AI coding agent outputs — Markdown plans AND standalone HTML reports — with comments that agents (Claude Code, OpenCode, Codex) can read back programmatically (files, CLI, API or MCP). Candidates to evaluate and compare: plannotator (Claude Code plan annotation), pullmark (macOS markdown margin notes), any 'agent inbox' / 'artifact review' web apps, Obsidian-based approaches, simple static file servers with annotation layers (e.g. hypothesis self-hosted). For each: format support (MD/HTML), comment storage and agent read-back, web vs native (phone access?), multi-machine/remote use, maturity, license.

---

## Bottom line

- **plannotator is the only candidate built for exactly this job** — one `plannotator` binary per session serving a browser SPA, accepting arbitrary Markdown *and* standalone HTML, returning reviewer comments to the calling agent on stdout / `--result-file` / exit codes — but it has **no HTTP or MCP endpoint for reading a *plan review's* comments back** (the CLI process *is* the channel), external annotations are session-only, the local API has **no authentication in either bind mode**, and `--tailscale` is never added by the agent hooks, so hook-driven plan reviews stay loopback-only.
- **In the self-hosted "agent inbox" field only Hypothesis `h` actually annotates arbitrary standalone HTML**; everything else is diff-, approval- or notification-shaped, and two headline "agent inbox" projects are dead (LangChain `agent-inbox` archived; HumanLayer OSS "pretty much all deprecated").
- **Self-hosting Hypothesis is workable but is a five-piece stack** (h + Postgres + Elasticsearch + RabbitMQ behind your own Caddy) with no production install guide, no single-user mode, no Helm chart — and a genuinely good agent read-back path in `GET /api/search?uri=…` with a per-user bearer key.
- **The Obsidian loop is the best fit for Markdown plans on mini + MacBook and half-works on the iPhone**, and **cannot** be the review surface for HTML reports on iOS at all.
- Concretely for your setup: **plannotator for MD plans (launched manually with `--tailscale` when you want the phone), Obsidian REST/MCP as the durable comment store for anything that must survive, Hypothesis or a small custom comment JS layer for HTML** — the one thing no tool gives you for free is HTML review comments that outlive the session.

## 1. plannotator — verified fact sheet

**Identity & license.** Canonical repo `github.com/backnotprop/plannotator`, homepage `https://plannotator.ai`, docs `docs.plannotator.ai`; the npm package `@plannotator/opencode` points back at `git+https://github.com/backnotprop/plannotator.git`. Root `package.json` reads `"name": "plannotator"`, `"version": "0.28.25"`, `"author": "backnotprop"`, `"license": "MIT OR Apache-2.0"`. **License is dual "Apache 2.0 or MIT at your option"** per README (`LICENSE-APACHE`/`LICENSE-MIT`, copyright "2025-2026 backnotprop"), npm agrees — but **GitHub's repo license field says only `Apache-2.0`**, a documented disagreement. Maturity: latest published version **0.28.25** (npm `lastPublished` 2026-10-21), no maintainer roster published — a single-owner, high-velocity project.

**Architecture.** Not a TUI, not an IDE-only plugin: "The plannotator binary runs a temporary server on your computer and opens the session in your browser", wired in through per-host hooks/plugins/skills for Claude Code, Codex, OpenCode, Copilot CLI, Gemini CLI, Pi, Amp, Droid and Kiro CLI. Plan review really is a **wrapper around Claude Code plan mode**: a `PermissionRequest` hook matched on `ExitPlanMode` runs bare `plannotator`, which reads the plan from hook stdin — so bare `plannotator` is the hook entry point, not an interactive one. On Claude Code ≥2.1.287 a plugin "mod" (on by default) lets Claude proceed without waiting and delivers your decision later as a message (`PLANNOTATOR_CLAUDE_MOD=0` disables). Sibling repos add a TUI and a VS Code webview.

**Formats.** `plannotator annotate` takes `.md/.mdx/.txt`; plain-text config/data (`.yaml/.yml/.json/.jsonc/.json5/.toml/.ini/.cfg/.conf/.properties/.csv/.tsv/.log/.xml`, `.env` deliberately refused); Mermaid/Graphviz sources; **standalone `.html/.htm`**; https URLs (Jina Reader); loopback live-app URLs; folders; multiple files; 2 MB per-file cap. Source code belongs to `review`. **Internal inconsistency:** SKILL.md says HTML is "rendered as the raw page by default; `--markdown` converts… `--render-html` is accepted for compatibility; raw rendering is already the default", while the README comments `--render-html` as "Render HTML as-is instead of converting" — treat raw rendering as the intended default and expect doc drift.

**Storage.** Not in-file, not a DB: everything lives under the data dir (`~/.plannotator`, or `PLANNOTATOR_DATA_DIR`) — config, session records, saved plans, document history, drafts, Guided Reviews; UI prefs in browser storage/cookies; feedback images as temporary local files. Version history groups plans by project + first heading + date, and annotated files by path; plan-save decision snapshots go under `<data-directory>/plans/`, browsed read-only with `plannotator archive`. Documented annotation schema: plan/doc `{source, text, type: GLOBAL_COMMENT|COMMENT|DELETION, originalText, author}` (Plannotator assigns IDs and placement — "Do not send a blockId"), review `{source, scope: line|file|general, filePath, lineStart, lineEnd, side, type: comment|suggestion|concern, text, suggestedCode, originalCode, author}`. **Durability is mixed:** "External annotations live only for the current session. Persist findings in your own tool if they must survive after the Plannotator server closes" — but annotation *drafts* are restored if you re-run the same command after a time-limit kill. Submitted feedback's durable home is the agent's own transcript.

**Agent read-back (the key column).** (1) stdout: plaintext ("The user approved." / feedback text), `--json` (one record: `decision` approved|dismissed|annotated plus feedback; review emits `{decision, message}`), `--hook` (approve emits nothing; annotations emit `{"decision":"block","reason":"…"}`). (2) `--result-file <path>` for an atomic file drop, plus `--require-approval` exit codes 0/1/2/128+n, e.g. `plannotator annotate report.md --gate --json --require-approval --result-file /tmp/decision.json`. (3) Session HTTP: `GET /api/plan`, `GET|POST /api/config`, `GET|POST|PATCH|DELETE /api/external-annotations`, SSE `GET /api/external-annotations/stream`, `POST /api/feedback`, `POST /api/exit` — all "called by the UI and return their result to the agent process that started the session". (4) MCP: `plannotator inbox mcp` (stdio, **Inbox only**) and the agent-visible `plannotator` / `plannotator_inbox` tools, which return immediately and deliver the decision later as a message. **There is no documented endpoint an agent can poll for a finished plan review's comments** — you'd have to scrape the data dir or capture stdout.

**Serving, auth, remote.** Local mode binds `127.0.0.1` on a random port; remote mode (SSH detected or `PLANNOTATOR_REMOTE=1`) binds **`0.0.0.0`** on fixed port **19432**; source confirms `getServerHostname()` returns `"0.0.0.0"` when `isRemoteSession()` else `127.0.0.1`, `DEFAULT_REMOTE_PORT = 19432`, and `PLANNOTATOR_URL_HOST` changes only the advertised URL, never the listen interface. **"The API has no authentication in either mode."** For the iPhone: `--tailscale` (v0.27.0+) keeps the server on loopback and publishes an HTTPS Tailscale **Serve** proxy with URL + QR code, removed at exit, never Funnel — but it "does not add a login screen or per-request authentication. Every permitted tailnet peer can use the session UI and its local API", and the embedded agent terminal is disabled for these sessions. **Blocker to know:** "Agent hooks do not add `--tailscale` automatically. When you need tailnet access, start a file gate directly" — so with your Caddy/Tailscale setup, hook-triggered plan reviews are phone-invisible unless you either run the file gate yourself (`plannotator annotate plan.md --gate --json --tailscale`) or widen the bind yourself.

Third-party corroboration of the remote design comes from DeepWiki's generated code analysis (SSH_TTY/SSH_CONNECTION detection, 127.0.0.1 vs 0.0.0.0, fixed 19432 for forwarding); no HN/Reddit discussion was located to cross-check maintainership claims.

## 2. The self-hosted inbox / artifact-review field

**Genuine arbitrary-HTML annotators — only two found.** ① **Hypothesis `h`** (see §3) — the only mature option. ② **MarkLayer** (`thevrus/MarkLayer`, Apache-2.0, 38★, created 2026-03-18, pushed 2026-10-16, **zero releases**) — share-link annotation of live pages with no reviewer account, open annotations to an agent via `marklayer-mcp`; "self-hosting" means deploying to your **own Cloudflare account** (Workers/D1/Durable Objects/R2), so it **cannot run as a container on the mini**. Its own guide is written by its author (bias noted).

Phone access goes through pairing at `cloud.vibekanban.com`, and a review reports bloop shut down 10 April 2026 with cloud services switched off ~30 days later (conflicting with docs that still describe it) — treat mobile as unreliable.

## 3. Hypothesis self-hosted, concretely

**Install shape.** The repo's `docker-compose.yml` defines **only backing services**, all bound to `127.0.0.1`: `postgres:15.10-alpine` (trust auth), `hypothesis/elasticsearch:elasticsearch7.10` (single-node), `rabbitmq:3.12-management-alpine`, plus an external network `dbs`. The h web app is **not** in that compose file; the README's only documented path is a development environment (`make services`, `make devdata`, pyenv/Docker/Node/Yarn). The `docs/` tree has `api`, `api-reference`, `arch`, `developing`, `publishers` and **no administration or production-deployment section**; there is a `Dockerfile` and that one compose file, **no Helm chart**. GitHub releases stop at v0.39.0 (2019-11-05, titled "Find the latest on Docker Hub") — Docker tags are the distribution channel. Realistically: Postgres + Elasticsearch + RabbitMQ + a self-built Pyramid app behind your Caddy wildcard door. One third-party template describes the same four-service shape and notes the client is loaded from `cdn.hypothes.is` by default with the admin account created on first boot.

**Embedding into pages you serve.** Per-page: `<script src="https://hypothes.is/embed.js" async></script>` "to the HTML source of each page". Self-hosting means overriding the `services` array (`apiUrl`, `authority`, `grantToken` — marked **experimental**, only the first array item is used) plus `assetRoot`/`sidebarAppUrl`/`notebookAppUrl`; `onLoginRequest`/`onLogoutRequest` let the host page own auth. Since it's per-page, you need template injection, the extension, a bookmarklet, or a proxy — and **Via won't do the proxying for you**: its README says the rewriting HTML proxy "isn't implemented yet" and "Via currently redirects to legacy Via for HTML proxying". For your mini the practical move is a **Caddy injection into served HTML** (the mechanism Hypothesis's own mobile workaround implies), not Via. URL restriction exists at *group* level (`scoped`, `scopes.uri_patterns`), not as a global host allowlist.

**Markdown.** No Markdown-aware path is documented — the annotator works on rendered DOM with `TextQuoteSelector`/`RangeSelector`/`TextPositionSelector`, so **convert MD→HTML first**, and expect re-rendering to orphan anchors.

**Storage & agent read-back.** Postgres (accounts, groups, annotations) + Elasticsearch index; no sidecar files. API: `GET /api/search` returning `{rows,total}` with `limit` 0–200 (default 20), `sort` in created|updated|group|id|user, `order`, `search_after`, `offset` ≤ 9800, and filters `uri` (alias `url`), `uri.parts`, `wildcard_uri`, `user`, `group`, `tag(s)`, `any`, `quote`, `text`, `references`; `GET /api/annotations/{id}`; `GET /api/groups/{id}/annotations` (`page[after]`, `page[size]` 1–100, `moderation_status`); `POST/PATCH/DELETE /api/annotations`; `/api/profile`, `/api/profile/groups`, `/api/groups`. Auth: **per-user bearer ApiKey** ("An API key corresponds to a single user") or an authority-scoped AuthClient (HTTP basic + `X-Forwarded-User`); tokens from `/account/developer`. Groups: `private|open|restricted`, `pre_moderated`. So an agent polls `{your-host}/api/search?uri=<page-url>` with a token — precisely the read-back you want, and the one thing none of the other candidates offer for HTML.

**Licensing.** h is **BSD-2-Clause**; `via` BSD-2-Clause; no commercial-use restriction encountered. **The client repo's license is unresolved** — GitHub reports `NOASSERTION`.

**Phone.** "Mobile browsers: None can currently run the extension" — on iPhone you must have the client embedded in the page (Caddy injection) and the sidebar rendered in-page; Via also does not work on sites requiring auth.

## 4. Obsidian vault as the comment store

**Plumbing is stronger than expected.** The plugin's published name is **"Local REST API with MCP"**, id `obsidian-local-rest-api`, repo `coddingtonbear/obsidian-local-rest-api`, **MIT**, latest release **5.5.2** (2026-10-17). Auth is a single **bearer API key**; HTTPS on **27124** (plugin-generated, name-constrained CA) or opt-in plain HTTP on **27123**. Endpoints: `/vault/{path}` (GET/PUT/PATCH/POST/DELETE), `/active/`, `/search/simple/`, `/search/` (JsonLogic), `/commands/` + `/commands/{id}/`, `/tags/`, `/open/{path}`, `/events/<emitter>/<event>/` (SSE), and **`/mcp/`** (Streamable HTTP) — it now ships its own MCP server, and the README states third-party MCP servers "are no longer necessary". Tools: `vault_read/write/append/patch/delete/move/copy`, `vault_get_document_map`, `search_simple`, `search_query`, `tag_list`, `command_list`, `command_execute`. `.obsidian` is hard-blocked (403, GHSA-66m9-r757-qvq7) *because* writing plugin config is RCE; signed URLs work **without** the key for their 300 s lifetime; wrong credentials get 429 after 10/min. **Security posture on a tailnet: keep the default 127.0.0.1 bind** — the key is whole-vault read/write/delete and `command_execute` is effectively plugin-level code execution, so the tailnet is not a sufficient boundary.

**Second MCP option.** `cyanheads/obsidian-mcp-server` **v3.7.0**, Apache-2.0, STDIO or Streamable HTTP on :3010, 14 read/write tools with `OBSIDIAN_READ_PATHS`/`OBSIDIAN_WRITE_PATHS`/`OBSIDIAN_READ_ONLY` scoping; needs Local REST API ≥4.0.0. Both options require **Obsidian running** on the mini.

**Comment conventions that are machine-parseable.** PATCH (and `vault_patch`) targets `heading`, `block` reference or `frontmatter` key with append/prepend/replace/delete/move, and `vault_get_document_map` lists a file's headings, block refs and frontmatter fields — so `^block-id` comments and frontmatter verdicts are first-class deterministic targets without rewriting whole files. `%%…%%` comments are recognised by vault tooling (cyanheads' inline-tag scanner skips code/wikilinks/HTML/math and reads `%%…%%`), though their mobile visibility is unverified.

**The three seams that break.** ① **iOS git sync is the weak link**: the community Git plugin (id `obsidian-git`, v2.42.0, MIT, Desktop+Mobile) says mobile is "very unstable… I would not recommend using this plugin on mobile" — no SSH auth, memory-limited repo size, no rebase, no submodules, may crash on clone/pull. ② **HTML doesn't render on iOS**: reading view sanitizes raw `<iframe>` and strips `<script>`; the workaround plugin (`html-embed`, MIT, v1.0.0) resolves files through `app://` in a sandboxed iframe but is **"Platforms: Desktop only"** — so serve HTML from your Caddy door and open it in Safari instead. ③ HTML reports still need their own comment layer, plus git conflicts across three working copies and a hard dependency on an always-on Obsidian.

## 5. What fits Mac mini + Caddy wildcard + Tailscale + iPhone

| | MD plans | standalone HTML | comment store | agent read-back | phone | license |

| **Obsidian + Local REST API** | ✅ native | ✗ (sanitized; desktop-only workaround) | vault files, in-file | `/vault/…`, `/search`, `/mcp/`, PATCH to block/heading/frontmatter | Obsidian iOS app, git sync unstable | MIT |
| **pullmark** (your background) | ✅ only | ✗ | HTML comments in-file | **none** (no API) | native macOS only | beta, single maintainer |

Practical shape: **plannotator replaces the plan-mode step for MD plans** (launch the file gate yourself with `--tailscale` when you want the phone, because hooks won't add it); **fold accepted comments back into the Obsidian vault** so they're durable and reachable by any agent through `/mcp/` or `/vault/{path}` (not in-file for HTML — XHTML reports get their anchors from Hypothesis or a small injected comment script + Caddy route); keep **Vibe Kanban for diffs** only if you want line-level code review; **Boop or openagent.email as the phone pager** if you want a notification rather than a pull. What no candidate gives you: HTML review comments that both survive process exit *and* come back through an MCP tool the agent already has. That gap is where a thin custom layer (Caddy-injected comment JS → JSON file → Obsidian MCP write) is likely cheaper than bending any of these.
