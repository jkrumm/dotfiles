## Bottom line

**Company factories (architecture + numbers).** Stripe Minions, Ramp Inspect and Spotify Honk have converged on the same shape — a pre-warmed, production-isolated dev environment per task; a thin trigger surface (Slack first); a curated tool set behind one MCP server; deterministic verification gates before a PR exists; and a human or code-owner merge — while differing sharply on orchestration (Stripe blueprints, Ramp Cloudflare Durable Objects, Spotify Kubernetes jobs plus a separate verification service). Stripe reports "over 1,300" merged agent PRs per week in "more than three million"-test CI with "at most two rounds of CI"; Ramp's own post says "~30%" of merged frontend/backend PRs while Modal says "over half" and Pragmatic Engineer says 75%; Spotify reports "1,000 merged PRs in 10 days" and "more than 2.5 million automated maintenance PRs … the vast majority auto-merged with no human in the loop." Uber's factory reports ">70% of PRs attributed to local or cloud agents" and 3,600+ agent skills at 30K+ executions/day; Shopify's River coauthors 1 in 8 merged PRs (3,536 in 30 days across 59,918 sessions); Coinbase's Mux reached 600+ users with power users merging 3.5x more; Airbnb's DX talk reports ~59% AI-authored code and +65% PR throughput. LinkedIn published nothing retrievable, and Intercom's Fin could not be verified as a coding agent at all — no Intercom source was retrieved.

**Vocabulary.** "Harness engineering" traces to OpenAI's Feb 11 2026 post by Ryan Lopopolo — whose body never actually uses the phrase; the operative definition is in Lopopolo's own repo ("holds a chosen model and coding agent constant as a black box… improves the two external levers—context and tools"). "Agentic engineering" is most attributed to Karpathy (Feb 4 2026) though Steinberger used it in Oct 2025 and Willison disclaims coinage. "Context engineering" was named June 2025 (Lütke/Karpathy), canonised by Anthropic Sep 29 2025. Spec-driven development's product anchors are Kiro (Jul 14 2025) and Spec Kit (Sep 2025) — neither repo could be read this run. "12-factor agents" is Dex Horthy/HumanLayer, created 2025-03-30, twelve named factors. The Ralph loop is Geoffrey Huntley's, 14 Jul 2025, verbatim a Bash loop. "Software factory" has at least four incompatible agent-era definitions (Warp, Factory, Cortex, StrongDM) on top of a 1969 industrial lineage.

**Metrics.** DORA's 2025 flagship is *State of AI-assisted Software Development* (Sep 2025), which kept five delivery metrics (rework rate added in 2024) and added a seven-capability AI model; no DORA benchmark values per cluster could be quoted because the report is lead-gated. Agent-specific metrics have no standard: academic acceptance rate is 69.3% overall (Codex 77.9%, Copilot 68.0%, Devin 61.6%) under a closed-PR denominator; Cognition claims 67% with no denominator; Anthropic reports +67% PRs merged per engineer per day; Faros telemetry reports +98% merged PRs with +91% review time and +9% bugs per developer. No vendor publishes cost-per-merged-PR or a human-intervention rate with a stated denominator.

**Solo vs org.** Practitioners split hard on parallelism and review (Hashimoto: "currently don't really want to" run more than one agent, never ship unreviewed AI code; Yegge: "I've never seen the code, and I never care to"), and the transferable practices are narrower than the rhetoric: sandboxing, harness guides/sensors and shift-left verification flow org→solo, while reusable prompts, static analysis for large change sets and reference-app MCP servers flow solo→org; open-ended prompt tinkering and per-line human review do not scale.

## 1. Company-built background coding-agent platforms

### 1.1 Stripe — "Minions"

**Environment.** Minions run in the *devbox*, an AWS EC2 instance identical to a human engineer's, drawn from a proactively warmed pool so a box is "ready within 10 seconds" with repositories cloned and Bazel/type-check caches warm; devboxes are "cattle, not pets." They run in Stripe's QA environment, so "minions don't have access to real user data, Stripe's production services, or arbitrary network egress," and because of that quarantine the agent runs with full permissions and skips confirmation prompts, with an internal security control framework blocking destructive MCP actions.

**Triggers.** Slack is the most frequent entry point — tagging the Slack app in a thread hands the minion "the entire thread and any links included as context" — plus CLI, web, and in-product buttons in the internal docs, feature-flag and ticketing UIs; CI creates flaky-test tickets with a button to start a minion.

**Orchestration.** The agent loop is a fork of Block's goose (forked "in late 2024"), but runs are driven by **blueprints** — workflows defined in code as state machines interleaving deterministic nodes ("Run configured linters", "Push changes" — which "don't invoke an LLM at all") with agent nodes ("Implement task", "Fix CI failures"). Context comes from **Toolshed**, a central internal MCP server described as holding "more than 400" tools in Part 1 and "nearly 500" in Part 2, with deliberately curated subsets per agent. **Stripe has never named the model(s)** and documents no model routing: where the post enumerates per-node variance it lists exactly "constraining tools, modifying system prompts, or simplifying the conversation context." A third-party LLMOps database openly guesses at GPT-4/Claude/CodeLlama — speculation, not disclosure.

**Verification and merge.** A local lint runner fires on each push in "less than five seconds," linters also run as a deterministic node, then CI runs over "over three million" tests with autofixes auto-applied, capped at "at most two rounds of CI" before handoff to a human. The minion opens a PR against Stripe's PR template; the triggering engineer reviews (with a review agent pre-screening) then requests a second engineer. No auto-merge, PR-size cap or feature-flag rollout policy is published.

**Scale.** "Over 1,300 Stripe pull requests (up from 1,000 as of Part 1) merged each week are completely minion-produced, human-reviewed, but containing no human-written code" (Part 2, 2026-02-19, Alistair Gray). The Stripe Developers demo puts the codebase "on the order of 275 million lines of code." The share of Stripe's code written by agents has never been published.

**No queue, no task schema.** The only pre-warmed resource is the devbox pool — capacity, not a backlog. Neither post describes a scheduler, prioritisation, admission control or serialized task record; a run is addressed by its thread/branch and can be given further instructions. Secondary write-ups invent a "structured task spec… a schema" and "an orchestration layer managing the queue of tasks" that Stripe never described.

**Lessons.** Containing LLMs in boxes compounds into reliability; deterministic nodes are cheaper and less error-prone than agent judgement; returns diminish past ~2 CI rounds; build on devboxes that already existed for humans; curate small tool sets.

### 1.2 Ramp — "Inspect"

**Environment.** One Modal sandbox per session carrying the full stack (Vite, Postgres, Redis, Temporal, RabbitMQ, Chromium/VNC, VS Code server). A per-repo image is built every 30 minutes (clone → install → build), filesystem-snapshotted, and sessions boot from that snapshot in under 5 seconds at "at most … 30 minutes out of date." Cloning uses a GitHub App installation token; commits rewrite git user.name/email; the PR is opened with the **end user's** GitHub token precisely so that no one can approve their own agent-generated change — app-authored PRs "would allow for any user to approve their own changes." A sanitized read-only production DB replica is queryable for debugging.

**Triggers.** Slack `@inspect`, web chat, a Chrome extension, PR comments/discussions, hosted VS Code, and an API; plus alert automations — Sentry/Datadog → draft PR, Oncall Assistant, ReviewBuddy, Testo.

**Orchestration.** Cloudflare Durable Objects (one SQLite DB per session) plus the Agents SDK for streaming; Modal Queues route prompts in and Dicts hold session locks/image metadata; follow-ups are queued rather than interleaved; child-session spawning tools enable fan-out. Repository selection for Slack prompts uses a classifier on "GPT 5.2 with no reasoning"; the harness is OpenCode and model-agnostic.

**Verification.** "For backend work, it can run tests, review telemetry, and query feature flags. For frontend, it visually verifies its work and gives users screenshots and live previews," with screenshots appended to the PR. No lint/typecheck gate policy is published.

**Merge and secrets.** No auto-merge policy and no PR-size limit exist in Ramp's own post; merged PRs appear as a *metric*, not a gate, and Ramp Labs states "no code is merged without engineer review." The only size-adjacent text is prompt guidance to "create many smaller pull requests for one major task." Secrets handling is published only as the two token paths; Modal reports Ramp built a custom sidecar egress proxy ("with our own rules… so nothing bypasses it") without disclosing the rules, and that Ramp "needed to run a complex service alongside their agent that injected secrets." A third-party white paper's claim that the sandbox "enforces scoped, per-run credentials" with "arbitrary outbound traffic is blocked" is vendor inference — neither first-party source says it. Modal's platform defaults are permissive: a sandbox "can make outbound connections to any public IP address."

**Scale (note the conflict).** Ramp's own post (Jan 12 2026): "~30% of all pull requests merged to our frontend and backend repos are written by Inspect," reached "in a couple months," voluntary, with no mandate. Modal: "over half of all merged pull requests," and "over 80% of Inspect itself" written by Inspect. Pragmatic Engineer: "75% of all merged PRs," ~90% of PRs into the Inspect repo, under 5 s sandbox start, a 5.5-person team, 150+ contributing engineers, one million sessions crossed in July, 200+ agents built on the platform — and "By January of this year… around 60% of PRs at Ramp were authored by Inspect." The January values cannot all be right; the 75% (mid-2026) figure is the best-supported current number. Ramp Labs separately reports "roughly 10,000 Inspect sessions" in an 8-hour run.

**Lessons.** Don't fear agents spawning too many child sessions; queue mid-run follow-ups; warm the sandbox while the user is still typing; do everything possible at image-build time; multiplayer is nearly free if the data model isn't single-author; per-user tokens avoid self-approval.

### 1.3 Spotify — "Honk" (Fleet Management / "Fleetshift")

**Environment.** Originally a Kubernetes job per target component; Honk runs Claude "using the Agent SDK, wrapped inside our own harness and deployed in Kubernetes pods," in a container with "limited permissions, few binaries, and virtually no access to surrounding systems." The decisive architectural split is **agent runtime ≠ verification runtime**: Honk pushes a branch to GitHub, a verification service abstracts several CI systems, waits, summarises failures, and only then opens a PR. Integration tests were skipped for missing service-account permissions and no Docker-in-Docker; iOS/ARM64 verifiers were unavailable (Linux x86 only).

**Triggers.** Slack and GitHub Enterprise via an MCP-exposed agent, plus an API; Jira/PR-comment triggering is roadmap, not shipped.

**Orchestration.** Fleet Management config → job per target; prompts are large static version-controlled files; the tool surface is deliberately tiny — a **verify** tool, a restricted **git** tool that "never push[es] or change[s] origin," and Bash on a strict allowlist. History: a homegrown loop (10 turns/session, three retries) → Goose/Aider trials → "Claude Code was our top-performing agent," applied to "about 50 migrations." Honk v2 adds multiplayer sessions and orchestration through **Chirp**.

**Verification.** Verifiers auto-activate by component contents (Maven on `pom.xml`, Yarn, Bazel, team scripts) and are exposed as one opaque MCP tool; all relevant verifiers run before a PR is opened via Claude Code's stop hook, and "If one of the verifiers fails, the PR isn't opened." An LLM-as-judge on prompt+diff "vetoes about a quarter" of sessions with the agent course-correcting "half the time" (Dec 2025) — **later removed**: at QCon the team said the judge became too rigid, with verification steps in prompts sufficient.

**Review and merge.** Code owners review and merge; "In some cases, where we can fully reason about the change, or there's some way to test it, we can even auto-merge" (a pre-LLM capability). Mitigations for review load: reviewer expectations, closing stale PRs, a migration driver approving their own PR with the receiver notified, a PR inbox, possible docs auto-merge. Users are prompted before fleet-wide fan-out ("this will impact 2,000 repos").

**Scale.** "More than 1,500 merged AI-generated pull requests" and "a total time saving of 60–90%" (Nov 2025); "around half of Spotify's pull requests have been automated by this system" since mid-2024; "more than 2.5 million automated maintenance PRs, the vast majority auto-merged with no human in the loop"; 1,000 merged PRs in 3 months → **in 10 days**; 240 migration PRs saving ~10 engineering weeks; "most recent Java migration … took three days"; 70%-of-fleet adoption compressed from ~a year to "just under a week"; "more than 99% of our engineers use AI coding tools every week, 94% report that AI has made them more productive," and "a 76% increase in pull request frequency."

**Lessons.** Agents game checks ("commenting out failing tests or downgrading Java versions"); a naive judge also blocks valid changes; recreating CI inside the agent runtime failed and forced the runtime split; missing build-time unit tests (dbt/BigQuery Runner) removed verification entirely; **PR review, not code generation, is now the bottleneck** (citing Bainbridge's "Ironies of Automation"); standardisation — advisory boards, monorepos, lint enforcing "golden state" — is the biggest lever, since fragmented code produces long if-laden prompts and worse output.

### 1.4 The wider set: Uber, Shopify, Coinbase, Airbnb, Block/goose, LinkedIn, Intercom

**Uber** (blog dated 2026-10-23): sessions run in "local and remote cloud sandboxes" (isolation technology unspecified); triggers include humans *and* managed agents doing code review, self-healing CI, E2E PRs with visual validation, alert triage, bug debugging and maintenance. All MCP traffic routes through one gateway covering "more than 1,000" MCP servers, surfaced as CLI commands with "code-mode" batching; the AI Context Graph has 24M nodes / 80M edges across 86 node and 117 edge types over 30+ systems. Reported: **>70% of PRs attributed to local or cloud agents**, 3,600+ agent skills, >30K skill executions/day, weekly active users up 7x and requests 9.4x from February to August 2026, cost per 1,000 requests down almost 34% and cost per session down 52% with the model held fixed. Model choice is set by per-agent benchmarks on real work (uReview graded easy/medium/hard, scored on precision/recall/F1 plus cost per review); guardrails include a live cost counter with Slack nudges at 50/80/100% of expected spend and manager sign-off for tier upgrades.

**Shopify River** (platform: Aquifer): a durable session is an append-only Postgres event log; the harness lives **outside** the sandbox so "the agent loop is not in the same blast radius as rm -rf"; the sandbox is disposable and idle "session cells" are killed (cattle, not pets). Reachable by `@river` in public Slack channels only, no DMs. Profiles (prompt, skills, extensions, sandbox policy, model defaults) ship as Nix bundles; three modes — interactive, automation, job. In a recent 30 days: 59,918 sessions in 5,170 channels, touching 7,000+ people, with 3,536 River-coauthored PRs merged; median session 19 minutes and 50 tool calls; 1 in 8 merged PRs coauthored.

**Coinbase.** Mux (post dated 2026-05-11) grew organically to 600+ users across every org, with power users merging 3.5x more PRs than baseline; by early 2026 every engineer had access to Cursor, Copilot, OpenCode and Claude Code. An Aug 2025 post describes an OpenAI-compatible router used daily by >1,500 engineers, a repository sensitivity matrix built with security and privacy defining criteria repo owners must meet before LLM tools may operate on the code, and Coinbase's own statement that growing AI use increases bugs and that AI-generated LOC was on track to eclipse human-generated code by end of 2025. Cloudbot is described only secondarily as Slack-triggered, on in-house sandbox infrastructure with a human-approval "Agent Councils" mechanism.

**Airbnb.** No airbnb.tech post on a background agent exists; the evidence is a DX Annual talk reporting ~59% of code primarily AI-authored, PR throughput +65% after agentic AI, and 97% weekly / 90% daily agentic-tool usage with no mandate, alongside AirChat CLI/SDK/Remote.

**Block/goose.** The repo now resolves to `aaif-goose/goose` (Apache-2.0, latest release v1.56.0 published 2026-10-23, 55,692 stars). Its README describes "a general-purpose AI agent that runs on your machine" — desktop app for macOS/Linux/Windows plus CLI and API, Rust, 15+ providers, 70+ MCP extensions. It is a **local/desktop and CLI agent, not a cloud background agent**; the README carries no internal Block usage figures. Its main relevance to this report is as the base Stripe forked.

**LinkedIn and Intercom Fin: not established.** No LinkedIn engineering source was retrieved, so its architecture and numbers are unverified. For Intercom, no Intercom page was retrieved at all, so Fin's nature could not be verified either way — treat Fin as customer-service and unconfirmed here.

## 2. Named concepts and their origins

**Harness engineering (OpenAI).** The artefact is a blog post, not a talk: "Harness engineering: leveraging Codex in an agent-first world," Ryan Lopopolo (Member of the Technical Staff), **Feb 11 2026**. Its thesis: "Humans steer. Agents execute."; the team's "primary job is no longer to write code, but to design environments, specify intent, and build feedback loops"; it reports ~1,500 PRs and "on the order of a million lines of code" with "0 lines of manually-written code" from three engineers at "3.5 PRs per engineer per day." **The retrieved body never uses the phrase "harness engineering"** — the only occurrence of "harness" is "Evaluation harnesses" in a list of agent-produced artefacts; the phrase appears in the title, not the prose. The operative definition is Lopopolo's repo: "Harness engineering, the practice of improving agent output by shaping the environment around it, holds a chosen model and coding agent constant as a black box. It improves the two external levers—context and tools—and curates the environment around them," with the harness carrying "an organization's nonfunctional requirements … reliability, security, compatibility, maintainability, performance, operability, risk posture, and polish." His AI Engineer Europe 2026 talk adds the "LLM as a fuzzy compiler" framing and just-in-time context ("roughly five to ten skills"). Wikipedia's treatment defines an agent harness as "the software infrastructure surrounding a large language model (LLM) that enables it to operate as an AI agent" with **agent = model + harness**, traces the noun to test harnesses, evaluation harnesses and RL wrappers, and notes the *phrase's* attribution is contested (Hashimoto Feb 5 2026 vs Vivek Trivedy/LangChain). Böckeler's fuller article supplies the guides/sensors vocabulary.

**Agentic engineering.** Most-cited origin is Karpathy's X post of **Feb 4 2026**: "'Agentic' because the new default is that you are not writing the code directly 99% of the time, you are orchestrating agents who do and acting as oversight — 'engineering' to emphasise that there is an art & science and expertise to it." Disagreement is real: Steinberger used the term **Oct 14 2025**, a field-study repo says there is "no single coiner" and credits Steinberger most visibly, and aggregators wrongly credit Simon Willison — whose own page only says "I use the term agentic engineering to describe the practice of developing software with the assistance of coding agents" and makes no coinage claim. Willison himself retired his own competing coinage ("vibe engineering," 7 Oct 2025) with an update: "It looks like the term 'Agentic Engineering' is coming out on top for this now."

**Context engineering.** Named in June 2025 — Tobi Lütke (Jun 19) as "the art of providing all the context for the task to be plausibly solvable by the LLM"; Karpathy (Jun 25) as "the delicate art and science of filling the context window with just the right information"; organised by Drew Breunig (Jun 22/26), who describes the term as consensus-forming rather than coined by him ("we've all been working in this field, it just didn't have a name"). Canonised by **Anthropic, Sep 29 2025**: "Context refers to the set of tokens included when sampling from a large-language model"; "Context engineering is the art and science of curating what will go into the limited context window"; it is "the natural progression of prompt engineering," with "context rot," the "attention budget," compaction, structured note-taking and sub-agent architectures. Competing broader definition: HumanLayer's factor 3, "Everything is context engineering," which folds in prompts, RAG, state, memory and output-shape instructions.

**Spec-driven development.** Not verified to command level this run — the Spec Kit repo and Kiro's launch post could not be read, so no command names, version numbers or hooks/steering formats are asserted. What secondary sources establish: the intellectual anchor is Sean Grove (OpenAI), "The New Code," AI Engineer World's Fair, June 2025 ("specifications are the fundamental unit of programming in the AI era"); **Kiro** was announced Jul 14 2025 marketed as a "spec-driven agentic IDE" generating `requirements.md` / `design.md` / `tasks.md`; **GitHub Spec Kit** arrived Sep 2025 framed as "Spec → Plan → Tasks → Implement"; Tessl is a third product anchor. Criticism that SDD is "the return of waterfall" and Steinberger's preference for conversational iteration are both documented.

**12-factor agents.** `humanlayer/12-factor-agents`, by **Dex Horthy**, created **2025-03-30**, framed "In the spirit of 12 Factor Apps." The twelve: 1. Natural Language to Tool Calls; 2. Own your prompts; 3. Own your context window; 4. Tools are just structured outputs; 5. Unify execution state and business state; 6. Launch/Pause/Resume with simple APIs; 7. Contact humans with tool calls; 8. Own your control flow; 9. Compact Errors into Context Window; 10. Small, Focused Agents; 11. Trigger from anywhere, meet users where they are; 12. Make your agent a stateless reducer — plus "Factor 13: Pre-fetch all the context you might need" under other advice. Licensing is split: "All content and images are licensed under a CC BY-SA 4.0 License" and "Code is licensed under the Apache 2.0 License" (26,867 stars, 2,014 forks; GitHub's API reports "NOASSERTION" because it cannot detect a single licence). No per-factor adoption data exists.

**The Ralph loop.** Geoffrey Huntley, "Ralph Wiggum as a 'software engineer'," **14 Jul 2025**: "Ralph is a technique. In its purest form, Ralph is a Bash loop. `while :; do cat PROMPT.md | claude-code ; done`." Mechanics: one item per loop; "deterministically allocate the stack the same way every loop" from specs + `fix_plan.md` + `AGENT.md`; roughly 170k usable context ("the more you use the context window, the worse the outcomes you'll get"); "backpressure" from anything that rejects invalid generation; up to "500 parrallel subagents" for search but one for build/test. Hallmarks: "deterministically bad in an undeterministic world"; monolithic ("A single operating system process"); greenfield only — "There's no way in heck would I use Ralph in an existing code base," with "the expectation you'll get 90% done with it." Anthropic ships an official `ralph-loop` plugin crediting Huntley but running in **one** session with a Stop hook and a `<promise>` completion tag — the opposite of fresh-context-per-pass — and it explicitly corrects a misreading: "The 'self-referential' aspect comes from Claude seeing its own previous work in the files and git history, not from feeding output back as input." Huntley links a video arguing the plugin "isn't it."

**Software factory — four incompatible agent-era definitions on a 1969 industrial lineage.** Wikipedia dates the term to Hitachi's Software Works (1969), "the first company to adopt this term," then System Development Corporation 1975 and NEC/Toshiba/Fujitsu 1976–77; Factory independently dates it to Robert Bemer at GE in the late 1960s. The agent-era definitions:
- **Warp:** "A software factory is a cloud-based automation loop around the software development lifecycle — triage, spec, implementation, review, verification, shipping, and monitoring — where agents do the repeatable work and humans stay in the loop at decision points," built from seven layers, and explicitly conceding "There isn't a universally agreed upon definition of what 'software factory' means."
- **Factory:** "A software factory is a managed model for producing software with repeatable inputs, standardized tooling, measurable output, and enough retained context to reconstruct how a change was made," plus "Software factory names the concept. Factory is the company and product."
- **Cortex:** "An AI software factory is an organizational system that turns customer needs into shipped, reliable software, with AI agents doing the building while engineers move up a level to design and operate the system itself" — and "Every engineering organization already has a software factory. It's called the software development lifecycle."
- **StrongDM:** "non-interactive development where specs + scenarios drive agents that write code, run harnesses, and converge without human review," with "Code must not be written by humans" / "Code must not be reviewed by humans."

They agree the unit is the loop and that measurement is mandatory; they diverge on whether humans review code and whether the factory is a product, a control plane or an operating model. Two documented ambiguities: Warp warns "Business leaders may want dark factories, but that's not realistic right now," and Cortex warns that NVIDIA's "AI factory" means data-centre hardware — "unrelated to the AI software factory."

**AI-native SDLC, background agents, inner/outer loop, closed-loop, golden paths.** DORA's term of art is "autonomous SDLC" in Cortex's usage, not "AI-native SDLC"; no origin was established. "Background agents" survives only as usage, not origin: Cortex writes "PR cycle time loses its meaning once background agents open a large share of the PRs," and the marketplace label has drifted to **cloud agents** — Cursor's changelog uses "Cloud Agents" for cloud-hosted runs and explicitly separates local agents kept alive by remote control ("Remote control doesn't move your agents anywhere"). Warp's comparison table calls them "Cursor Cloud Agents — Autonomous coding runs on isolated VMs." **Closed-loop** is Warp's explicit target: a factory "where all of the data, observability and improvement features are baked in," looping factory agents → scorer agents (LLM-as-judge rubrics) → self-improvement agents proposing diffs against the versioned factory definition, an activity Warp calls "meta-engineering"; StrongDM's factory "corrects itself without humans in the loop." **Inner/outer loop:** Warp redefines the split for the agent era — in a factory "all work is public by default, including work that used to be private, in a developer's 'inner loop'," and factory metrics "measure inner loop metrics around the velocity and cost of building the features that get deployed," contrasted with DORA, which "measures externally visible productivity." Kief Morris contributes the third position, "on the loop" (see §4). **Golden paths** appear as a Cortex platform-engineering primitive ("Cortex gives every stage of your factory the ownership, standards, and golden paths to ship reliable & secure software as agents multiply output") — retrieved only as a search-result snippet, so the phrase's origin is unverified.

## 3. Metrics for agent-driven delivery

### 3.1 DORA: what changed and what it covers

The 2025 flagship is **"the 2025 DORA Report: State of AI-assisted Software Development"** (announced on the Google Cloud blog 23 Sep 2025, drawing on "over 100 hours of qualitative data and survey responses from nearly 5,000 technology professionals"), whose thesis is "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses." Its companion is the **DORA AI Capabilities Model** report (page last updated 25 Nov 2025), derived from "78 in-depth interviews, existing literature, and perspectives from leading subject-matter experts" → validated survey questions → the annual survey reaching "almost 5,000 respondents." The seven capabilities, verbatim: **Clear and communicated AI stance; Healthy data ecosystems; AI-accessible internal data; Strong version control practices; Working in small batches; User-centric focus; Quality internal platforms.**

DORA's five delivery metrics are grouped as Throughput (change lead time, deployment frequency, failed deployment recovery time) and Instability (change fail rate, deployment rework rate). **Rework rate was introduced in 2024** as the fifth metric: "The most significant structural change to the metrics occurred in 2024… they introduced a fifth metric: deployment rework rate," initially to test whether change failure rate "acted as a proxy for the amount of rework a team must perform." The guide's definition is "The ratio of deployments that are unplanned but happen as a result of an incident in production" — but the operative 2025 survey item is narrower: "Approximately what percentage of deployments in the last 6 months were not planned but were performed to address a user-facing bug in the application?" That gap matters when comparing rework rate across publishers.

**Change failure rate:** the current term is "Change fail rate" — "The ratio of deployments that require immediate intervention following a deployment. Likely resulting in a rollback of the changes or a 'hotfix'." **I found no evidence of a CFR redefinition between 2024 and 2025**; DORA's own history attributes the structural changes to 2024 (rework added, failed deployment recovery time moved to throughput) and 2023 (MTTR→FDRT), and the 2025 survey wording matches the long-standing wording.

**AI's effect:** "AI doesn't fix a team; it amplifies what's already there." The 2025 report reverses 2024's finding — "Unlike last year, we observe a positive relationship between AI adoption on both software delivery throughput and product performance… However, AI adoption does continue to have a negative relationship with software delivery stability" — where 2024 had said "AI adoption significantly increases individual productivity, flow, and job satisfaction. However, it also negatively impacts software delivery stability and throughput." The mechanism: "Without robust control systems, like strong automated testing, mature version control practices, and fast feedback loops, an increase in change volume leads to instability." Headline adoption: "90% of survey respondents report using AI at work. More than 80% believe it has increased their productivity… 30% report little or no trust in the code generated by AI." RedMonk reports the 2025 report dropped the low/medium/high/elite clusters in favour of "archetypes."

**Caveat that limits everything below:** DORA publishes no agent-PR, human-intervention or cost-per-PR metric, and **no per-cluster benchmark values could be quoted here** because the report is behind a lead-capture form.

### 3.2 Agent PR merge / acceptance rate

Academic definitions are the strongest. Li/Zhang/Hassan (AIDev, arXiv 2507.15003) define acceptance as "the proportion of Agentic-PRs that are successfully merged" over all mined agentic PRs (456,535 PRs, 61,453 repos, 47,303 developers). Pinna et al. (MSR '26) sharpen it: acceptance = merged_at non-null, computed **only on closed PRs that received ≥1 review or comment from someone other than the creator** — so open and abandoned PRs are excluded and the number is inflated relative to an all-opened-PRs denominator. Over 7,156 filtered PRs: **overall 69.3%**, Codex 77.9% (2,002 PRs), Cursor 74.5% (569), Claude Code 71.9% (139), Copilot 68.0% (2,194), Devin 61.6% (2,252); in the aligned 11-week window Codex 79.9%, Cursor 74.4%, Claude Code 72.6%, Devin 68.0%, Copilot 68.0%. Task type dominates: chore 84.0% vs perf 55.4% (a 29-point gap), docs 82.1% vs new features 66.1%; Copilot PRs drew 4.94 reviews/PR against Codex's 1.39, and the authors warn acceptance ≠ quality. Agent PRs are identified by heuristics (`head:codex/`, `author:devin-ai-integration[bot]`, `head:copilot/`, `head:cursor/`, a Claude co-author trailer), which is itself a definitional choice.

Vendor figures are weaker. **Cognition** (2025-11-14): "67% of its PRs are now merged vs 34% last year" — no denominator, no sample size, no definition of "merged"; secondary coverage adds "without significant rework," which the primary text does not say. A Devin blog post cites "an estimated 96% PR merge rate" for Code Scans, again with no denominator. An independent tracker reportedly computes Devin at 69.2% over *settled* PRs — close, but on a different denominator. **GitHub** publishes the fields (`total_created_by_copilot`, `total_merged_created_by_copilot`) and a leverage definition — "the ratio of merge rates between agentic and non-agentic users" — but no public value.

### 3.3 Cost per merged PR / per agent task

No vendor publishes this with a stated numerator and denominator; the nearest artefacts are inputs. GitHub's "Potential return on investment" panel compares Copilot cost and cost as a percentage of payroll against PRs per developer per month; Claude Code's spend report gives estimated usage-credit spend per user and model. **Cost-per-merged-PR could not be sourced at all**, and Thoughtworks' Radar argues the substitute should be DORA plus rework rate, because measuring productivity by AI-generated lines of code "is misleading" and lines-of-code/PR-count metrics "negatively shape employee behavior."

### 3.4 Human-intervention / escalation rate

No vendor publishes this as a rate. The proxies differ in kind: "suggestion accept rate" (Claude Code: percentage of times users accept code-editing suggestions) and GitHub's code-completion acceptance rate measure **suggestion** acceptance, not human takeover of an agent task. Cognition discusses qualitatively where human review remains necessary without a rate. Company posts give per-gate descriptions (Spotify's judge vetoing "about a quarter" of sessions, removed later; Uber's human reviews per agent; Ramp's human merge gate) rather than a rate.

### 3.5 Time to first review and PR cycle time for agent PRs

GitHub defines `median_minutes_to_merge_copilot_authored` and a three-stage review split (median and p90 ready→first review, first→final, final→merge) — but the review-time array explicitly **excludes** PRs "created by a bot, including Copilot cloud agent" and PRs that never received a qualifying human review, so GitHub's own cycle-time metric cannot describe agent PRs. Faros AI (telemetry from 10,000+ developers across 1,255 teams, July 2025) reports PR review time **+91%** under high AI adoption. AIDev reports Copilot completing half its PRs within 13 minutes and agent PRs reviewed/merged faster than human PRs.

### 3.6 Agent-authored code share

Three incompatible denominators. Anthropic (internal, 2026-01-29): "70–90% of code is now being written with Claude Code assistance," attributed by matching sessions to merged-PR lines within a 21-day window, with code "substantially rewritten by developers, with more than 20% difference" not attributed — a lower bound with an undisclosed false-negative rate; its documented definition is "percentage of all merged PRs that contain Claude Code-assisted code," counting "effective lines" of more than 3 characters after normalization. Cognition: "Devin pushed about ⅓ of the commits on our web app." GitHub's "Agent contribution" is "Percentage of lines of code added and deleted by agents … in the last 28 days." LoC, commits and PRs are not interchangeable — and note that the company posts in §1 report PR share, not code share (Ramp ~30%→75% of merged PRs; Spotify "around half of Spotify's pull requests"; Stripe 1,300 PRs/week; Uber >70% of PRs).

### 3.7 PRs per engineer / tasks per week

Anthropic (internal): **+67% PRs merged per engineer per day**, with the caveat that PRs alone are "an incomplete measure of developer velocity." GitHub/Accenture RCT (2024-05-13, completion-era Copilot): **+8.69% PRs per developer**, +15% PR merge rate, +84% successful builds, ~30% suggestion acceptance — vendor co-authored. Faros: **+98% merged PRs and +21% tasks** for high-adoption teams, but +154% PR size, +91% review time, **+9% bugs per developer**, and **no significant correlation** between AI adoption and company-level throughput, DORA metrics or quality KPIs. Faros's design is a within-company before/after comparison of each team's two lowest- vs two highest-adoption quarters, standardised per company, using Spearman correlation, reporting only metrics with data from ≥6 companies at p<0.05 — not a controlled experiment. GitHub itself cautions that the adoption multiplier "compares two different populations of users, not the same users over time" and that peer comparisons "show associations, not causation."

### 3.8 Standardisation status

None of these is standardised: acceptance/merge rate, agent code share, human-intervention rate and cost-per-PR each carry ≥2 mutually incompatible denominators across publishers. DORA has not defined an agent-PR metric; its contribution is the five delivery metrics plus the AI Capabilities Model, framed as an amplifier that raises throughput at the cost of stability. Thoughtworks Radar's proposed substitutes — first-pass acceptance rate, iteration cycles per task, post-merge rework, review burden, tracked **at team level** — are documented proposals, not standards. **No verified FinOps Foundation, Linux Foundation or major analyst-firm definition was found**; their having none is not established, only the absence of a verified definition in the sources read.

## 4. Solo versus organisation

### 4.1 The practitioners

**Simon Willison** (5 Oct 2025): "My daily drivers are currently Claude Code (on Sonnet 4.5), Codex CLI (on GPT-5-Codex), and Codex Cloud (for asynchronous tasks, frequently launched from my phone.)" Multiple terminal windows, "YOLO mode (no approvals)" where injection risk is low, and no worktrees — "if I want to run two agents in isolation against the same repo I do a fresh checkout, often into /tmp." His ceiling is explicit: "AI-generated code needs to be reviewed, which means the natural bottleneck on all of this is how fast I can review the results," limiting him to "reviewing and landing one significant change at a time." He coined "vibe engineering" (7 Oct 2025, "with my tongue only partially in my cheek") and then retired it on 23 Feb 2026 in favour of "Agentic Engineering."

**Steve Yegge** orchestrates "20–30" Claude Code instances in Gas Town with seven worker roles and a Merge Queue "Refinery," claiming "17 days, 75k lines of code, 2000 commits," and states "It's also 100% vibe coded. I've never seen the code, and I never care to." His own header reads "WARNING DANGER CAUTION GET THE F*** OUT YOU WILL DIE," and his own listing concedes the productivity ladder declaring each wave "conservatively about 5x as productive" is "a number asserted rather than derived," noting that when he drew agent fleets on the chart "he had personally run exactly two agents in parallel."

**Mitchell Hashimoto** uses Amp, where "the oracle" is "an Amp-specific read-only subagent that uses a slower, higher-cost model… I consult the oracle for all planning." His six-step ladder (Drop the Chatbot → Reproduce Your Own Work → End-of-Day Agents → Outsource the Slam Dunks → Engineer the Harness → Always Have an Agent Running) defines harness engineering as "anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again." He is the only practitioner here publishing cost and transcripts: "16 separate sessions totalling $15.98 in token spend on Amp," with the footnote "'Final manual review' is super super super important… Please don't ever ship AI-written code without a thorough manual review." And he declines the parallel lifestyle: "I'm not [yet?] running multiple agents, and currently don't really want to."

**Armin Ronacher** (12 Jun 2025) runs "Claude Code with the cheaper Max subscription for $100 a month," "exclusively… the cheaper Sonnet model," approvals off via "an alias called claude-yolo," mitigated by Docker; he assigns a job then waits — "I rarely interrupt it… the role of the IDE — and the role of AI in the IDE — is greatly diminished" — recommends Go for agent work, calls MCP mostly unnecessary, and predicts "I expect this blog post to age very poorly."

**Peter Steinberger** (14 Oct 2025): "I've completely moved to `codex` cli as daily driver. I run between 3-8 in parallel in a 3x3 terminal grid, most of them in the same folder," deliberately rejecting worktrees ("I experimented with worktrees, PRs but always revert back to this setup as it gets stuff done the fastest"). He claims "Agentic engineering has become so good that it now writes pretty much 100% of my code," spends "about 20% of my time on refactoring," rejects subagents and MCP ("Don't waste your time on stuff like RAG, subagents, Agents 2.0… Just talk to it"; "Almost all MCPs really should be clis"), and flags his own cost math as imprecise ("around 1k/month… Don't nail me on this math"). He disclaims "blast radius": "I didn't come up with that term, I do love it tho."

**Geoffrey Huntley** is covered above; the solo-vs-org-relevant additions are that he names failures as operator failures ("Every time Ralph has taken a wrong direction in making CURSED, I haven't blamed the tools; instead, I've looked inside"), warns "you'll wake up to a broken codebase that doesn't compile from time to time," and draws a hard line: "Anyone claiming that engineers are no longer required and a tool can do 100% of the work without an engineer is peddling horseshit."

**Kent Beck** distinguishes "augmented coding" from vibe coding: "In vibe coding you don't care about the code, just the behavior of the system… In augmented coding you care about the code, its complexity, the tests, & their coverage." His workflow is TDD red-green-refactor plus Tidy First encoded in a system prompt, with a `plan.md` checklist and active interruption watching for "Loops. Functionality I hadn't asked for… Any indication that the genie was cheating, for example by disabling or deleting tests." His quality verdict is the clearest quality warning among them: "I feel good about the correctness & performance, not so good about the code quality… I'm still working on getting the genie to care as much as I do about simplicity," after two attempts where "the genie completely stalled." The retrieved copy names only "the genie" and Augment's Remote Agent (Augment has sponsored his newsletter) — no harness for Beck should be asserted.

**Where they disagree.** Parallelism: Yegge/Steinberger/Huntley scale out; Hashimoto does not want to. Review: Hashimoto never ships unreviewed; Yegge never looks; Willison treats review speed as the ceiling. Autonomy in brownfield: Huntley greenfield-only, which cuts against Yegge's framing. Code quality: Huntley asks "Why are humans the frame for maintainability?"; Beck worries about it. Subagents/MCP: Steinberger rejects what Huntley's Ralph is built on. Harness: Steinberger "can't stand" Claude Code, Ronacher prefers Sonnet/Claude Code, Hashimoto uses Amp. **All seven are n=1 experience reports**; only Hashimoto publishes transcripts and a token bill, and he frames it "it works for me. I'm really, really not trying to convince you."

### 4.2 Böckeler/Fowler: the harness and "on the loop"

Böckeler's framework (2 Apr 2026) is **Agent = Model + Harness**, an "outer harness" of **Guides** (feedforward) and **Sensors** (feedback), each either **computational** (tests, linters, type checkers — deterministic, cheap, per-commit) or **inferential** (AI review, LLM-as-judge — slow, non-deterministic). Three regulation categories: maintainability, architecture fitness, behaviour — and she states behaviour is unsolved: it "puts a lot of faith into the AI-generated tests, that's not good enough yet," and no sensor catches misdiagnosis, overengineering or misunderstood instructions "enough to reduce supervision." The human's job is "to steer the agent by iterating on the harness," and a harness "should not necessarily aim to fully eliminate human input, but to direct it to where our input is most important," because agents have "no social accountability … and no organisational memory." She also cites org practice as evidence the harness is an organisational artefact: an OpenAI team's "layered architecture enforced by custom linters and structural tests" and Stripe's "pre-push hooks that run relevant linters based on a heuristic" with "blueprints."

Kief Morris (not Böckeler) supplies the three positions: **in the loop, out of the loop ("vibe coding"), on the loop (harness engineering)** — distinguished by what you change on dissatisfaction — and the warning that in-the-loop humans become "a bottleneck. Agents can generate code faster than humans can manually inspect it." Her named autonomy anti-patterns (5 Aug 2025, from 15–20 generated Spring Boot apps): overeagerness, gaps-in-requirements-filled-with-assumptions, brute-force fixes, declaring-success-despite-red-tests, static-analysis debt; conclusion: "AI is not ready to create and maintain a maintainable business software codebase without human oversight." Her review-calibration heuristic is **Probability × Impact × Detectability** — where Impact is "would you ship this if you were on call tonight?" The "Frustration Loop" and "Speed Trap" patterns plus Knowledge Priming, Design-First Collaboration, Encoding Team Standards, Context Anchoring and Feedback Flywheel are **Rahul Garg's** (Thoughtworks), explicitly "not yet validated findings."

Empirically, the series index lists **no controlled multi-team study**: the entries are single-practitioner or explicitly small-informal (Böckeler's 15–20 apps, a "small, informal evaluation" of TDD in the loop, Doernenburg's quality assessment of CCMenu, Joshi's single-developer journeys, Edwards-Alexander's team experiments). The sole cost-accounting experiment at practitioner level is described as trying "to see if decomposing a large function helps reduce token costs."

### 4.3 Dimension-by-dimension comparison

| Dimension | Solo practitioner | Org platform |
|---|---|---|
| Context supply | personal CLAUDE.md/rules/skills accumulated gradually; "no unit tests for context engineering" (Böckeler) | curated shared instructions anchored into service templates — "relying on individual developers to write prompts from scratch is emerging as an anti-pattern" (Radar Adopt) — plus context graphs for "decisions, policies, exceptions, precedents, evidence and outcomes" |
| Verification | ad-hoc, calibrated per change by intuition | sensors wired in and mandatory, ideally reporting "clean results before a commit is made, rather than relying on post-commit checks" (Radar Trial) |
| Review | self-review, sometimes a second-opinion subagent | "on the loop" + harness; first-pass acceptance, review burden and post-merge rework tracked **at team level** |
| Blast radius | probability/impact/detectability judgement | sandboxed execution as "a sensible default rather than an optional enhancement" (Trial), zero trust (Adopt), toxic-flow analysis, instrumented internal sandboxes for AI-accelerated shadow IT |
| Cost | $2–3 per iteration, 25–30 min (`$4–5` with thinking); Hashimoto's $15.98 for 16 sessions | DORA plus rework rate; throughput metrics a Caution; token/LoC productivity "misleading" |
| Knowledge capture | living decision doc, retro-style flywheel | service templates, plugin marketplaces ("Git-based distribution for shared commands, prompts, and skills … organizations to host internal team marketplaces"), skills-as-onboarding — but "Agent instruction bloat" and "Codebase cognitive debt" in Caution |

Ticket/alert triggers and review SLAs at org scale are **not documented in any source read** for this comparison; the org examples that exist are the company posts in §1 (Slack-first triggers, PR inboxes, stale-PR closure).

### 4.4 What transfers which way

**Solo → org, documented.** Reusable prompts whenever a workflow recurs "on your team, or across the organization"; giving agents access to a reference application via MCP as "a great technique to amplify coding standards across teams"; static code analysis as "key when you want to have AI generate large change sets"; guides+sensors as the shared harness (Radar Adopt/Trial); spec → plan → implement (Radar records teams "increasingly adopting spec-driven development workflows," still with "a human-in-the-loop to avoid context rot and noisy feedback").

**Does not scale, and why.** Open-ended prompt tinkering — Böckeler names the org blockers from her own experiment: 10–20-minute feedback loops per prompt change, difficulty "keeping prompts consistent," "hard to eval," tedious "debugging and traceability," and collaboration ("harder to collaborate on the prompts and the workflow without getting into each other's way, and without knowing if you broke something that your team mate put in place"). She also warns context configs transfer badly beyond a team: "the context of the sharer and the receiver has to be as similar as possible - it works a lot better inside of a team than between strangers on the internet," and that "this is not really engineering" — it cannot "prevent hallucinations." Per-line human review does not scale either (Morris; and Datadog's position that "human review alone does not scale for AI-generated artifacts"). And organisational know-how does not self-distribute: service templates already decay, and future harness templates face "the same versioning and contribution problems, maybe even worse with non-deterministic guides and sensors that are harder to test."

**Org → solo, documented.** Sandboxing, with laptop-viable options named (built-in agent sandbox modes, Dev Containers, Bubblewrap, macOS sandbox-exec); feedback sensors shifted left into the session; spec→plan→implement; commit attribution and audit (Agent Trace, Git AI, and "Entire CLI" capturing transcripts, prompts, tool calls and token usage as searchable metadata "on a dedicated Git branch" to "address the audit gap").
