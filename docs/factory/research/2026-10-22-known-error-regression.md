# Research: 2026-10-22-known-error-regression

Job `19fe9e52-82d1-4200-a3a6-1ccc90a23d3b` · depth deep · status ok

**Query:** Known-error database (KEDB) and regression detection in incident management, 2026 practice: how ITIL known-error records, Sentry's "regressed" issue state (resolved-in-release then reappearing), PagerDuty "Past Incidents"/"Related Incidents", incident.io/Rootly similar-incident suggestions, Opsgenie, and AIOps tools store fix recipes and match a new alert or incident against past ones. Concretely: what keys they match on (fingerprint, service, error signature, embeddings), how a fix is linked (commit, release, runbook), how a regression is defined and detected (fix version vs reappearance time window), how reuse of a past fix is verified, and published precision/false-positive figures. Also open-source implementations of runbook/fix-recipe stores linked to alerts (Keep workflows, HolmesGPT runbooks, StackStorm, Rundeck auto-remediation).

## Bottom line

- **ITIL 4**: a known error is a *state* of a problem ("A problem that has been analysed but has not been resolved"), not an object; the practice guide prescribes two closure conditions and verification "using pre-agreed criteria", and specifies **no field schema, identifier, matching algorithm, review interval or retention rule** — the term "Known Error Database"/"KEDB" never appears in it.
- **Vendors diverge from ITIL**: ServiceNow stores known error as a Problem `State` value plus separate `Workaround`/`Cause notes`/`Fix notes` fields and a `kb_template_known_error_article` KB child table with dedicated `Cause` and `Workaround` fields; JSM has no known-error object at all (Confluence article + a `Known error` *resolution*, which inverts ITIL by marking the problem resolved); Freshservice uses a boolean "Is this a known issue?" toggle decoupled from lifecycle state.
- **No ITIL vendor documents automatic known-error→incident matching**; linkage is manual association or agent-side search. ServiceNow's nearest thing is Predictive Intelligence similarity over Description/Short description/Resolution notes with a diagnostic (not default) score reference of 60; its "Related Search" panel has **no similarity-threshold field**.
- **Sentry** "regressed" is not a status: it is `GroupSubStatus.REGRESSED = 6` on `GroupStatus.UNRESOLVED`, decided by three guards (already unresolved / `GroupResolution.has_resolution` / pending commit resolution) followed by one conditional `UPDATE … WHERE status=RESOLVED` whose affected-row count *is* the verdict — no event count, no rate, no `resolved_at` comparison.
- **Sentry is the only system found that verifies a fix actually shipped**, via release ordering (`date_released or date_added`) or commit-in-release containment — and its exact-release-equality case returns "not protected", so an event from the very release you resolved in can regress.
- **PagerDuty** publishes factors, never an algorithm: Past Incidents = same-service incidents ranked by an undocumented `score` (e.g. `46.8249`); Related Incidents = up to 20 other-service incidents from an online ML model plus a deterministic five-minute service-dependency rule.
- **incident.io** is the only vendor documenting its retrieval key: `text-embedding-ada-002` (1536-d) over summary+updates+custom fields, in pgvector with HNSW, cosine + a `minDistance` cutoff; Rootly does semantic search but weights matches by shared service, severity, owning team and recency; FireHydrant exposes a numeric similarity `threshold` defaulting to `0.2`.
- **Opsgenie's dedup key is `alias`, not `dedupKey`/`deduplicationId`**, scoped to *open* alerts, with counting/logging stopping at 100 occurrences while dedup continues; Opsgenie is end-of-sale 2025-06-04, end-of-support 2027-04-05, replaced by JSM only.
- **Large-scale AIOps grouping is deterministic**, dressed as AI: tag+time-window patterns (BigPanda), Sørensen–Dice over shingles with per-field thresholds (Moogsoft), WHERE-clause + `split by` (Splunk ITSI), `aggregation_key` (Datadog). **The only quantitative accuracy figures are vendor-reported** (BigPanda's white paper: 70–80% correlation, >90% noise reduction, 60% MTTR cut); no independent measured precision/false-positive rate was found anywhere, and the AIOps literature states there are no public benchmarks.
- **Open-source runbook stores bind recipes by description/tag matching, not by key**: StackStorm = trigger + ANDed `criteria` YAML (one action per rule); Rundeck = webhook + handler plugins with `retry`/notifications; Keep = CEL-filtered `alert` trigger; HolmesGPT = LLM matches the issue against each `description` (skills ≥0.26, runbook catalog ≤0.25) with **no expected-outcome field**.

## 1. The ITIL known-error record: what is prescribed and what is left to you

**Definitions (verbatim).** Problem = "A cause, or potential cause, of one or more incidents." Known error = "A problem that has been analysed but has not been resolved." Workaround = "A solution that reduces or eliminates the impact of an incident or problem for which a full resolution is not yet available. Some workarounds reduce the likelihood of incidents." (AXELOS *Problem Management ITIL 4 Practice Guide*, 22 Nov 2019).

**Known error is a state, not a record type.** ITIL says it is "the state of a problem" and merely *permits* separation: "although 'known error' is the state of a problem, some organizations prefer to have separate records for problem control and error control." Consequently the closure rule is inherited: "The above conditions for closure apply to known errors, regardless of whether they are problems."

**Prescribed:** three phases (problem identification — proactive and reactive, problem control, error control); two closure conditions; verification; and outputs including change requests, "Incident solutions" registered in the problem record, and the requirement that "Closed problem records should be available as part of the organization's knowledge base." Reactive identification links a problem record to "one or more incident records."

**Not prescribed — the whole data model.** No field schema, no identifier design, no matching-to-incident algorithm, no review interval ("periodically… in line with the agreed mitigation approach"), no retention rule. **"Known Error Database"/"KEDB" does not appear in the ITIL 4 practice guide**; the split development/live KEDB is an ITIL v3 artefact surviving only in legacy reproductions ("ensuring that the associated known errors are transferred from the development Known Error Database into the live Known Error Database").

**Closure and verification.** "Problem records may be closed only if one of the following conditions is met: The problem is solved: the risk of incidents associated with the problem is removed or decreased to an acceptable level. The problem no longer affects the organization." Verification exists but has no window: "The implementation of the solution is controlled and confirmed using pre-agreed criteria… For reactively identified problems, this can be done based on the change in incident dynamics (related incidents are resolved or prevented). For proactively identified problems, resolution control is based on the success of the initiated changes and may include a period of monitoring." If unconfirmed, "the team returns to the problem solution development step." Known errors may therefore stay open indefinitely.

**Table 2.1 — three mitigations, three outcomes:** full permanent fix → record **closed**; permanent workaround isolating errors (third-party/legacy) → "may be closed or remain open"; solutions that only optimise incident handling → record **remains open** and the known error is "periodically reviewed". Permanent workarounds "increase an organization's technical debt", and workarounds found during problem analysis "usually do not reduce the likelihood of incidents".

**Takeaway for a KEDB schema:** ITIL gives you a lifecycle predicate (`analysed && !resolved`), a closure predicate, and an obligation to verify against criteria you define. Everything a warden needs — the key, the similarity function, the review interval — is yours to specify.

Newer state management is New → Assess → Root Cause Analysis → Fix in Progress → Resolved → Closed, with `Resolution code` ("whether the problem is resolved, a fix is applied, a duplicate is available, or the problem coordinator accepts the risk") and `Duplicate of`. Do not conflate this with the newer Article Templates layer (`kb_article_template` / `kb_article_template_definition`), which the platform's pre-defined-template list covers with FAQ/How-To/What-Is/KCS/Standard — **Known Error is documented under ITSM Problem Management, not that list**.

**JSM details.** Default problem workflow "Problem Management workflow for Jira Service Management" is described by *purpose*, not a text state list: it exists to "transition problem workflows alongside these ITIL recommended activities: problem investigation, identification of workarounds, recording of known errors"; the graph itself ships only as an image. The DC 11.2 tutorial names concrete transitions — "Select Review and later Investigate. This will move your problem right into the investigation state"; after "Request for change", "the status of the issue is now **Waiting for change**" — and community reports add `Under Investigation`/`Under Review`. The incident↔problem link type is `Problem/Incident`, outward "causes", inward "is caused by", and is Atlassian-shipped (`pstyle = 'servicedesk_automation_default_linktype'`). The `[System] Problem` work type ships Affected services, Affected hardware, Investigation reason, Urgency, Impact, **Root cause**, **Workaround**, Pending reason, Source, Product/Operational categorization — though Atlassian's own template page calls the same set "the custom fields available for a problem ticket". There is no `Known error` work type; the five ITSM categories are Service request, Incident, Problem, Change, Post-incident review. A practitioner report (2025-05-29) found "no fields within the Investigate a Problem that refers to RCA or the Governance process" — the Root-cause field is free text, not an RCA process.

**Freshservice details.** "you can link a solution article from your knowledge base and as a workaround or a permanent solution for the problem"; the toggle is "From the problem's detailed view, toggle the 'Is this a known issue?' switch to YES", motivated by "factors like business impact, cost of the solution and ROI" delaying the fix.

## 3. Sentry: how "regressed" is decided, exactly

**States.** `Group.status` is an int enum: `UNRESOLVED=0, RESOLVED=1, IGNORED=2, PENDING_DELETION=3, DELETION_IN_PROGRESS=4, PENDING_MERGE=5, REPROCESSING=6`, with `MUTED = IGNORED`. "Regressed" is **not** a `GroupStatus`: `GroupSubStatus.REGRESSED = 6`, valid only for `UNRESOLVED` (siblings: `ESCALATING=2, ONGOING=3, NEW=7`). Search terms `is:new|ongoing|escalating|regressed`. The API action `resolvedInNextRelease` maps to `GroupStatus.UNRESOLVED` in `STATUS_UPDATE_CHOICES` — it is an action recorded in `GroupResolution`, not a queryable status.

**The decision.** `_handle_regression` in `src/sentry/event_manager.py` is three guards then one write:

1. `if not group.is_resolved(): return` — repeated events never re-regress;
2. `elif GroupResolution.has_resolution(group, release): return`;
3. `elif has_pending_commit_resolution(group): return`;
4. `is_regression = bool(<UPDATE … WHERE status=GroupStatus.RESOLVED SET status=UNRESOLVED, substatus=REGRESSED>)` — the DB row count is the verdict, so a concurrent resolve wins.

There is **no minimum event count, no rate/volume condition, and no comparison against `Group.resolved_at`** in that module. That is the single most transferable design fact here: regression is defined purely as *"a new event arrived for an issue that is currently in the resolved state, and no fix-scope guard covers it."*

**The fix-scope guard (`GroupResolution.has_resolution`).** No `GroupResolution` row → no protection (plain Resolve ⇒ any later event regresses). Event with no release → protected (no regression). `current_release_version` set ("resolved in next release") → semver: protected while `compare_version_relay(current_release_version, event_release) >= 0`; non-semver: protected while the anchor release matches or its order-date is newer. `type=in_release` → protected while the resolved release is semver-greater (or order-date ≥); **exact release-id equality returns False**, so an event from the very release you resolved in counts as a regression — a code-only inference the docs do not state.

Model: `GroupResolution(group unique, release FK, current_release_version, future_release_version, type {in_release=0, in_next_release=1}, status {pending=0, resolved=1})`. "Resolve in next release" is stored as `in_next_release`/`pending`; on new release creation `clear_expired_resolutions` re-points pending rows to that release, flips them to `in_release`/`resolved`, and stamps `data['version']`.

**Shipped-ness data.** `release_order_date()` = `(date_released or date_added)` when `organizations:release-resolution-finalized-order` is on, else `date_added`. Semver comparison uses parsed `major/minor/patch/revision/prerelease/build` columns. `Deploy` is **not** consulted — it only creates `ActivityType.DEPLOY` and notifications. Commit resolution uses `GroupLink(linked_type=commit, relationship=resolves)` + `GroupCommitResolution(group_id, commit_id)`, and regression waits while the resolved commit is absent from every `ReleaseCommit` (including commits reached via its PRs). API surface: PUT `/api/0/organizations/{org}/issues/{issue_id}/` accepts `status ∈ {resolved, unresolved, ignored, resolvedInNextRelease, muted}`, `statusDetails` (release data allowed only for issues in a single project), `substatus ∈ {archived_until_escalating, archived_until_condition_met, archived_forever, escalating, ongoing, regressed, new}`, `ignoreDuration/ignoreCount/ignoreWindow/ignoreUserCount/ignoreUserWindow`, `snoozeDuration`. The serializer types `statusDetails` as `{inNextRelease: bool, inRelease: str}` only — no `inCommit`/`inUpcomingRelease` key appears.

**Matching keys on the issue.** `Group` carries `culprit` (`db_column="view"`), `type`, `data` (JSON metadata/title/type), `message`, `logger`, `platform`, `level`, `first_release`, `times_seen`, `first_seen/last_seen/active_at`, `resolved_at`, `short_id`. Identity is `GroupHash`, unique on `(project, hash)` with a 32-char `hash`, plus `group_tombstone_id` (discard-forever) and `state=1` (locked during migration). `get_associated_fingerprint()` returns `hashing_metadata['fingerprint']` **only** for hybrid/custom fingerprints; default stacktrace-derived hashes have none.

**Fingerprint construction.** Every event gets `["{{ default }}"]` unless the client sets one. Pipeline: `normalize_stacktraces_for_grouping` (stack-trace rules flip `in_app`, original preserved for reprocessing) → server-side fingerprint rules (may override, or emit `{{ default }}` for a *hybrid*) → the grouping algorithm "if and only if" the fingerprint is unset or contains `{{ default }}`. One event yields **several** hashes (an "app" hash over in-app frames and a "system" hash over all frames); they become `GroupHash` rows and **any** match attaches the event. The hash function is `hash_from_values`: `md5()` updated with each value's bytes, **no separator** — an order-dependent concatenation. `CustomFingerprintVariant.get_hash()` hashes the raw list; `SaltedComponentVariant` splices `root_component.iter_values()` in place of each `{{ default }}` and suffixes the variant key `_hybrid_fingerprint`. Rule syntax is `matcher:expression -> value list` with matchers `error.type, error.value, logger, level, message, stack.abs_path, stack.function, stack.module, stack.package, tags.<name>`, `app:` and `family:`; **first match wins**; `{{ default }}` on the RHS subdivides rather than overrides.

**Churn defences (worth copying).** Grouping-config changes are versioned per project, and `maybe_run_secondary_grouping` recomputes hashes under the older `sentry:secondary_grouping_config` so an unknown primary hash "can be matched to an existing group if there is one"; secondary hashes that don't already exist are never persisted. Frame hiding keeps a secondary hash (`[A1,B1,A2,A3]` **and** `[A1,A2,A3]`), producing an implied merge.

**Failure modes.** Auto-resolve (`sentry:resolve_age`) resolves every `UNRESOLVED` group with `last_seen <= now - age hours` and logs `SET_RESOLVED_BY_AGE` — so the next event is declared a regression **with no fix behind it**: a systematic false positive by construction. Conversely, release-less events (and semver events ≤ the anchor) stay silently unresolved-but-erroring. Ignore/snooze expiry produces `UNRESOLVED`, not `REGRESSED` (`Group.get_status()` silently un-snoozes). Refactors changing a Python context line, minified JS function names, added decorators and cross-OS native frames all create new groups instead of regressions; message fallback "is very likely to create a high number of independent groups"; merge/split is lossy and backlogs Snuba. The self-hosted/SaaS semantics are shared ("Applies To: All SaaS Customers and Self-Hosted Users"); divergence is feature-flag gating and Celery lag, not logic.

**AI grouping as a hash-miss fallback.** After hashes are computed and no group is found, an eligible event's message + in-app frames are embedded and compared against the project's existing error embeddings, merging "if a similar issue is found within the configured threshold". Eligibility excludes fully custom fingerprints, platform `{"other"}`, empty/oversized stacktraces (`should_call_seer_for_grouping`); the rate-limit check must run last because it increments the attempt counter. Request: `{event_id, hash, project_id, stacktrace, exception_type, k, referrer, model, training_mode, platform, skip_fallback}`; response entries `{parent_hash, stacktrace_distance, should_group}` + `model_used`, sorted ascending by `stacktrace_distance`, threshold sent as `SEER_MAX_GROUPING_DISTANCE`. Tokenizer from `data/models/jina-embeddings-v2-base-en/tokenizer.json`; stable model `SEER_GROUPING_STABLE_VERSION = v2.1`, with training-mode requests populating embeddings "until it is promoted". A Seer match can still be rejected on exception type/value mismatch. Sentry publishes **no** recall@k or precision figures.

## 4. PagerDuty: Past Incidents and Related Incidents

REST v2 (`Accept: application/vnd.pagerduty+json;version=2`, `https://api.pagerduty.com`), Events v2 (`https://events.pagerduty.com/v2/enqueue`).

- **Past Incidents** — ML, **same service only**: "Past Incidents will only return incidents from the same service as the incident you are viewing." Four stated factors: "The semantics of the incident title", "Which responders have responded to past incidents", "The duration of the past incident", "The date and time of the past incident's creation." UI is a **6-month heat map** (darker = higher concentration/day; clicking a day populates the top five) plus a list of Title / Duration / Created / Last Changed By, sortable Recent vs Relevant. Gated to the AIOps/Signal Intelligence/Event Intelligence add-ons with AIOps enabled per service.
- **Related Incidents** — "up to 20 recent incidents on other services" from "a completely online and real-time machine learning algorithm" plus service-dependency data; ML factors are time proximity, relatedness of alert metadata, and human feedback (thumbs up/down, cross-service merging). Deterministic rule: "When two incidents are triggered within five minutes of each other and one service is directly dependent on the other, these incidents will be marked as related. Similarly, if incidents occur within this time frame and share a parent business service." Thumbs appear "only… on incidents generated by the machine learning algorithm, and it takes about 5–10 human inputs to train our algorithm on a new behavior."
- **Keys never named as factors**: escalation policy, team, alert group, incident type, title string match.
- **Endpoints**: `GET /incidents/{id}/past_incidents` → `past_incidents[].{incident:{id,created_at,self,title}, score}` — e.g. `"score": 46.8249` for a title match, `0` for an unrelated one; default `limit` 5 (max 999); **the score's definition and scale are undocumented**. `GET /incidents/{id}/related_incidents` → `relationships[]` of `type: machine_learning_inferred` with `metadata.grouping_classification: "similar_contents"` and `user_feedback.{positive,negative}_feedback_count`, or `type: service_dependency` with `dependent_services`/`supporting_services`. `GET /incidents/{id}/outlier_incident` leaks the text-mining artefact: `incident_template {id, cluster_id, mined_text}` where mined_text looks like `[LINUX]Used disk space is more than <MEASUREMENT> on volume <*> : PROBLEM for <*>`, plus `occurrence {count, frequency, category, since, until}` — categories are numeric: Frequent ≥20% of incidents in the preceding 30 days, Rare ≤5%, Anomaly = not seen in 30 days.
- **History sweep**: `GET /incidents` filters `incident_key`, `service_ids[]`, `team_ids[]`, `user_ids[]`, `urgencies[]`, `statuses[]`, `since`/`until` (max 6 months), `sort_by`; incidents carry `alert_grouping {grouping_type:"advanced", started_at, ended_at, alert_grouping_active}` and `resolve_reason`. **No title search, no similarity filter.**
- **Dedup keys**: Events v2 `dedup_key` ("Identifies the alert to trigger, acknowledge, or resolve. Required unless the event_type is trigger"); REST alert-level `alert_key` ("Alert de-duplication key"); legacy `incident_key` — "Incidents with child alerts do not have an incident key."
- **Grouping is configuration, not inference**: Intelligent Alert Grouping joins when the most recent alert is inside the window, the incident is <24h old, and "the… algorithm determines that the alerts are similar" over up to five PD-CEF fields (default `Summary`, ≤1,000 chars, "does not evaluate based on exact matches", single-service only, API merges don't train it); Content-Based Grouping requires **exact match** on Class/Component/Group/Severity/Source/Summary/custom details, All vs Any, 5 min–24 h rolling, and "does not chain fields with subsequent alerts".
- **Accuracy**: none published. The only quantified claim is a customer narrative — DataOps "achieved a 37% reduction in incidents and increased efficiency two to three times, allowing 10 FTEs to support a workload that would typically require 20–30 FTEs" — alongside an explicit warning: "The larger the grouping time window, the higher the chance of overgrouping."
- **Unreconciled disagreement**: the current KB describes `Incident Types` as a *manual* taxonomy (Base/Major/Security/custom, inheritance up to three levels), while the outlier API returns a mined `incident_template` with `cluster_id`. Nothing retrieved reconciles ML clustering with the manual type hierarchy.
- **Not established**: resolution notes, postmortem links, runbook fields or automation actions on the incident object; the related change-events response shape.

## 5. incident.io, Rootly, FireHydrant

**incident.io** is the only vendor whose matching key is documented — in an engineering post, not the docs: text is serialised into a labelled block of **summary, updates and custom fields** (timestamps and UUIDs excluded, newlines stripped), embedded with OpenAI `text-embedding-ada-002` (1536 dims), stored in Postgres **pgvector** with an **HNSW** index, ranked by **cosine similarity** with a `minDistance` cutoff — embeddings + threshold, not LLM ranking. Vectors carry `model` and `prompt_version` so they can be backfilled; an in-progress incident is **re-embedded on every update but only after a minimum-activity gate** (an update plus a few messages). Current Nexus docs describe matching "not by keyword, but by what actually happened… the symptoms, the systems involved, and the shape of the failure" and are silent on the model. Separate mechanisms: alert `deduplication key` (fingerprint) and "duplicate incident prevention", which is purely the last **10 minutes** over Triage/Active incidents. Suggestions surface the previous incident's final summary, its lead, and links to channel/post-mortem; "Mark as related" persists a first-class object (`GET /v1/incident_relationships`). The fix record is the AI-suggested summary (Problem / Impact / Causes / Steps to resolve). No documented path auto-executes a stored fix. **No accuracy/adoption/time-saved figures** — the AI launch post is testimonials only.

**Rootly** = semantic recall + explicit deterministic weighting: matches are "weighted by shared services, comparable severity, the same owning team and recency", search is "by meaning rather than keyword"; inputs are "title, summary, severity, services"; scope is own-org, **confirmed, public** incidents, default **180-day** lookback; "similar wording alone doesn't qualify". No model or store is named. Crucially the docs separate match from fix: "a match points AI SRE at an earlier incident **but doesn't say how it was fixed**", and live investigations do not read Slack history; same-service conclusions from the last **30 days** including resolution/mitigation notes are fed in as candidates. The fix is stored as two fields — **mitigation notes** ("what actions were taken to stabilize") and **resolution notes** ("what was done, why it worked, any remaining follow-up") — flowing into timeline, retrospective and status updates. Mark as related / Not related is described as training; scripting is manual Slack-command workflows only.

**FireHydrant** — algorithm undocumented; the API leaks the cutoff: `GET /v1/incidents/{incident_id}/similar` takes `threshold` (float, **default 0.2**) and `limit` (default 5). Copilot "proactively compares ongoing incidents to your existing and previous incidents"; posts to the incident's Slack channel and lists under **Suggested Incidents** in the Command Center sidebar (snoozable), separate from manually-marked **Related Incidents**. FireHydrant *does* auto-execute stored fixes — but **by runbook condition, not by AI recall**: runbooks are "FireHydrant's automation engine", steps "execute immediately and concurrently", conditions are re-evaluated against the last 90 days of incidents, and an **Execute a Script** step stores the Shell/Bash script itself and records executor, duration, output and success/error. AI features are individually gated with per-feature cooldowns and max-posts.

**Cross-vendor pattern:** every one of the three treats the "what fixed it" record as *prose* (summary / resolution notes), attaches it as *evidence* rather than executable action, and none publishes accuracy, adoption or time-saved figures that could be verified.

## 6. Opsgenie: dedup semantics and the 2027 endgame

**Dedup key = `alias`.** "The Alias field is a user-defined unique identifier for 'open' alerts. There can be at most one open alert with the same alias at any time." A create on an existing open alias "increases the Count value of the open alert by one instead of creating another alert"; "the Count property and logging of the de-duplication event stops after 100 occurrences; however, de-duplication still continues as long as the alert is not closed." There is **no documented time window** — the scope is the lifetime of the open alert — and the only time interaction is that dedup postpones an Auto-Close Policy by that policy's duration. Because the constraint is on *open* alerts, closing (not acking — acked alerts are still open) releases the alias. `alias` is also a valid `identifierType` alongside `id` and `tiny`, so an agent needs no stored ID.

**Not `dedupKey`/`deduplicationId`.** The JSM Integration Events OpenAPI schema defines the key as schema `Alias` ("Client-defined identifier of the alert, that is also the key element of Alert De-Duplication", max 512) and `CreateAlertRequest` has no `deduplicationId` property. API limits: `message` 130, `description` 15000, `entity` 512, `source` 100, `note` 25000, `details` 8000 total, responders 50, visibleTo 50, actions 10×50, tags 20×50; create/delete/action calls return 202 and are polled via `GET /v2/alerts/requests/:requestId`. The JSM successor repeats the model verbatim ("Only one open alert with a specific alias can exist at any given time"; count logging ceases at 100, dedup continues) and exposes `GET /v1/alerts/alias?alias={alias}` plus a hard list cap ("More than 20000 alerts cannot be retrieved").

**Correlation / knowledge reuse.** Opsgenie's documented mechanism is account-level alert↔incident association (Standard/Enterprise): "You can only associate up to 50 alerts when creating a new incident"; alert types are Responder/Owner/Associated; "For the Associated Alerts of an incident, the notification flow will be suppressed"; closing/deleting an incident closes/deletes responder alerts but leaves associated alerts untouched. The JSM feature index adds "Group alerts using Rovo", "Configure alert grouping", "View alerts by signal or noise", "View related alert groups", and "View similar alerts, past responders, and related resources" (Atlassian Intelligence). ## 7. Large-scale AIOps: correlation is deterministic, retrieval is semantic, numbers are vendor-owned

**BigPanda** — two layers, and its own sources disagree on which is "AI". Alert→incident grouping is specified as *correlation patterns*: source system + tags + time window. Defaults: `host`/60 min ("used by over 90% of BigPanda customers"), `application`+`check`/30, `application`/29, `service`/25; max 300 alerts per incident, up to 2,000 tags per alert; patterns are re-evaluated in real time and the longest-window match supplies the incident title. BigPanda's own 2026 blog classifies alert correlation as "scoped to a single domain, rules-based, and primarily designed to reduce alert noise", positioning a separate **incident correlation** product as the AI layer — while docs-index phrasing calls the alert engine "AI/ML-driven". Incident correlation (genAI + IT Knowledge Graph, requires account-team enablement) takes "natural language, topology data, CMDB relationships, and historical runbooks" and emits six relation types including **Recurrence** ("The same or highly similar incident repeating at a different time") plus a General relation for semantic/topological similarity — so its retrieval key is semantic + graph-neighbourhood, not a hash.

**Moogsoft (Dell)** — acquired 2023-09-17; continues as *Dell APEX AIOps Incident Management*. Its similarity is concretely specified: bag-of-words + shingling (default shingle size 3) with the **Sørensen–Dice** coefficient against a per-field threshold (worked examples at 80% and 70%, e.g. `clst1sql4` vs `clst1sql5` = 85%); list fields (`services`, `tags.labels`) match on exact member overlap with no threshold ("datacenter" does not match "database"). Correlation groups exist so different teams can set different "similarity requirements for incidents before they are candidates for merging". Legacy Onprem v9 clustering was Cookbook (attribute/text similarity + Vertex Entropy topology) + Tempus (timestamps). Its marketing ("far more robust and scalable than traditional AIOps approaches based on hard-coded rules") sits uneasily with documented field-by-field thresholds, and its own datasheet lists correlation as "AI/ML-based… similarity matching" while publishing **no** precision, recall, noise-reduction or compression figure.

**Splunk ITSI** — correlation searches emit notable events; aggregation policies group them via WHERE-clause filters, a `split by` field, and breaking criteria (pause, event count, clearing event). The overview says events are grouped "based on their similarity" and then defines that as "a set of predefined rules". Retrieval of past episodes is field search over Episode Review; no semantic retrieval is documented. Normalised third-party fields are `itsiAlert`, `itsiDetails`, `itsiInstance`, `itsiRawStatus`, `itsiSeverity`, `itsiSubInstance`.

**Datadog** — incidents are declared from monitor alerts/events; past incidents are retrieved by key:value search (`severity:`, `services:`, `teams:`, `state:`, responder, root-cause category) plus Incident Analytics. Documented grouping key is `aggregation_key`, unique per Monitor ID and, "starting March 1st [2025], this key will also include Monitor Group". Watchdog computes baselines and publishes no precision/recall. Bits Investigation is an agentic hypothesizer ("iteratively forms hypotheses, gathers relevant telemetry, and uses data-based reasoning"), not a documented similar-incident retriever.

**Dynatrace** — only marketing-level description retrievable: Smartscape is "a real-time dependency graph that keeps itself accurate", feeding Dynatrace Intelligence "with reliable live context for root cause analysis and auto-remediation". No algorithm, thresholds or metrics.

**Numbers.** Only BigPanda's white paper: most customers "achieve correlation rates of 70 to 80 percent as soon as they subscribe"; a Fortune-100 networking customer at "94% correlation out of the gate" cutting MTTR "by 60 percent" on >70,000 daily alerts; product reduces noise "by over 90 percent". These conflate correlation rate, noise reduction and MTTR and must not be averaged. No third-party measured figures were found. The AIOps survey (arXiv 2304.04661) explains why: threshold rules trade false positives against false negatives, there are "no public benchmarks on log based RCA tasks", evaluation is on private enterprise data, existing anomaly datasets "have been criticised to be trivial and mislabelled", and ticket/human-activity data holding prior fixes is largely unexploited.

## 8. Matching keys, precisely: four families and their failure modes

1. **Exact hash keys (fingerprints).** Sentry: `md5` over an ordered, unseparated value list, several hashes per event ("app" + "system"), any-match attaches. Failure modes are documented and structural: refactor changes the Python context line; minified JS function names are "unstable between builds"; decorators add a frame; native frames differ by OS/compiler; message fallback over-splits; fingerprint-rule or grouping-config edits mint a new hash and therefore a new issue (the old resolved issue never regresses). Mitigations worth copying: secondary/legacy-config hashing, frame-hiding secondary hashes, hash tombstones, and a short grouphash cache (60 s).
2. **Deterministic tag + time-window keys.** BigPanda `host`/60 min; Opsgenie `alias` scoped to open lifetime; PagerDuty Content-Based Grouping (exact match, All/Any, 5 min–24 h, no chaining); Datadog `aggregation_key` (Monitor ID [+ Monitor Group]); Splunk ITSI `split by` + breaking criteria. Cheap, explainable, and the only family with *published defaults*. Failure mode: over-grouping when the window widens (PagerDuty's own warning), and no chaining means transitive duplicates stay separate.
3. **Text/template similarity with a threshold.** Moogsoft Sørensen–Dice over shingles with per-field thresholds; PagerDuty Intelligent Alert Grouping over ≤5 fields, ≤1,000 chars; FireHydrant similarity `threshold` default 0.2; ServiceNow Predictive Intelligence with a tuned per-solution threshold. **Drain/Drain3** is the reference log-template miner: fixed-depth parse tree (length layer, then first `depth-2` non-numeric tokens, digits collapsed to `*`), leaf chosen by `simSeq` = matching tokens / token count against threshold `st`; below `st`, a new group is created and differing positions wildcarded. Paper settings `depth` 3–4, `st` 0.3–0.4, `maxChild` 100; highest accuracy on four of five datasets, but **0.86 on Proxifier versus Spell's 0.87**, with 51.85%–81.47% faster runtime. Failure mode: template drift when message text changes shape, and threshold trade-offs with no ground truth.
4. **Embedding / semantic retrieval.** incident.io (`text-embedding-ada-002`, 1536-d, pgvector HNSW, cosine + `minDistance`, re-embed gated on activity, `model`+`prompt_version` stored); Sentry Seer (`jina-embeddings-v2-base-en` tokenizer, `k` neighbours under `SEER_MAX_GROUPING_DISTANCE`, sorted by `stacktrace_distance`, model version pinned `v2.1`, training-mode requests staged separately); Rootly (semantic + service/severity/team/recency weights); ServiceNow PI similarity (word corpus over Description/Short description/Resolution notes, refresh every 15 minutes). **No retrieval-metric figures were published by any of them**; the ServiceNow KB does document a concrete small-data failure: when training data is sparse "the percentile score distribution compresses", and fewer than a few hundred records in the training pool is "a strong confirmation".

## 9. Fix-artifact keying: what is stable, what is not, and who verifies

| Fix artifact | How it is keyed | Who does it | Stability caveat |
|---|---|---|---|
| **Commit** | `GroupLink(linked_type=commit, relationship=resolves)` + `GroupCommitResolution(group_id, commit_id)`; resolution is *pending* until some `ReleaseCommit` contains the commit (PR commits included) | Sentry | Rebase/cherry-pick identity not verified by any source retrieved |
| **Release/version** | `GroupResolution(group, release, type, status)` + `release_order_date = date_released or date_added`; semver columns drive ordering; archived releases skipped when picking "next" | Sentry | Non-semver releases fall back to creation-date ordering; exact-release equality is treated as *not* protected |
| **Deploy** | `Deploy(date_finished, date_started, name, url, notified)` — notifications/activity only | Sentry | Explicitly **not** used to decide shipped-ness |
| **Runbook / skill** | StackStorm pack YAML path + rule `criteria`; Rundeck job UUID + webhook path; Keep workflow id + CEL `alert` trigger; HolmesGPT `SKILL.md` frontmatter `description` (+ `alerts:` scoping to `GroupedIssues.aggregation_key`) | all four | HolmesGPT matches on *prose description*; no expected-outcome field exists |
| **KB article** | ServiceNow `kb_template_known_error_article` (`Cause`, `Workaround`, `Valid to`, `Source Task`); JSM Confluence article; Freshservice solution article linked as workaround/permanent | ITSM vendors | Linkage is manual association or agent search, not a key |
| **Script** | FireHydrant "Execute a Script" stores Shell/Bash inline with executor/output/status recorded back | FireHydrant | Not AI-selected; fires on runbook conditions |

**Verification of reuse** is the thinnest documented layer. Only two mechanisms actually check outcome: (1) Sentry's release/commit containment test, which is the only "did the fix ship?" primitive found; (2) execution-status recording — StackStorm actions must `exit 0` (or return `(False, msg)` for a failed execution), Rundeck exposes `retry`/`onretryablefailure` and `notification` hooks templated with `${execution.id}`/`${execution.status}`, FireHydrant records runbook-step success. Everything else records that a human *said* what fixed it (Rootly's mitigation+resolution notes, incident.io's summary, ServiceNow `Fix notes`) with no automated check that the fix still applies. HolmesGPT is explicit: frontmatter is only `name`/`description`; the schema has no expected-outcome, success-criterion or verification field, and "remediation plus verification steps" is authoring guidance in a README, not an enforced check.

## 10. Open-source alert→fix-recipe stores

- **StackStorm** — recipes are pack-scoped YAML: `/opt/stackstorm/packs/<pack>/rules`, plus action YAML metadata + script and Orquesta YAML workflows. Binding = trigger type + ANDed `criteria` (equals, regex, matchwildcard, contains, search/any/all, timediff_*, exists…), with Jinja interpolation into action params. **One action per rule**; multiple actions require multiple rules or a workflow. Deployed rules are queryable (`st2 rule list`), enforcements recorded (`st2 rule-enforcement list`), executions retrievable (`st2 execution get`). A real in-repo rule: webhook trigger, criteria `trigger.body.name equals st2`, action `core.local`.
- **Rundeck** — job YAML (`job-yaml-v12` served at the v13 URL) with `sequence`, `options`, `retry` (int or `{delay, retry}`), `schedule`, `nodefilters`, `notification`, `orchestrator`, `plugins`; per-step `errorhandler` with `keepgoingOnSuccess`; conditional-logic steps commercial (5.20.0+). Binding = `POST /api/<ver>/webhook/<id>#<event>` into handler plugins ("Run Job" in OSS; Advanced Run Job, PagerDuty/DataDog/SNS/GitHub Run Job commercial); Runbook Automation adds a Webhook Debugger that explains why a payload did or did not trigger rules.
- **Keep** — declarative workflow YAML (`workflow:` metadata, `triggers:`, `actions:`); triggers manual/interval/alert/incident/field-change; `alert` filters are **CEL** (`source.contains("datadog") && severity == "critical"`), with the legacy key-value+regex filter list deprecated but supported.
- **HolmesGPT** — version-split: ≤0.25 used `catalog.json` (`id`, `update_date`, `description`, `link`) + markdown runbooks loaded via `custom_runbook_catalogs`; **≥0.26 replaced this with Skills** — one directory per skill, `SKILL.md` with YAML frontmatter (`description` required and used for matching, `name` optional) plus a body (Goal / Workflow / Synthesize Findings / Recommended Remediation Steps). Loading precedence: remote Robusta skills > `custom_skill_paths` > built-in (`holmes/plugins/skills/builtin/`); `custom_runbook_catalogs`/`catalog.json` no longer supported. Packaged latest is **0.45.0** on PyPI. Binding is **LLM description matching** + `fetch_skill`, with optional `alerts: List[str]` scoping against `GroupedIssues.aggregation_key` — i.e. alert-name-scoped skills. **No documented mechanism reads a runbook URL out of alert annotations.**

**Published auto-remediation success/failure figures: none found for any of the four.**

## 11. Design implications for a solo "warden" (3 hosts, ~600 incidents/6 months)

- **Make regression a predicate over (state, fix scope), not a timer.** Mirror Sentry's three guards: regress only if the record is currently `resolved`, the fix artifact does not cover the incoming version, and no commit is pending-in-release. Do **not** add an event-count threshold — no system reviewed uses one — and do not compare against `resolved_at`.
- **Never let age-based auto-resolve set the fix.** Sentry's `sentry:resolve_age` is the canonical systematic false positive: the next event is "regressed" with no fix behind it. In a 600-incident ledger, mark stale records `stale_auto_resolved` and exclude them from regression counts, or your regression rate becomes a measure of idle time.
- **Store the fix as a scope, not a note.** The only verifiable fix key is version/commit containment (`released_at`/`fix_release`/`fix_commit` with an "is this commit in this release?" check). Record prose (Rootly-style `mitigation_notes` + `resolution_notes`) *alongside* that scope, not instead of it.
- **Two keys per incident, deliberately.** A stable hash over `(service, normalised error_type/error_value, top-N normalised frames or log template)` for identity, plus a per-source `alias`-style dedup key with Opsgenie semantics (one **open** incident per alias, increment count, stop logging at 100, no time window). Keep the hash recomputable under an older config, as Sentry does, so a rule change does not orphan history.
- **Prefer deterministic matching at this scale.** With ~600 incidents, tag+time-window patterns (BigPanda's `host`/60 min is the most-used default anywhere) and Drain-style templates give explainable matches; embedding retrieval is the least-evidenced option, and the one documented small-corpus pathology — score-distribution compression below a few hundred training records — applies directly. If you do embed, pin model + prompt version and store the threshold, as incident.io and Sentry do.
- **Bind a recipe to an alert by name/tag, verify by execution status.** HolmesGPT's `alerts:` scoping and `description`-based matching, StackStorm's ANDed `criteria`, and Rundeck's `retry`+`notification` hooks together give the whole loop; add the field none of them has — an `expected_outcome`/post-check per recipe — or reuse verification stays unmeasured.
- **Gate the AI layer.** Every vendor gates similarity behind a plan, per-feature toggles, cooldowns and max-post limits (FireHydrant per-feature toggles + posting limits; PagerDuty add-on + per-service AIOps; BigPanda incident correlation requires enablement). A solo warden should do the same: suggestions as evidence, never as execute authority.
