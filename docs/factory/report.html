1. Verdict

Build one loop that takes every piece of work — an outage, a bug, a stale dependency, a feature you asked for — through the same path: deterministic code does everything it can, cheap models judge, Claude Code on your two Max accounts writes every line of code in herdr, and verification gates every ship. It runs as one new factory service on the mini — a reconcile loop over Postgres, in Bun — with Argo as the cockpit on the same box. Warden is switched off, not migrated.

The scarce resources are your attention and the Max windows, not money. 32 % of new items reached you in v1's 14-day sample, at ≈ 62 notifications a week, and only 3.8 % of those escalations were genuinely yours. IU API spend for all personal gateway work was $183 last week, most of it review.

The target in ten points#

  1. One loop for all work. Incidents, bugs, hygiene findings, upgrades and your requests are Issues; a wave plan is a set of Tasks. Nothing has a side door.
  2. Three engines, one job each. Deterministic code spends nothing. Cheap models on IU API tokens (Haiku 5.5, DeepSeek V4.1 Flash, agent-gateway's decision model) triage, investigate, plan and review. Claude Code on Max writes code — only there, and only in herdr.
  3. Two Max accounts, one pool. The account is picked at spawn and kept while its cache is warm. Urgent work takes any headroom, normal work respects pace, upkeep uses capacity that would lapse. Nothing spills to IU API tokens; work waits for the reset.
  4. A reconcile loop, not a workflow engine. Every few seconds each open Issue and Task is re-observed, its state derived from facts, and at most one next action taken. A crash, a redeploy or a reboot costs one tick.
  5. Every repo describes itself in project.yaml and implements one make contract that CI, agents, review and the ship step all call.
  6. Dedup is deterministic first and learns. Rules group signals (F1 0.889 on the held-out set); a decision model scores the ambiguous rest; the investigator merges and splits; every grouping decision is kept as a label.
  7. Self-healing starts with waiting. A grace window lets transient failures recover; a known fix runs as a deterministic runbook; only then does an agent investigate.
  8. Verification gates shipping, and the candidate cannot weaken it. Checks run on the merge result with the base branch's own Makefile and tests; a failed post-deploy check rolls back to the last deploy that held.
  9. Upkeep is cheap code. Jobs are small scripts that spend zero tokens when nothing is wrong.
  10. You decide business only — product direction, spend, irreversible data loss, other people — as a three-line card with a default and an expiry. SLO: under 1 % of items reach you.

2. What changes for you

Once it runs#

  • You keep working in herdr exactly as now. c, rd wave, /wave and your own sessions stay; the picker balances the iu and me accounts, and nothing you start runs on IU API tokens.
  • You ask for work in one sentence — in Argo, to Hermes, as a TickTick item tagged #factory, or factory issue new weatherorb "…". It is planned, queued, built in herdr, verified and shipped; you read about it in the morning briefing.
  • You look at one place: Argo on the mini — Now (anything that needs you; usually nothing), Projects, Factory (what runs, what waits for capacity and until when), Usage, Artifacts.
  • You get pinged for two things: a decision card that is genuinely yours, and the 07:00 briefing. No evening briefing. Slack stops being an alert inbox; the one alert left there is "the mini or the factory is down".
  • Every text the factory writes to you is three lines: what happened, what it did, what you decide (usually nothing). No ids, no internal names; detail sits behind an expander. A lint rejects a card that breaks this before you see it.
  • You comment on plans and reports in Argo's Artifacts; the comment reaches the agent that wrote it. Until W5 lands, plannotator stays the review surface.
  • Work repos stay yours. IuRoot is never monitored and the factory never starts work there.

3. Principles

Eight rules. A design choice that breaks one is wrong.

  1. Deterministic before cheap before expensive. If a script can decide it, a script decides it. If it needs judgment but no code change, a cheap model decides it. Only writing code earns a Max session.
  2. Max writes code, IU API tokens think. Claude Code on the iu and me Max accounts is the only thing that changes a repo, and it runs in herdr, where you can watch it. IU API tokens pay for gateways, OpenCode, Hermes, research and review. A full Max pool means waiting, never spilling.
  3. One loop, no side doors. Every piece of work enters as an Issue or a Task and leaves through verification.
  4. Facts are stored, state is derived. The database holds what happened: signals, commits, check results, decisions, session observations. "Working", "stuck", "ready to merge" are computed from facts on every tick, so they cannot drift.
  5. Done means observed. A Task is done when its checks pass on the exact commit that merges and, after a deploy, when the running system says so. An agent saying "done" is a claim.
  6. Wait before acting, look before acting. Every alert class has a grace window, a known fix runs before an investigation, and every action re-reads the current state of the world first.
  7. You decide business, nothing else. Product direction, spend, irreversible data loss, other people. Anything else that reaches you is a defect in the loop.
  8. Plain words for humans. What the factory writes to a human is short, verdict-first and free of internal names.

Fixed boundaries#

  • Security is the tailnet plus your GitHub user. The factory opens no public endpoint. Sources it cannot reach directly are polled, or arrive through the Slack adapter.
  • No caps on an agent's work. No turn limits, no wall-clock ceilings; the one liveness rule is the idle watchdog. Budgets stop runaway loops, not slow work.
  • AGENTS.md only. No CLAUDE.md in any repo.

Three ways in#

  • Signals from sources and jobs pass dedup and become Issues: incident, bug, upkeep.
  • Requests — Argo, Hermes, a TickTick item tagged #factory, factory issue new — skip dedup and settle and start at Investigate + plan. A request that already has a plan starts at Admit.
  • Wave plans (/wave, or a plan an investigation produced) are Tasks with dependencies. The plan file keeps the prose and the task ids; the factory keeps the state.

What you see of an Issue#

Six states in Argo; the reconciler keeps finer steps internally. Stuck has an exit that does not need you: after three failed attempts the Issue waits for the next capacity window, gets one more attempt with a fresh investigation that is told why the earlier ones failed, and then closes as gave up with a line in the briefing. A new signal re-opens it.

The reconcile loop#

The factory service is one Bun process. It holds a Postgres advisory lock, so a second copy exits at start. Every five seconds, and immediately on a NOTIFY from new facts, it picks up every Issue and Task whose wake_at has passed or whose facts changed, and for each:

  1. reads its facts and the current state of the world it depends on (the container, the PR, the session's pane, the deploy);
  2. derives its state;
  3. takes at most one next action through the effect registry, keyed by (entity, generation, step) — an effect that already happened is observed, never repeated;
  4. records the outcome as a fact and sets the next wake_at.

Long work is started, then observed: spawning a session, starting an investigation or a deploy is one action; its progress arrives as facts on later ticks. Nothing waits in memory, so a crash, a redeploy of the factory itself or a reboot loses at most one tick. Re-opening an Issue or un-sticking it bumps its generation, so effects from an earlier generation can never land twice.

After downtime, every open deadline is shifted by the time the factory was down, so a decision you could not answer while Argo was dark does not take its default the second the mini comes back.

The brief every session gets#

Sent on every spawn and every resume, generated from the Task. The standing-orders part is identical across spawns, so it stays in the prompt cache; the task part comes last.

  • Goal and done-definition — the acceptance checks, as commands.
  • Scope — repo, files, what is out of bounds.
  • Context — the Issue, the investigation, similar past Issues and how they were fixed.
  • Branch — factory/<task-id>. Never rebase another branch, never merge, never touch the Makefile, CI or test configuration unless the Task says so.
  • Report — factory task done|blocked|note. The factory, not the agent, decides when a Task is done.

Witness#

Witness is part of the factory process. It watches herdr and records facts per session: spawned (with an epoch number), output seen, idle, blocked on a question, hit a usage wall (and its reset time), exited, and the account actually in effect. The Task reconciler reads those facts — there are no messages to lose. Rules:

  • Done needs the agent's factory task done, no new commit for five minutes and an idle pane. The pane is then stopped before verification starts, so nothing lands after the checks.
  • A usage wall is not idleness. The idle watchdog is suspended until the reset; the Task re-enters admission (§5).
  • A dead pane is respawned from the branch. Three deaths in ten minutes without a new commit mark the Task blocked and send it back to planning.
  • Stuck sessions get at most one interrupt every three minutes, never a continue from you.
  • Finished workers' tabs are closed when their Task closes.

Workers and mothers#

  • Every Task gets a fresh worker by default — a Claude Code session in herdr with the brief.
  • Fleet projects keep a mother (basalt-ui, argo, weatherorb, shutterflow, factory): the session that owns that project's multi-wave plans, as basalt-ui's does today. Tasks from her plan go to her, and she may fan out workers on disjoint files. Incident fixes and small requests do not wake her.
  • A follow-up goes where the cache is warm: within the hour, to the session that did the work.
  • Idle mothers are compacted or closed by the herdr hygiene job once the first one idles past a day (§9); finished workers' tabs close with their Task from W2.

Verification the candidate cannot weaken#

  • Required checks run in a factory-owned checkout of the merge result (the branch rebased onto the current tip), using the base branch's Makefile, CI and test configuration.
  • A change that touches the verification surface — Makefile, CI, test config, project.yaml, verify scripts — gets a full review whose adversary is asked one question: does this weaken verification? Test and check counts may not drop. If either fails, the Task goes back to planning; it does not stop at you.
  • No evidence, no auto-ship. A project without make test or make verify cannot auto-ship code; the factory first opens a Task to add the missing target.
  • Acceptance checks are written from the plan, not the diff: a separate fresh session reads the plan and turns its acceptance checks into smoke steps in make verify.

Merge, deploy, hold, roll back#

  1. Merge, one at a time per repo: rebase onto the current tip, re-run the changeset checks on the result, then fast-forward the default branch to exactly that commit (or merge the PR with its head SHA pinned, in the PR-required repos). A moved tip means rebase and check again.
  2. Deploy by the project's deploy.mode (§7): automatic on push, make deploy, or an agentic deploy — a Max Task whose done-definition is make verify passing on the target.
  3. Hold. make verify must pass, then the deploy must stay free of new signals for its hold window (30 minutes by default) before it counts as held.
  4. Roll back to the last held deploy if verify or the hold window fails, and mark the failed artifact bad so it is never shipped again. If the rollback itself fails, the project is paused and you get one card.
  5. Migrations are declared in project.yaml. Additive (expand/contract) migrations ship like code; a migration that drops data is a business decision whose default on expiry is do not proceed.

The factory ships itself differently#

The factory cannot deploy itself from inside its own loop. Its make deploy is a small script outside the loop: build a release, swap it in, wait for health and one synthetic Issue to round-trip, and swap back to the last held release if either fails. The loop only calls it and observes the result.

Waiting Tasks are rows, not running work: they hold no slot, and an urgent Task never queues behind them. When your own iu 5-hour window passes 85 %, normal and upkeep sessions running on iu are parked at their next idle point and resumed later.

Both accounts walled, production down: the deterministic parts still run — settle, restart, rollback, runbooks. Code waits for the first reset.

The prompt cache#

Two Max accounts are two organisations; a cache never crosses them.

  • The account is fixed at spawn and kept on resume while the cache is warm (under an hour since the last turn) or the wall lifts within the hour. After a longer wall the cache is cold anyway, and the Task goes back through the picker instead of waiting days for one account.
  • Witness records the account actually in effect, so a session that a herdr restart moved to the other account is accounted correctly.
  • Briefs are stable at the front, so the standing orders are cache hits on every spawn.

6. State

Postgres on the mini#

One database, factory, on the Postgres 18 that already runs on the mini (Homebrew, always on). Argo moves into the same server as database argo at W5, with its own role, a connection limit and a statement timeout, so a slow dashboard query cannot starve the loop.

Postgres over SQLite because Argo reads it directly (views, and LISTEN/NOTIFY for live updates — no sync job), because FOR UPDATE SKIP LOCKED, JSONB and full-text search cover the ready queue, raw payloads and "seen this before" without extra machinery, and because you have hit SQLite locking before.

A reconcile loop, and why not DBOS#

You suspected v1 used DBOS wrong. It did: the spike ran DBOS on SQLite with its default application version — a hash of the workflow source — so a one-line redeploy stranded every queued flow; pinned, it passed. Configured right, on Postgres, DBOS works.

v2 still does not adopt it, for a reason the spike did not test. The factory is a control plane: every step must re-read the world before acting (does the PR exist, is the container up, is the session alive). A reconcile loop does that natively. DBOS replays recorded step results instead, and the design review found five ways that bites here — a parallel fan-out whose replay order is not stable, any second process that launches DBOS stealing the daemon's in-flight work, recovery counters that dead-letter long-waiting work after enough self-deploys, message waits that consume stale messages, and the factory deploying itself through a workflow that its own deploy restarts. Each has a fix; a reconcile loop has none of them. It also keeps the factory on Bun — DBOS's TypeScript SDK supports Node only.

What the loop needs, Postgres provides: wake_at for timers, a SKIP LOCKED ready queue, facts plus NOTIFY for waits, an advisory lock for the single process, and (entity, generation, step) keys for effects. v1's spike measured this design — its option A, on SQLite — at 75 of 75 runs, crashes included.

W1 proves it on Postgres before anything depends on it: a kill mid-effect, a redeploy mid-settle, a second process starting, a restore into adopt mode. W2 extends the suite to its own effects: a kill mid-merge, two Tasks of one Issue with the factory killed between them, a late decision. Zero duplicate effects, zero lost Tasks.

Telemetry and money#

  • Traces (from W5): the factory, agent-gateway and headless Claude Code sessions export OpenTelemetry to the VPS ClickStack over the tailnet, one trace per Issue: trace_id sits on Issues, Tasks and sessions.
  • Usage: usage-tracker stays the record of tokens and cost. A session's id links its usage rows to its Task and Issue, so Argo shows cost per Issue and per project without a second copy.

Backups and restore#

From W1, not later: a nightly pg_dump to the homelab bucket and a weekly restore drill, both part of the infra job's first slice. A restored database is behind the world, so the factory starts in adopt mode: no effects until every open Issue and Task has re-read the world once.

Retention#

Facts stay. Agent transcripts and dead sessions are archived to the homelab and the local copies are kept; nothing is deleted. Warden's database is deleted at W1, as you said; the golden set already holds what was worth learning from it.

8. Dedup and learning

One cause should be one Issue, and a cause seen before should arrive with its fix. The deterministic part is proven (grouping F1 0.889 against warden's 0.744 on a held-out set); "seen before" is not (known-fix match 0.479). Every production platform we looked at gates grouping deterministically and keeps similarity and judgment beside the gate, not in it; none exports corrections as labels, so the learning loop is ours to build (research/2026-10-24-learned-correlation.md).

How a signal finds its Issue#

StepDecidesHow
Rulesmost signalsstateful sources (Kuma, Beszel, containers): one episode per subject until the source reads healthy again — polled, so a missed recovery is caught on the next read; stateless sources (CI, logs, GitHub issues): the same refined fingerprint within a window; topology joins a container's failure to its host's
Scorethe ambiguous rest: two open Issues on related subjects within 30 minutes, or a new Issue whose fingerprint or text matches a recent oneagent-gateway's decision model returns the probability that both share a cause. ≥ 0.8 merges, ≤ 0.2 keeps apart, anything between attaches them as possibly related for the investigator. A failed call keeps them apart; intake never waits on it
Investigatoreverything the cause explainsthe investigation merges or splits with a reason (factory issue merge|split). A merge stops the absorbed Issue's Tasks and sessions; a split starts the new Issue on its own

Seen before#

Each new Issue is matched against closed ones by fingerprint and by Postgres full-text search over title, root cause and fix recipe, ranked by project, subject and recency. The top matches, with their recipes, go into the investigator's brief. A closed Issue whose recipe is a runbook becomes a known fix: the next occurrence runs it before any investigation.

The label loop#

Every grouping decision — by a rule, the score, the investigator or you — is a row in issue_links with who and why. That gives three things at no extra cost:

  1. A split rate per rule. A rule whose groups are split more than 10 % of the time over two weeks is flagged as an upkeep Issue.
  2. Calibration. The score's two thresholds are re-checked monthly against the labels and the frozen golden set; a change is accepted only if grouping F1 stays at or above 0.889.
  3. Regressions. A signal matching an Issue closed in the last 30 days re-opens it as a regression, linked to the change that closed it.

Not built until measured need: embeddings and vector search. They come when full-text matching misses known fixes you can name, or the split rate says the rules are not enough.

9. Upkeep jobs

A job is a small TypeScript module, not an agent. Code does the looking; a model is called only when the code found something worth a sentence. Swamp's ideas, without its runtime: typed steps in code, assertions as first-class steps, nothing spent when everything is fine.

// factory/jobs/deps.ts
export default job({
  schedule: "0 6 * * 1",
  projects: (p) => p.jobs.includes("deps"),
  async run({ project, probe, summarize, open }) {
    const outdated = await probe.outdated(project);            // bun outdated --json, release ages
    const due = outdated.filter((d) => d.ageDays >= (d.major ? 14 : 3));
    if (due.length === 0) return;                               // green: zero tokens
    const notes = await probe.releaseNotes(due);                // changelogs + migration guides, cached
    const plan = await summarize("group-upgrades", { due, notes }); // one Haiku call
    await open({ kind: "upkeep", class: "upkeep", title: plan.title, plan });
  },
});

A job never edits a repo. Code changes become Tasks and go through the loop.

10. Surfaces

Where everything runs#

Intake#

The mini can reach the homelab and the VPS; they cannot reach the mini. So the factory polls — Kuma's monitor states, Beszel, Docker on the three hosts, HyperDX alerts and ClickHouse error clusters, GitHub issues and checks, RollHook deploys, failed launchd jobs, CrowdSec decisions, TickTick. Polling the current state also means a missed recovery is caught on the next read. The few sources that can only notify Slack arrive through a Slack adapter. Nothing listens on a public address.

FAQ

Can I still just use Claude Code in herdr? Yes. Your sessions are outside the loop unless you hand work to it, and the picker keeps choosing the account.

Both Max accounts are walled and production is down — then what? Settle, restart, rollback and runbooks still run; they need no model. Code waits for the first reset. No IU fallback, by your rule.

Why does review run on IU API tokens if IU must not write code? Review reads code and changes nothing. A reviewer with a DeepSeek adversary is a second pair of eyes from another model family.

Why not DBOS, if v1 used it wrong? Because the factory re-reads the world before every action anyway, and a reconcile loop does exactly that without replaying recorded results (§6).

What do I lose during the rewrite? Warden's triage, for the two days W1 takes. Raw alerts keep reaching Slack until each source's adapter lands.

What does it cost? No new subscription. IU API spend grows by ≈ $10–40 a week, mostly review. The rewrite itself costs ≈ 20–40 % of one iu week.

How do I steer something in flight? Argo intents (steer, pause, stop), a comment on its plan in Artifacts, Hermes, or factory issue|task from any shell.

What will I notice first? After W1, a container that stops comes back on its own, and you read one line about it in the morning instead of an alert in Slack.
