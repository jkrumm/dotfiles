1. Verdict

Rebuild warden as level-triggered reconcilers over one ledger, describe every repo in one manifest, take signals from their sources, and let verification — not the owner — gate every ship. Adopt no heavy runtime: beads, a workflow engine and Keep's model each lost a measured spike, and their designs are copied instead. The factory's real cost today is owner attention, not tokens: 577 owner-facing notifications and 50 "continue" nudges, against $2.60 of agent spend on the ten worst incidents.

The target in ten lines#

  1. One fresh ledger (ledger.db, history imported once from the archived warden.db, replicated continuously to the homelab bucket) with an append-only event log; eleven nouns, one writer each.
  2. One project.yaml per repo; the per-repo AGENTS.md block, herdr groups, Argo's registry and reconciler policies are generated from it, and tool routing renders once into a global rules file.
  3. Signals from their primary sources with source time; Slack intake stops at W1a and the adapters replace it from W3a.
  4. Per-project reconcilers open and close Conditions; a webhook only schedules a reconcile.
  5. A correlator folds conditions by fingerprint, topology and time window into one incident per cause; closed incidents with a recipe are the known-error store.
  6. Tasks live in the ledger with a blocker-aware ready queue; mothers (six fleet projects) and sessions (everything else) work them through one spawner, rd.
  7. Every agent runs in herdr; engine by class — your own sessions and waves on Claude Code/Max, routine work and factory judgment (mother wakes) on OpenCode/IU, with Max used for factory work only where its capacity would lapse; the quota guard is a scheduler input; Witness resumes parked agents.
  8. A verification ladder per action class authorises auto-ship; absent evidence fails closed to propose-only; rollback redeploys the last held Deployment and squash merges keep the git revert mechanical; a breaker counted per lineage stops runaway loops without paging anyone.
  9. The owner decides four things only — product direction, spend, irreversible data loss, other people — each as a card with a default and an expiry; SLO: under 1 % of items reach him, stretch 0.1 %.
  10. Argo answers his 27 canonical questions, the brief's 3 and one about his own requests from live read models on the mini; the VPS keeps the life pages and the off-site dead-man's switch.

3. Invariants (each one a CI check or a ledger constraint)#

  1. One writer per entity table: write functions live in one module per noun; a CI check rejects writes from anywhere else. Adapters write Signals only.
  2. Every state change emits its event in the same transaction (transactional outbox).
  3. Conditions close only on an observation.
  4. An Incident closes only after a pass Verification linked to it.
  5. A Decision with decider owner exists only for product direction, spend, irreversible data loss or other people, and always has a default and an expiry. Pause is not a Decision.
  6. A worker Agent has a hook before it runs; one live worker Agent per Task, fenced by its lease epoch (ADR-002): a stale epoch is rejected on every ledger call, push and merge, and rd fails closed for any spawn that carries a task_id (ADR-007 §3); one writer per checkout.
  7. Every merge the factory makes goes through the train and only when its action class's verification ladder is satisfied. A merge outside the train (the owner's direct push) is never gated; the ref adapter records it and it counts in regression and change-failure accounting.
  8. Every pure read model is a fold over the event log. Every loop decision is itself an event carrying its outcome and reason (§4), so a rebuild replays decisions and never re-evaluates policy against a manifest, rule or calibration that has since changed. A read model with no event source is a live probe: labelled so in design/argo.md, rendered with as_of, never feeding a KPI or a control input. Effectors send through deliveries(event_id, channel) (ADR-011): an accepted delivery is never re-sent, a decision or heads-up push is retried until accepted, and an effector skips events with actor import.
  9. Every event carries correlation = its lineage root; emit() enforces it, and planner, spawner and decide inherit it. The root is an Incident, or the Task an owner brief or the planner created — or, until correlated, the Signal itself (correlation = the signal id). Attaching a Signal emits incident.member_added, which records the merge of roots; nothing already written is rewritten. The autonomy KPI counts per root, and items count only Incident and Task roots, so a Signal root is never an item (evidence/DEFINITIONS.md).

1. Reconcile — desired vs observed, level-triggered#

A reconciler is a pure function reconcile(project, observed) → condition updates, run per project on a resync timer and whenever a Signal for that project arrives. Signals never open work directly; they only schedule a reconcile (Kubernetes' controller pattern). Running it twice gives the same result; it holds no memory between runs.

  • Desired state = the manifest runtime minus in-flight Deployments and declared maintenance. A deploy path (make deploy, RollHook, WUD) announces itself with a started Signal before it stops anything; the deploy reconciler (the only Deployment writer, model.md §1) turns started, deployed and failed into Deployment transitions, so the in-flight window the health reconciler subtracts is derived, not declared, and a deploy draining replicas or a deliberate stop is not a fault. A container replaced with no started Signal is an unplanned Deployment, recorded from Docker events — not a fault to restart. The health reconciler reads container-level state (docker ps / inspect) on every resync; Docker events only wake it. Restarts call spec.commands.restart.
  • availability: intermittent runtime targets (the MacBook): output-age conditions replace liveness heartbeats (a vault backup older than its policy opens infra.backup); no investigation runs while the host is known asleep (#5, a 4.5-day missing heartbeat, evidence/incidents/incidents.md).
  • Kuma group monitors are topology parents. Their state derives from their children (22 of the 120 monitors; two parents sat red for 59.2 h as derived state, evidence/incidents/incidents.md #4), so they never open a Condition of their own and never hold a recipe; the drift check (warden manifest check) maps each group to its children.

2. Correlate — one cause, one incident#

Stateless sources (CI failures, log lines, issues, chat): the same refined fingerprint inside w_dedup, also while an incident is open; a later occurrence starts a new candidate. The Condition key includes the fingerprint class (model.md §1), so two causes on one subject are two Conditions, each a member that close-by-member and split can act on.

  1. Close by member: an incident closes only when every member's own Condition has resolved. Split: when every other member has resolved and one is still open after its type's hold, it splits into a new incident and its timeline carries over. Members with no condition type — chat, requests, issues, log lines below an alert rule — have no Condition to hold an incident open, so they join an incident only by an explicit, reversible edge (the investigator's, a known-error match or a shared deploy suspect).
  2. Act per incident: while a topology ancestor has an open host condition (boot, mount, reachability), child recipes are held for the host's hold window, and they stay held until the host answers a direct reachability check and its mounts are present; the host runbook runs first.
  3. Candidate gate (Keep's promotion): a candidate becomes an incident when it persists ≥ T, or reaches N signals, or matches a known error, or its severity is critical; otherwise it expires as noise, recorded and scored.
  4. Known errors: a closed incident with a recipe (root cause, fixing change, action class, verification evidence); the fixing Change is attached at closure, never inferred from notes. The judgment calls — root cause, recipe choice, decision_class — belong to the investigate worker on OpenCode/IU; no single-shot decision model sits anywhere in this loop (ADR-003).

Exception-first: when nothing is wrong, each surface says so in one line and stops. The shell never changes shape (rail, ambient status, one attention queue, detail on selection); the content does.

Freshness. Every read model returns as_of and its expected cadence. A source older than its cadence renders as a stale term in place of its value (quota stale since hh:mm, not a frozen Max 46 %); "all up" needs every health source fresh, so a dead collector can never produce it.

One slot per entity. Each entity renders in exactly one Home slot, picked by precedence decision > broken > parked > in flight: a stuck agent whose agent.stuck condition sits in an open incident shows with that incident, not again under Parked/stuck. Fixed alone is a count with a drill-down, never a list on Home. Parked/stuck holds only agents whose resume failed or is blocked; an agent waiting on a scheduled resume is the factory handling it, so it is a count on line 1 and a row in Fleet. Broken holds production incidents past their budget (ADR-012); an incident inside its budget or on a non-production project is an In flight row.

Home adapts to the situation, decided by a pure function of the read models. Situations stack in table order, so a decision during an incident has exactly one layout; quiet is the absence of the rest: | Situation | Trigger | Home shows, in this order | |-|-|-| | decision | a business Decision is open | the card with options, default and expiry, above everything else | | incident | a production incident past its budget | the incident card: cause, suspects, what automation did, what runs now, ETA | | many in flight | more than 5 agents working | the fleet matrix (ambient status per agent) replaces In flight rows | | quiet | none of the above, no failed or blocked resume, no open Condition on a paused project, every health source fresh | the status line, In flight rows, Since you left, the Fixed alone count — no card, no exception slot |

A scheduled resume does not leave quiet, and neither does an incident inside its budget. The degraded factory — breaker open, quota guard tripped, mini unreachable — is no situation and no banner: the shell never changes shape, so it is an ambient term on line 1, and its drill-down names what still runs.

4. Holdout scenarios#

Per fleet project (basalt-ui, argo, weatherorb, shutterflow, dotfiles, warden): end-to-end user stories stored in a private holdouts repository that is never cloned into an agent-writable checkout; the verifier runs them against the deployed app after every deploy and scores observed behaviour (HTTP responses, rendered pages, CLI outputs). Workers see only pass/fail and the failing story's title, never the scenario text. CI check: no worker transcript contains a holdout path. Mothers draft each set (D4). A set binds on measurement, not on a date: it passes against the current production release, and each scenario has been seen to fail against a seeded fault — the evidence-producer rule below, applied per scenario. The owner may edit a set at any time; no timer runs on it. Binding gates only that project's switch from propose-only to auto-ship — W5's gate runs on drafted sets and records the date each binds.

  • Update path: a holdout changes only through a Change to the holdouts repo, authored by a verifier-role agent that sees the approved plan Artifact, never the product diff, or by the owner, who may edit at any time; each Verification record stores the holdouts sha that gated its deploy.
  • Absent evidence fails closed: warden manifest check computes effective autonomy per (project, action class); a rung whose evidence has no producer (no probe, no deployed app, no holdouts) drops to propose-only and files the gap as a factory Task; it flips back when the producer exists. A producer counts only after the verifier has watched it fail: a fault injected in a canary or scratch window turns it red, recorded as a Verification.
  • Substitute producers where no deployed app can exist: a library — consumer-build holdouts (argo and weatherorb built and tested against the candidate basalt-ui); infra — a dry run plus a plan diff; tooling without a runtime (dotfiles) — the test suite plus a canary run; warden — factory-self. A propose-only PR whose gap stays open closes after 14 days with its Task kept; the owner never merges it.
  • factory-self: changes to the ship path, verifier, holdout runner, breaker and rollback, and Changes that add, remove or weaken an evidence producer (probes, monitors, verify commands, rollback references), are verified by the previous release — N-1 is a CI job that runs the previous release's verifier and holdout suite against the Change, with no second installed release. A small independent watchdog rolls warden back to its last held release, because a bad warden deploy cannot be trusted to roll itself back. factory-self releases migrate the ledger by expand/contract steps only and the ledger carries a schema stamp: the watchdog restores the last held release only if it supports the current stamp, otherwise it stops automation and sends a heads-up (gameday row 21).

Tradeoffs the panel accepted#

  • One digest, three renderings (Home, briefing, per-project changelog).

  • New CLIs and services follow the agent-CLI contract (ADR-004) from their first commit.

11. FAQ

Why not just adopt beads, a workflow engine, or Keep? Each was measured on our data. beads v1.3.1 leaves cross-repo dependencies unenforced (0 of 9), fixes its lease at 5 minutes, and touches work repos even in contributor mode (spike 1). DBOS on SQLite survived every kill but strands flows on a redeploy and adds a second system of record (spike 2). Keep's model — fingerprint fields plus attribute rules, no topology — scored F1 0.737 on the held-out golden set, no better than leaving every event alone (0.740), against 0.889 for the proposed correlator's v1 rules (spike 3). What each does well is copied: bd's verbs and ready semantics, durable primitives, Keep's candidate gate.

Why not Mastra? It was not run, and ADR-002 records why: it is TypeScript-only, the research could not verify its durability, suspend/resume and timeout semantics, and it would add a TS runtime and a second system of record beside a Python loop.

What happened to the decision models? There is no single-shot decision model in the loop. Yours become the investigate worker on OpenCode/IU, making the judgment calls — which recipe, which decision_class (ADR-003). Measured as a single shot, the decision model agreed 92 % with warden's LLM triage but only 60 % with the true grouping (kpi/decision_shadow); deterministic rules group, the worker judges.

Is this a rewrite of warden? Yes — rewrite and cutover, no co-running. The old loop stops when W1a starts and its database is archived read-only; history enters a fresh ledger by one import. Each rewritten piece goes live when it passes its own proof gate (backtest, gamedays, holdouts, the timed Argo test). Only the build lane, your apps and their data, and the archived stores stay up throughout. The legacy loop is a way back only until the new ledger performs its first external effect, a moment the ledger records; after that a failure is fixed forward in the new ledger, never by restarting the old loop (waves.md W1a, Rollback).

Why mothers at all, and why only six? A mother pays for itself where planned work arrives continuously; the rule (≥ 10 planned units and ≥ 25 commits a week over 90 days) picks basalt-ui, argo, weatherorb, shutterflow, dotfiles and warden. Everywhere else a session per task is cheaper and enough. Scheduling stays in code; mothers spend tokens only on judgment.

Will the factory eat my Max quota? Not by design, and it will not waste it either. Max demand is already 120 % (109–144) of a weekly window per week before any factory judgment (kpi/forecast), so routine work and mother wakes run on IU. The guard projects your burn for the rest of the cycle (p90 rate × hours to the reset) and, when that projection reaches 100 %, parks work in a fixed order — improve, fleet, then your unattended waves, which continue on IU with a Claude-class model; your interactive sessions and the waves you attend are never victims (ADR-008). Resumes go through the admission queue at the forecast's token rate, never in a burst. The inverse rule spends capacity that would lapse, late in light cycles: 3 of 7 cycles peaked at 55–79 %. Measured as owner interactive sessions blocked per cycle (target 0) and Max lapsed % (today p50 4 %, p90 30.6 %, kpi/forecast); the IU price of the spillover is D2.

What still needs me? Product direction, spend, irreversible data loss, other people — as a card with options, a default and an expiry. Today 6 of 156 decision-relevant events in the golden set were genuinely yours; the SLO is under 1 % of items, the stretch 0.1 %. Product direction is found by structure, not opinion: a change to a declared product surface whose lineage holds no event from you — a brief you submitted, or a comment or resolve on the plan — becomes a card with a reversible default. Besides cards there is one present-human ask when a credential needs your fingerprint: one per expiry, scheduled 7 days ahead and coalesced, at most 2 a month, counted outside the SLO.

What happens when the mini is down? Argo's VPS half says "mini unreachable since hh:mm"; the VPS dead-man's switch pushes to the phone after 15 minutes. Kuma cannot do it — it shares the mini's house and power. That is the only push sent while the mini is dark: decision and heads-up pushes originate on the mini, so open decisions wait with their expiries extended by the downtime (gameday row 13, design/proof.md §2).

Why did every previous model drift, and why would this one hold? Prose claims held 1 of 11; claims that code runs held 7 of 7. Here every invariant is a capability limit with a test, a CI check or a generated file — or it is labelled target. The doc-contradiction lint and the generated blocks and routing file make drift fail CI instead of failing silently.

Can I still open a herdr tab and just work? Yes. The manual Claude Code + herdr lane is a rule of every wave, and rd wave keeps working after each one.

Does Slack go away? As an intake, at once — it stops with the old warden (W1a) and the primary-source adapters replace it (W3a). As a human channel it stays until Argo's notifications (W6), Hermes' briefings (W11) and the per-project changelogs (W13) replace what is posted there.

What does Hermes become? The conversational door: it answers from the factory's read models, files briefs as Tasks, steers agents and asks rd for sessions — through the same verbs as Argo. It loses every code tool: a capability limit with a test (a code-tool call is refused), proven at W11 by replaying the last 30 days of your requests to Hermes through the new Hermes — zero file, code or commit tool calls. Its briefings are generated from the event log — the Home digest plus one push with an audio link — and the daily "Project narratives" cron that posts to Slack retires into per-project changelogs in the brain (W11, W13).

MCP or CLIs? CLIs, on one agent contract (ADR-004). Spike 4's only systematic CLI failure — headless polling on a long job, 95k tokens — was fixed by one policy sentence (2 calls, 38.9k tokens). That behaviour now lives in the CLI: --wait blocks to a budget the harness sets and exits pending with the exact resume command, so the sentence is gone. Commands are defined once in code; help, docs, skill references and the global routing rules file are generated and drift-checked. MCP stays only for research-gateway (Claude Desktop) and chrome-devtools until a browser CLI exists.

How do we know the design works before building it? A golden set of 959 labelled events with pre-registered thresholds, a backtest that never tuned on its held-out half (v1's numbers — the revised rules are accepted by W3b's frozen-output regression and blind replay), a baseline gameday against today's system, and KPI scripts the loop cannot edit (section 7).

How long does the rewrite take? Fourteen waves in three lanes on a serial warden spine, ≈ 26 working days of wave time at the planned rate, re-planned from W1a's measured rate (waves.md Calendar); W1 to W4 each split in two, W1–W3 are fully specified, and W1a and W2a can start now. Raw alerts reach your Slack channel on days 1–8; from day 5 warden status --json and a stub page show the factory; verified shipping returns with W5 (day 14) for restarts and producer-backed config, and for fleet code fixes project by project as their holdouts bind on measurement; full autonomous operation follows W10 (day 26) once its gate passes — section 1b, During the rewrite.
