1. Verdict

Build a factory that runs the lifecycle of every piece of work and lets Claude Code do the work. The factory (plain code, with cheap models for routine judgment) takes in signals and requests, merges duplicates, heals what a runbook can heal, and queues the rest. It then starts a Claude Code session on the right Max account with the problem and its evidence. That session, the lead, owns the Issue from root cause to a verified production change and reports back; the factory watches the result, closes the Issue and learns. It runs as one new factory service on the mini over Postgres, with Argo as the cockpit on the same box. Warden is switched off, not migrated.

The scarce resources are your attention and the Max windows, not money. In v1's 14-day sample, 32 % of new items reached you, at ≈ 62 notifications a week, and only 3.8 % of those escalations were genuinely yours. IU API spend for all personal gateway work was $183 last week, most of it review.

The target in ten points#

  1. One lifecycle for all work. Incidents, bugs, upkeep findings and your requests are Issues; an initiative is an Issue whose waves are child Issues. Nothing has a side door.
  2. Claude Code owns the work, end to end. A lead finds the root cause, plans, builds (alone or with workers), tests, reviews, ships, checks production and reports. It decides how.
  3. The factory owns the lifecycle, never the reasoning. Intake, dedup by symptom, settle, classify, queue, capacity, watch, learn. Every repo under ~/SourceRoot takes requests; a project.yaml adds automation, and one make contract makes the same commands work everywhere.
  4. The brief is the problem, not a diagnosis. Facts, evidence and verified history; no cheap-model root cause or plan for the lead to unlearn.
  5. Cheap models do the routine around it, freely: dedup judging, classification, wording, the changelog, learning write-ups, job summaries, and the review and research tools leads call.
  6. Two Max accounts, one pool, 5-hour aware. Each lead gets a model and effort sized to its Issue and an account with headroom for it. Urgent work takes any headroom, upkeep only what would lapse. Nothing spills to IU API tokens.
  7. Two layers of agents: an orchestrator over the leads. The orchestrator plans initiatives into waves, steers stuck leads and watches queue and accounts, in short sessions woken per event. It never writes code.
  8. Done means production evidence. The lead ships only with the evidence its change needs, fixes forward when production disagrees. After the hold, the factory runs make verify and the project's journey probes, which no lead edits within its own Issue.
  9. It learns, and turns learning into code. Grouping decisions become labels; verified causes become known fixes; a fix verified twice becomes a runbook or a job check that code runs from then on.
  10. You decide business only: product direction, spend, irreversible data loss, other people. Each decision arrives as a three-line card with a default and an expiry. SLO: nothing else reaches you.

3. Principles

Eight rules. A design choice that breaks one is wrong.

  1. The factory runs the lifecycle; Claude Code does the thinking. What a script can decide, a script decides. Routine words and routine judgments (is this the same symptom, which project, how big) go to cheap models. Anything that needs understanding a problem or code goes to a lead.
  2. Max reasons about code, IU API tokens do the routine. Claude Code on the iu and me Max accounts is the only thing that diagnoses or changes a repo, and it runs in herdr, where you can watch it. IU API tokens pay for gateways, OpenCode, Hermes and the tools leads call. A full Max pool means waiting, never spilling.
  3. Hand over the problem, not a conclusion. A brief holds facts, evidence and verified history. A weaker model's guess at the cause is noise a stronger model has to unlearn.
  4. One lifecycle, no side doors. Every piece of work enters as an Issue and leaves with evidence or a stated reason.
  5. Facts are stored, state is derived. The database holds what happened: signals, phases, evidence, decisions, session observations. "Working", "stuck", "waiting" are computed from facts when read, so they cannot drift.
  6. Done means observed in production. A lead saying "done" is a claim; the evidence and the factory's own make verify after the hold are the proof. Wrong in production means fix forward.
  7. A self-improving platform, as code. Agents find the fix; once a fix is verified twice, it becomes a runbook or a job check that code runs from then on. Every rule, runbook, probe, policy threshold and prompt lives in a repo, and changes only through an Issue a lead ships with evidence. That includes the factory's own code: a scorecard measure off target for two weeks becomes an Issue in the factory repo. The factory gets cheaper and better as it learns.
  8. You decide business, nothing else. Product direction, spend, irreversible data loss, other people. Anything else that reaches you is a defect. Everything written for you is short, verdict-first and free of internal names.

Fixed boundaries#

  • Security is the tailnet plus your GitHub user. The factory opens no public endpoint. Sources it cannot reach directly are polled, or arrive through the Slack adapter. On GitHub, only your user's factory label or /factory comment starts work.
  • No caps on a lead's work. No turn limits, no wall-clock ceilings; the one liveness rule is the stall rule (§5), and the orchestrator handles a lead that stops making progress.
  • AGENTS.md only. No CLAUDE.md in any repo.

4. The loop

The factory runs the lifecycle; Claude Code does the work. The factory takes everything in, merges duplicates, heals what a runbook can heal, and queues the rest. When capacity allows, it starts a Claude Code session in herdr, the lead, with the problem and its evidence. The lead owns the Issue: it finds the cause, plans, builds, tests, reviews, ships, checks production and reports back. The factory then watches the result, closes the Issue and learns from it.

Three ways in#

  • Signals from sources and jobs become incident, bug or upkeep Issues after dedup.
  • Requests go straight to Classify, with no dedup or settle: Argo, Hermes, factory issue new, a TickTick item tagged #factory, a GitHub issue in one of your repos labelled factory, or any issue where you comment /factory. A label, not authorship, starts work, because every agent on the mini acts as your GitHub user; an issue labelled alert (weatherorb's alerts) is a signal. The factory never triggers on its own comments, and a source it cannot parse triggers nothing.
  • Initiatives: a request too big for one lead is classified initiative and wakes the orchestrator, which plans it into waves: child Issues with their dependencies.

Every repo under ~/SourceRoot takes requests, with or without a project.yaml; the manifest adds signals, runbooks, the hold and probes (§7). IuRoot stays outside. So do the herdr sessions you start yourself: Hermes files a request when you ask it to do something, and opens a plain session (rd work) only when you ask for a session.

Done means evidence#

The factory derives the evidence an Issue needs from what its merged commits touched (§7's deploy and ship), so a lead cannot pick a lighter bar: ship is refused without that evidence, and close is refused when the commits touch deployable paths. The factory checks that the evidence is there and fresh: a screenshot newer than the deploy, a deployed version from make verify that contains the merged commit. No lead edits a probe within the Issue it is shipping. Each deployable project lists a few user-journey probes in project.yaml: can I log in, does the forecast load, does the upload finish. Tests a model wrote for its own change can give false confidence, and the probes are the check that does not depend on it.

The brief: the problem, never a diagnosis#

A lead reasons better from facts than from a weaker model's guess, so the brief carries no cheap-model root cause and no cheap-model plan.

  • The ask: your words, or what the signals saw: what, where, since when, how often.
  • Facts: the raw signals, the commands that pull their logs and traces, the project's last deploys and commits. Alert and issue text is marked as data, never instructions.
  • History: closed Issues that looked similar, with the cause and fix their lead verified, marked past, may not apply.
  • The project: its make contract, deploy mode, how each path ships, production targets.
  • Done means: the evidence table above and the factory verbs.
  • Standing orders: decide alone except the four business classes; ask through factory issue ask; no turn or time limits; workers stay on Max.

Classification sets labels (project, kind, class, size) and routing (account, model, effort), never a cause; of its output, the brief shows just kind and class. The standing orders are identical in every brief, so they are a prompt-cache hit.

Following a running lead#

  • Turn ends are events, not guesses. The lead's Stop hook reports every turn end and its SessionEnd hook the session's end, straight into the Issue's inbox. engrams learned that inferring turn ends from output wedges sessions. Witness reads herdr every minute as the backstop (blocked, walled, dead) and records the account in effect. The lead's factory reports are authoritative, and the server validates each one against its schema.
  • The hooks act only in factory sessions and never block one. The launcher sets FACTORY_SESSION; without it every hook exits at once, so your own sessions and the build's never see them. When the factory does not answer, a hook or a factory issue call appends its event to a local spool, which the factory replays on start; the idempotency keys make the replay safe.
  • A Stop hook keeps the lead honest, and only then. It sends the lead back with one line (report ship, close, block, ask or wait) when all three hold: nothing reported since the last prompt, no declared wait, and the turn did not end on a usage limit. factory issue wait --on workers|deploy|owner is the report for a lead whose rd fan worktrees or deploy are still running. A turn that answers a message you typed is never sent back. Claude Code continues a session when a Stop hook exits with code 2, and stop_hook_active stops it looping. A second unreported stop parks the Issue with a line for you, never a card.
  • New facts go to the running lead. A signal linked as possibly related to an Issue in work (by the rules, and by the judge once trusted) reaches that lead as a note, not a second session. The lead records whether it shares the cause; that answer is the judge's label (§8).
  • Notes go through the factory. The factory and the orchestrator write to a lead only with factory issue note, which records each note under its prompt id and types it once. The factory alone owns lead-* panes: herdr-reap skips them, and the stall rule (§5) replaces any idle watchdog.
  • You can step in at any time: open the lead's tab and type. The lead treats your message like a note, and the factory keeps following.
  • Walls: Witness marks a walled lead and resumes it when its window resets. If the wait would pass an hour and the other account has headroom, the lead resumes there by session id instead (§5); the prompt cache is gone after such a wait either way.
  • After ship the lead stays open and idle through the 30-minute hold, so a regression reaches it while its context is warm. Once the hold has passed and make verify and the probes are green, the factory closes the tab and removes the worktree.

Two layers: the orchestrator and the leads#

Under the factory's code run two kinds of agent. Warp's factories make the same split, a foreman over workers and one level deep: "A child runs its own work and reports back; it does not spawn its own children" (research/2026-10-25-warp-factories.md).

  • The factory is not a layer. It is the conveyor: it queues, admits, spawns, follows and closes, in code. The orchestrator decides and the factory executes. Queue order, first rule first: stop the line, urgent, dependencies, the orchestrator's priority within a class (factory issue prio|dep, with a reason), age.
  • A lead's helpers are not a layer either. Subagents, rd fan worktrees or a /wave chain are tools the lead picks; the factory sees only the lead's reports, such as wait --on workers.
  • No orchestrator session lives long. Each wake starts fresh from factory status, the initiative's plan in docs/waves/ and the event, and ends when its decision is recorded. The event is the boundary, so nothing compacts and a crash costs one wake.
  • An initiative is the orchestrated /wave mode you use today, with the factory doing the spawning: the orchestrator writes the plan in the project's directory and opens the waves as child Issues; each wave is an Issue with its own lead; when a wave ships, the orchestrator reads the result and adjusts the waves still ahead.
  • It reaches leads through the factory: it reads a lead's pane and leaves notes with factory issue note. It never writes code, touches a repo or starts work the queue does not hold.

What you see of an Issue#

Parked is waiting with a reason; a stopped Issue is closed as dropped; pausing is a flag on the project, not a state. A lead that makes no progress does not wait for you either: the orchestrator steers it, gives it a stronger model, splits the Issue, or parks it with a line for you (§5).

6. State and durable execution

Postgres on the mini#

One database, factory, on the Postgres 18 that already runs on the mini. Argo moves into the same server as database argo at W5, with its own role and connection limit. Postgres because Argo reads it directly (views, LISTEN/NOTIFY for live updates, no sync job), because JSONB, full-text search and SKIP LOCKED come built in, and because you have hit SQLite locking before.

Durable execution: no DBOS#

Decided (you left it to me on 25 October): no DBOS. Each Issue is a state machine in Postgres, driven by an inbox. The reason is Cortex's engrams, an open-source software factory that runs Claude Code on DBOS on Bun. Its blog argues for durable workflows; its code and ADRs argue the other way for exactly our case (research/2026-10-25-engrams-source.md):

Cortex's blogengrams' code and ADRs
"A software factory is just a durable workflow"ADR 0119: "an entity lifecycle that spans days … must NOT be one long-lived run … The automation is stateful; no run is."
DBOS runs the factorythree workflows, using DBOS only for step checkpoints, send/recv and idempotent workflow ids; cron (croner + a Postgres lease), concurrency claims, retries and recovery are their own code
"every run resumes where it was"DBOS ties recovery to an application version hashed from workflow source, and deploys stranded production runs (253 unread messages, 15 orphaned runs). The fix is a ≈ 2,000-line sweeper (ADR 0104); pinning the version was rejected because it forces patch bookkeeping

An Issue lives for hours or days, so engrams' own rule applies: the Issue is stateful, and no run is. What DBOS would add on top is checkpointing for steps that last seconds, which a deterministic id does as well, and the price is version gating on every deploy. On one Mac mini there is no multi-pod recovery to buy. v2.1's instinct (short runs, state in tables) was right; engrams arrived at the same place the hard way.

  • One writer. issues.state changes in one module, a transition table over the states in §4.
  • One inbox. Everything that concerns an Issue is a row in issue_inbox with a mandatory, unique idempotency key:

  • One Issue at a time. A worker takes an Issue's oldest unhandled rows under a row lock (FOR UPDATE SKIP LOCKED), so two events for one Issue never race. LISTEN/NOTIFY wakes it at once, and a tick every few seconds catches the rest.
  • Effects are attach-or-start by deterministic id. The lead's herdr name is lead-<issue>-<attempt>, and spawning again attaches to that pane. A prompt id (issue:<id>:<phase>:<n>) is recorded before anything is typed into a pane. A GitHub comment carries a marker, a card a key. A replayed tick never spawns, prompts or posts twice.
  • Claims (engrams' concurrency table, without its policies): repo:<name> admits as many leads as the repo's leads allows (one by default), plus one urgent (§5); everything else queues in order. A repeat of the same symptom is a note to the running lead (§4), not a policy.
  • Finalize once, from every exit path: terminal state, release the claim, remove the worktree, promote the next queued Issue.
  • Every start reconciles. Before any effect, each open Issue looks at the world once (herdr, its worktree, GitHub, the sources), and the spool is replayed. There is no separate adopt mode.
  • Ids survive a restore. After a restore the Issue sequence moves past every id seen in pane names and the spool, so a new Issue never attaches to a running lead's pane. A lead reporting an Issue the dump lost gets that Issue rebuilt from the spool, or parked.
  • Schedules: croner plus a Postgres lease; job_runs is unique per (job, slot), and a missed slot runs once after downtime.
  • Tests, from engrams without its engine: a golden test pins each path's sequence of transitions and effects; a replay test crashes after every effect and replays, and must end with zero duplicates.

What would change my mind: the lifecycle module passing ≈ 500 lines, or the replay test finding a race the per-Issue lock cannot close. Then DBOS in engrams' short-run form, sweeper included. The runtime decides nothing either way: Cortex runs DBOS on Bun 1.4.3, and the factory stays on Bun.

8. Dedup and learning

One cause should be one Issue, and a cause seen before should arrive with its verified fix. The deterministic part is proven: grouping F1 is 0.889 against warden's 0.744 on a held-out set. "Seen before" is not proven: v1's known-fix match scored 0.479. Every production platform we looked at gates grouping deterministically and keeps similarity and judgment beside the gate, not in it. None exports corrections as labels, so the learning loop is ours to build (research/2026-10-24-learned-correlation.md).

Two tiers: symptom at intake, cause in the lead#

Your comment named the catch: true dedup needs the root cause, and the root cause needs a smart model. So dedup happens twice:

Intake only has to catch the obvious repeats: the same monitor flapping, the same error fingerprint in a window. Two Issues that look different but share a cause are the lead's catch. A lead running in a project receives possibly related signals as notes (§4), so a second lead never starts on the same cause. A merge tells the absorbed Issue's lead, if one is running, to push its work in progress to a branch and drop its Issue as merged; its notes go to the surviving lead.

Seen before#

Each new Issue is matched against closed ones by fingerprint and by Postgres full-text search over title, the lead's root cause and fix, ranked by project, subject and recency. The top matches go into the lead's brief as history, marked past, may not apply (§4).

The learning loop#

Every grouping decision (by a rule, the judge, a lead or you) is a row in issue_links with who and why. Every closed Issue carries the lead's verified cause and fix. From those, the learn step (a cheap model) maintains four things:

  1. Labels. Lead merges are ground truth for what intake missed; lead splits are ground truth for what it wrongly joined. A rule whose groups are split more than 10 % of the time over two weeks becomes an upkeep Issue.
  2. Known fixes. Cause and fix per closed Issue, searchable as "seen before".
  3. Runbooks. A fix verified twice for the same cause and subject (a restart, a cache purge, a rerun) becomes an upkeep Issue: "add this as a runbook". A lead adds it to the project's heal: list through review, and from then on code runs it before any lead is spawned.
  4. Thresholds. The judge's 0.8 and 0.2 change only through an upkeep Issue that replays the labels and the frozen golden set; a change is accepted only if F1 stays at or above 0.889.

Whether it actually learns is measured, not hoped. You are right that this is the tricky part. The scorecard (§9) tracks, per month, beside the judge's own precision and recall:

  • the missed-at-intake rate (lead merges per 100 Issues)
  • the wrong-join rate (lead splits)
  • the seen-before hit rate (a lead confirms the suggested past cause)
  • the runbook share (incidents closed by a runbook, without a lead)

If none of the four improves over two months, the orchestrator opens an Issue that says so.

Not built until measured need: embeddings and vector search. They come when full-text matching misses known fixes you can name, or the split rate says the rules are not enough.

9. Upkeep jobs

A job is a small TypeScript module, not an agent. Code does the looking; a cheap model writes up and groups what it found; a lead does whatever needs understanding. Swamp's ideas, without its runtime: typed steps in code, assertions as first-class steps, nothing spent when everything is fine. Jobs are also where the factory grows more deterministic: a check a lead keeps doing by hand becomes a job assertion.

// factory/jobs/deps.ts
export default job({
  schedule: "0 6 * * 1",
  projects: (p) => p.jobs.includes("deps"),
  async run({ project, probe, summarize, open }) {
    const outdated = await probe.outdated(project);            // bun outdated --json, release ages
    const due = outdated.filter((d) => d.ageDays >= (d.major ? 14 : 3));
    if (due.length === 0) return;                               // green: zero tokens
    const notes = await probe.releaseNotes(due);                // changelogs + migration guides, cached
    const groups = await summarize("group-upgrades", { due, notes }); // one cheap call: grouping, not a plan
    for (const g of groups) await open({ kind: "upkeep", title: g.title, evidence: g }); // a lead plans it
  },
});

FAQ

Can I still just use Claude Code in herdr? Yes. Your sessions are outside the loop unless you hand work to it, and the picker keeps choosing the account.

Can I hand work in the brain or my website to the factory? Yes. Every repo under ~/SourceRoot takes requests without a project.yaml: one lead per request, one at a time, no orchestrator. A manifest adds signals, the hold, probes and more leads at once (§7).

Both Max accounts are walled and production is down — then what? Settle and runbooks still run; they need no model. Leads wait for the first reset: usually a 5-hour one, the weekly one when a week is spent. No IU fallback, by your rule.

Why does review run on IU API tokens if IU must not reason about code? The lead calls it as a tool and weighs the findings; the review decides nothing. A reviewer from another model family sees what the lead's own family misses.

DBOS or not? No (§6); you left it to me. Cortex's engrams runs a Claude Code factory on DBOS, and its own ADR says a lifecycle that spans days must not be one long-lived run; DBOS's version gating stranded their runs in production. We take engrams' patterns (an inbox per Issue, deterministic ids, claims, replay tests) and leave the engine.

What do I lose during the rewrite? Warden's triage, from W1a. Raw alerts keep reaching Slack until each source's adapter lands, Kuma's in W2; job failures go to Slack until W4 (§2).

What does it cost? No new subscription. Cheap models are used freely within your €500; review is the line to watch, and depth gating keeps it in bounds. The rewrite costs ≈ 20–40 % of one iu week.

How do I steer something in flight? Type into the lead's tab in herdr, or use Argo intents (steer, pause, stop), a comment on its plan (in plannotator until W5, in Artifacts after), Hermes, or factory issue from any shell.

What will I notice first? After W1b, a one-line request becomes a shipped change with a production screenshot and a three-line summary, without you touching it. After W2, a container that stops comes back on its own, and you read one line about it in the morning instead of an alert in Slack.

Why two layers and not three? There are two: the orchestrator decides (initiatives into waves, stuck leads, priorities, the accounts) and the leads do the work end to end (§4). The factory is code, not an agent, and a lead's subagents or rd fan worktrees are its own tools. v2.2's mothers and the steward are both the orchestrator now. It runs as short sessions, one per event, so its context never rots. Building the factory is different: it touches nearly every repo, so until W3 a build orchestrator runs over one wave orchestrator per wave, the orchestrator of orchestrators you meant (§12).

Why herdr, and not the Agent SDK or claude -p? Every Claude Code session the factory starts is an ordinary interactive session in herdr: the plainest use of Max, one you and the orchestrator can watch and type into. herdr does not own the work: Postgres does, and the session id is the handle, so a herdr restart costs one turn. claude -p cannot be steered mid-turn and, by an open Claude Code bug reproduced on four accounts, costs about 1.8× the 5-hour window per token. The Agent SDK's subscription use is contested. Claude Code's own background sessions fit best, with herdr only the view, but they are a research preview: they become the second adapter behind the same port once that label goes (§6).

Can I read an old lead's conversation? Yes, and continue it. Each attempt keeps its session id, and the factory archives the transcript at close (W1b), because Claude Code deletes its own after 30 days. factory issue resume <id> (W6) opens it in a herdr tab as a fork, so you can ask the lead why it did what it did; until then claude --resume <session id> works within the 30 days (§6).

Is a factory on one Mac mini a real factory? Warp says "you can't have a local software factory because you can't have automations running off your laptops." The mini is not a laptop: it is always on, and Warp's own self-hosted workers run on customer machines too. What makes it a factory is the loop that measures and improves itself, not where it runs (appendix E).
