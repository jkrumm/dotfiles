## Synthesize documented 2025–2026 best practices for 'agent-first' CLI design

**Evidence quality first.** Of six sources read in full, only two are vendor-grade (Anthropic engineering; InfoQ). The rest are practitioner checklists — the irurueta guide carries an explicit "generated with the assistance of AI … verify" banner. clig.dev is pre-agent and explicitly *human-first*: "Human-readable output is paramount. Humans come first, machines second." It is the baseline agent-first guides build on or argue with, not an agent-first source.

**(a) Schema-derived, machine-readable help.** irurueta: `docsctl schema --json` emits the whole tree — `schemaVersion`, `globalFlags`, per-command args/flags with types, `output.schema`, `exitCodes`, `safety` — and requires help text, tree, completion and man page to be generated from one declaration "so they cannot disagree". It treats `--help --json` as an equivalent alternative: "pick one spelling and keep it everywhere." The agentic-cli-design skill's P7 names `commands --json`, `schema --command … --output json-schema`, `--help --json` with fixed top-level `schemaVersion`/`type`/`ok`. clig.dev asks only for a parsing library and complete `--help`; machine-readable help is absent there.

**(b) Envelope + exit codes.** InfoQ: structured output *is* an API contract; version it (Terraform state's `"version": 4`), define JSON Schema/CUE and `vet` it in CI; exit codes "0 success, 1-2 correctable user defined errors, 3-125 application specific". No numbering is standard: dev.to uses 0/1/2/3/4/5 (4 = permission denied), the skill uses 4 = *retryable*, irurueta assigns 5 = confirmation-required, 6 = retryable, 7 = auth. The *categories* (usage / retryable / needs-human) are documented; the digits are not.

**(c) Token efficiency.** Anthropic: paginate, filter, truncate with sensible defaults, steer with the truncation message; Claude Code caps tool responses at 25,000 tokens; a `response_format` enum lets the agent pick "concise" (~72 tokens) vs "detailed" (~206). Skill P6: `--fields/--select`, `--output ndjson`, summary-by-default. InfoQ's AWS CLI v2 pager regression ("thousands of CI jobs failed") is the canonical non-TTY hazard.

**(d) Progressive disclosure.** clig.dev already prescribes terse help with no args, full help on `--help`, and `myapp help subcommand`. irurueta formalises four layers: help text → schema → completion/man → agent skill, with `schema` listing commands and `schema <cmd>` pricing only the one needed.

**(e) Async.** Only fragments: InfoQ demands progress streaming so work "doesn't appear hung" and stable streams (agents background jobs and read the file), plus graceful SIGTERM; dev.to's help example documents `--wait` and `--timeout`.

**(f) Idempotency.** Well cross-verified: irurueta's `--idempotency-key` ("the same key returns the earlier result"), skill P3's `dedupe-key`/`client-request-id` + `--if-exists skip|update|error`, dev.to's `ensure`/`apply`/`--if-not-exists` (kubectl apply as reference), clig.dev's "idempotent where possible" + crash-only.

**(g) Non-interactive.** Universal: clig.dev (`--no-input`, prompt only on TTY, `--confirm="name"`), InfoQ (`--no-prompt`, flags > env precedence), skill P2, irurueta (`--yes`, exit 5). *Disagreement:* dev.to allows auto-skipping prompts on non-TTY; clig.dev and irurueta fail instead. Auto-yes for destructive ops is opinion, not documented practice.

*Also contested:* InfoQ says adopt MCP day one; dev.to deleted three MCP servers for CLI (~40% token saving).

## Only two frameworks self-describe machine-readably
**incur** is purpose-built for it: `--llms` prints an "LLM-readable manifest", `--schema` prints JSON Schema for a command's args/options/env/output, and `--format json` makes both parseable; it also emits OpenAPI (`/openapi.json`) and an MCP endpoint. **oclif** is the other: `oclif manifest` "[g]enerates plugin manifest json (oclif.manifest.json)". For the other seven, no manifest/JSON-Schema emitter appears in the official docs read — that would require custom generation (e.g. walking citty's `args` or commander's `.options` and hand-emitting JSON Schema).

## Help generation
`--help` is derived from the same declarations in **all nine**. citty: automatic usage + `renderUsage`/`showUsage`. clipanion: `static usage = Command.Usage({category,description,details,examples})` → `Builtins.HelpCommand`. cleye: rich generated tables, `help.render` override. commander: "help information is auto-generated based on the information commander already knows". incur: help rendered from the Zod schemas. Only cleye and incur tie help *to a schema* in the strict sense; the rest tie it to bespoke arg descriptors.

## Nested subcommands / JSON output / Bun
Nested: citty (`subCommands`, lazy), clipanion (`static paths=[['a','b']]`), commander (`.addCommand`), oclif, incur (command groups + `fs()`), gunshi (composable/lazy), @effect/cli (`withSubcommands`), stricli. **cleye** documents only a flat `commands` array. JSON output: only **incur** ships a real convention (`--json`, `--format toon|json|yaml|md|jsonl`, `{ok,data,meta}` envelope); others leave it to the user. Bun: **gunshi** states Node/Deno/Bun; **incur** is Bun-first (`Bun.serve(cli)`, `incur build`); the rest don't document Bun.

## Q1 — cyclopts vs typer (Python)

**Registry facts (both from PyPI JSON):** `cyclopts` **5.3.1**, `requiresPython >=3.11`. `typer` **0.27.3**, `requiresPython >=3.10`; Typer's own docs note it **vendored Click since 0.26.0** and that `typer-slim` is no longer supported since 0.22.0.

**Type-hint/annotation-driven definition + annotation-derived help — both yes, out of the box.**
- cyclopts: `App` / `@app.command` / `@app.default` / `cyclopt.run`; help from *docstrings* (Google/numpy "Parameters" sections) plus `Parameter(help=…)`, `metavar`, `choices`, `show_default`, `env_var`, validators, converters. Its docs page renders a `Literal`-typed `env` with `[choices: …]` in help.
- typer: `typer.Typer()`, `@app.command()`, `typer.run()`; "automatic `--help`, auto-completion" from plain Python types; bools get `--formal/--no-formal`; help text from `typer.Option/Argument(help=…)`.

**Machine-readable manifest / JSON Schema — neither framework documents one.** cyclopts' API reference lists `App.generate_docs(output_format=…)` accepting only `"markdown"/"md"`, `"html"/"htm"`, `"rst"/"rest"/"restructuredtext"`, plus `command_tree()` (returns a `rich.tree.Tree`) and `generate_completion()`. There is no JSON/JSON-Schema emitter in the documented API (page truncated at 80k of 172k chars, so treat absence as *unconfirmed*). Typer's docs describe only `--help` and shell completion. So an OpenAPI-shaped CLI manifest requires **custom glue** — for cyclopts the building blocks are documented introspection APIs (`assemble_argument_collection()`, `__iter__`, `app[key]`, `parse_commands()`).

Note: the cyclopts "Compared to Typer" section (vendor-authored, not independent) claims Typer lacks union-type support and docstring parsing.

## Q2 — one schema across CLI / HTTP / MCP

**Python.** Official MCP Python SDK: PyPI `mcp` **2.3.0**, import `from mcp.server import MCPServer`, `@mcp.tool()` / `@mcp.resource("greeting://{name}")`, `mcp[cli]` extra. Docs state outright: "**No JSON Schema. `a: int, b: int` is the schema.**" (Docs say Python 3.11+; PyPI metadata says `>=3.10` — contradiction.) FastAPI→MCP is **out of the box**: `fastmcp` **4.1.4** (PrefectHQ) generates an MCP server from a FastAPI app since **2.0.0** (built on its OpenAPI integration; `RouteMap` remapping; `http_app()` mount since 2.3.1); `fastapi-mcp` **0.4.0** does `from fastapi_mcp import FastApiMCP; FastApiMCP(app).mount()` with request/response schemas preserved.

**TypeScript.** `@modelcontextprotocol/sdk` **1.32.2** is the legacy v1 line; v2 ships split packages `@modelcontextprotocol/server` **2.4.0** (zod `^4.2.0`, node ≥20) and `@modelcontextprotocol/client`. Tool schemas use **Standard Schema** ("bring Zod v4, Valibot, ArkType"): `registerTool('greet', { inputSchema: z.object({ name: z.string() }) }, handler)`. zod itself is **4.6.7**; the v1 SDK depends on `zod-to-json-schema ^3.25.1` (registry metadata — internal conversion, not a documented public API).

**Out of the box:** annotation/type-hint → CLI + help (both Python frameworks); typed model → HTTP (FastAPI/OpenAPI); OpenAPI/FastAPI → MCP tools (FastMCP, fastapi-mcp); Zod object → MCP tool schema (TS v2). **Glue required:** CLI → JSON-Schema/OpenAPI manifest for the frameworks that document no emitter, and Zod schema → CLI command surface outside incur (no other documented first-party tool surfaced in my searches).

## Assemble the evidence base on 'CLI over MCP for agents'

## Part A — the CLI-vs-MCP debate (what I could actually read)

**Mario Zechner, "MCP vs CLI: Benchmarking Tools for Coding Agents", 2025-08-15** — 120 runs (3 tasks × 4 tools × 10 reps) in Claude Code comparing his `terminalcp` MCP server, the same tool as a CLI, `tmux` and `screen`. Result: "MCP vs CLI truly is a wash: Both terminalcp MCP and CLI versions achieved 100% success rates. The MCP version was 23% faster (51m vs 66m) and 2.5% cheaper ($19.45 vs $19.95)." He also flags "MCP's hidden advantage: no security checks" — CLI invocations trigger Claude Code's malicious-command detection on every bash call (Haiku tokens 35k vs 1.3–2M). His conclusion is *not* "MCP loses": "The protocol is just plumbing… if you're building a tool from scratch and your users already have a shell tool available, just make a good CLI. It's simpler and more portable," and "adding an MCP server on top of it is very straightforward."

**Armin Ronacher** — 2025-07-03 "Tools: Code Is All You Need": "I'm not a big fan of MCP right now," citing non-composability and context cost; "try completing a GitHub task with the GitHub MCP, then repeat it with the `gh` CLI tool" — the CLI wins; "I can only encourage people to bypass MCP." But 2025-08-18 "Your MCP Doesn't Need 30 Tools: It Needs Code" adds real nuance: CLIs are platform/version-dependent, undocumented, weak at non-ASCII input, suffer Claude Code's "security preflight" pass, and lose multi-turn session state; his fix is a *single-tool* MCP ("ubertool") exposing a programming language (`pexpect-mcp`, `playwrightess`).

**Simon Willison** — 2025-10-16 "Claude Skills are awesome, maybe a bigger deal than MCP": "My own interest in MCPs has waned ever since I started taking coding agents seriously. Almost everything I might achieve with an MCP can be handled by a CLI tool instead. LLMs know how to call `cli-tool --help`." Earlier (2025-06-29) he relayed Armin's talk: "When your agentic coding tool can run commands in a terminal you can mostly avoid MCP."

**Anthropic** — Claude Code docs, "Best practices for Claude Code" → "Use CLI tools": "CLI tools are the most context-efficient way to interact with external services. If you use GitHub, install the `gh` CLI… Without `gh`, Claude can still use the GitHub API, but unauthenticated requests often hit rate limits." Same page keeps a separate "Connect MCP servers" section — Anthropic treats them as complementary, not exclusive. Anthropic's engineering post "Writing effective tools for agents" is MCP-centric and never argues CLI-over-MCP; its relevant warning is against "tools that merely wrap existing software functionality or API endpoints."

**Agreement:** CLI+shell + `--help` discovery is cheapest in context (all four). **Contradiction:** Zechner's own benchmark says the two are a wash for success rate and MCP was *faster/cheaper*; Ronacher concedes CLI failure modes and builds MCP ubertools; Mario treats bypassing Claude Code's security check as an *advantage*, Ronacher calls that same bypass a CLI cost and "security is a sham". Anthropic never endorses replacing MCP with CLIs.
