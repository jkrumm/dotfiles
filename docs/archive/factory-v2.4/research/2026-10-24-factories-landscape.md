## Bottom line
- **Swamp** is an adaptive-automation CLI in which the reusable unit is a *behavior* — a TypeScript type plus YAML definition — composed into a workflow DAG whose only step task types are `behavior` (stored as `model_method`), `workflow`, `manual_approval` and `assert`; there is no agent step type, so agents author definitions or get shelled out to via the `@swamp/agent-runner` extension, while `context.runModel()` invokes another behavior, not an LLM.
- **Sandcastle** (`@ai-hero/sandcastle`, v0.12.0, MIT) is a TypeScript harness for AFK coding agents in sandboxes: the orchestration loop lives in code, agents are invoked as steps inside git worktrees, and the issue tracker is a two-command seam that already includes Beads via `bd ready --json` / `bd close`.
- **Agent Orchestrator** is a local desktop app plus Go daemon plus `ao` CLI where one worker session equals one task, one coding agent and one isolated workspace; its most transferable idea is storing only durable facts in SQLite and deriving every display status at read time, with triggers → `change_log` → CDC → SSE as the event spine.
- **oh-my-hermes** is an operating layer for Nous Research’s Hermes Agent — not a Hermes agent itself — adding `omh`, ten `ulw-*` workflows, a Hermes plugin, deterministic handoff preparation, a “Plan · not run / Code · reported done / Test · verified” claim ladder, append-only approval receipts, and category-to-model chains that fail over rather than silently downgrade.
- **pstack** is an MIT Cursor plugin by Lauren Tan (@poteto) in `cursor/plugins`: `/poteto-mode` routes to 23 playbooks, `/create-verification-skill` builds a project-local verify CLI and Feature Map, and the orchestration ledger is keyed by PR plus head SHA so a new head voids the verdict; the 2,000–2,500 PRs/month figures are self-reported and unaudited.
- **Gas Town/Beads mechanics remain unverified here beyond your background**; from that background, the ready queue and role-separated supervision are the portable pieces, while the fixed 5-minute lease and cross-repo dependencies are the parts to replace or avoid.
- **Across the verified wider landscape**, OpenHands and Claude Code both converge on the same shape: a stateless step function over an append-only event log, with deterministic hooks or analyzers bracketing every tool call — which maps directly onto Claude Code workers, OpenCode triage and a Postgres ledger.

## (a) Swamp — swamp-club.com

**Summary.** Swamp describes itself as “an adaptive automation framework designed to be operated by AI agents,” decomposing automation into behaviors, workflows, vaults, extensions, skills and a data layer ([how Swamp works](https://swamp-club.com/manual/explanation/how-swamp-works)). The crucial design choice is that the agent is usually outside the runtime: a behavior has two halves — “The type is reusable logic written in TypeScript … The type is code; the definitions are data,” and because definitions are structured data, “an agent can produce one using only its general reasoning ability” ([how Swamp works](https://swamp-club.com/manual/explanation/how-swamp-works)). A workflow is “a DAG of jobs” whose steps run behavior methods, with jobs in dependency order and steps within a job in parallel ([how Swamp works](https://swamp-club.com/manual/explanation/how-swamp-works)). The step schema is deliberately small: exactly `behavior`, `workflow`, `manual_approval` and `assert`, with `model_method` as the stored compatibility spelling ([workflow reference](https://swamp-club.com/manual/reference/workflows)). There is no agent/LLM step type; in-workflow agent invocation is packaged as `@swamp/agent-runner`, which “manages agent CLI binaries” and returns structured verdicts rather than a chat completion ([agent-runner](https://swamp-club.com/extensions/@swamp/agent-runner)). In-process model calls come from a behavior type such as `@keeb/anthropic/claude`, whose `generate(prompt)` uses the Messages API while `cli_generate` spawns the local `claude` CLI via `Deno.Command` ([Anthropic extension](https://swamp-club.com/extensions/@keeb/anthropic)). `context.runModel()` is not an LLM call: “Model” is the legacy product term for a behavior, and the API keeps that spelling ([model reference](https://swamp-club.com/manual/reference/extensions/model)); it invokes another behavior’s method, bounded to depth 10, 100 total invocations per top-level execution, with cycle detection and an isolated vault bag ([model reference](https://swamp-club.com/manual/reference/extensions/model); [invocation service](https://github.com/swamp-club/swamp/blob/HEAD/src/domain/models/model_invocation_service.ts)).

**Binding, failure and gates.** Every method execution writes “versioned, immutable data artifacts” into `.swamp`, and downstream steps read them through CEL expressions such as `data.latest(...).attributes.status` ([how Swamp works](https://swamp-club.com/manual/explanation/how-swamp-works)). The boundary is typed: “The output of one behavior becomes the input of another through typed, validated references. If the data doesn’t exist yet … the expression fails loudly rather than passing through a blank value” ([how Swamp works](https://swamp-club.com/manual/explanation/how-swamp-works)). Idempotency uses a per-step `guard` CEL expression; failure tolerance uses `allowFailure`; dependency conditions are `always/succeeded/failed/completed/skipped` ([workflow reference](https://swamp-club.com/manual/reference/workflows)). There are **no per-step retry/backoff fields**: the step Zod object’s complete key set is `name, description, task, forEach, dependsOn, weight, concurrency, dataOutputOverrides, allowFailure, placement fields, guard, writes`, and unknown keys are rejected rather than silently stripped ([step.ts](https://github.com/swamp-club/swamp/blob/HEAD/src/domain/workflows/step.ts)). Retry is a workflow-level CLI operation: `swamp workflow resume <wf> --run <id>` resets failed steps and everything downstream, `--from <step>` re-enters the DAG, and checkpoint recovery is `recover` then `resume`; the docs warn that retry “does not guarantee exactly-once execution” ([workflow reference](https://swamp-club.com/manual/reference/workflows)).

`manual_approval` suspends the run — status `suspended`, step `waiting_approval` — and “Approving a gate does not continue the run; a resume does,” with an `approvalDecision{approved, reason, decidedBy, decidedAt}` written to the step record ([workflow reference](https://swamp-club.com/manual/reference/workflows)). `assert` is a first-class verification task: raw CEL `expr`, `message`, `severity` low/medium/high, a `--fail-on` threshold, and `--junit` output ([workflow reference](https://swamp-club.com/manual/reference/workflows)). Vault references are resolved at step execution, not planning, and a workflow-level `vaults:` list is an allowlist ([workflow reference](https://swamp-club.com/manual/reference/workflows)).

**Maturity.** `swamp-club/swamp` has 673 stars and 49 forks, was created 2026-01-28, last pushed 2026-10-24, and its latest release is CalVer `v20261024.185121.0-sha.03e347b9` published the same day — daily-cadence development, not a demo ([repo](https://github.com/swamp-club/swamp)). Governance is unusual: only employees of Elder Swamp Club contribute code, external PRs are automatically closed, and running the CLI requires a swamp-club.com account ([org](https://github.com/swamp-club); [README](https://github.com/swamp-club/swamp/blob/HEAD/README.md)). Licensing is AGPL-3.0 with a Swamp Extension and Definition Exception ([org](https://github.com/swamp-club)). Per-step token and cost recording is **not verified**: the run tracker is documented as recording identity, heartbeat and status in `.swamp/run_tracker.db`, not cost ([run tracker](https://swamp-club.com/manual/explanation/the-run-tracker)); a `@webframp/ai-usage` listing advertises cross-provider token monitoring, but its schema was not retrieved ([extensions](https://swamp-club.com/extensions?label=ai)).

**Worth stealing.** (1) **Type/definition split** — code owns methods, schemas and execution; the model only emits declarative YAML conforming to a schema. (2) **Four primitive task types**, especially `assert` and `manual_approval` as workflow citizens rather than afterthoughts. (3) **Typed artifact references plus `guard`** — downstream reads fail loudly rather than accepting blanks, and re-runs skip completed work. (4) **Approve ≠ resume, with a decision record and vault allowlist** — a clean model for a Postgres-backed approval ledger.

## (b) mattpocock/sandcastle

**Summary.** Sandcastle is a TypeScript library and CLI for orchestrating AFK coding agents inside isolated sandboxes: “You invoke agents with a single `sandcastle.run()`. Sandcastle handles sandboxing the agent with a configurable branch strategy. The commits made on the branches get merged back” ([README](https://github.com/mattpocock/sandcastle/blob/HEAD/README.md)). It deliberately is not a task manager: “You write the prompt, and the engine executes it — no opinions about workflow, task management, or context sources are imposed” ([README](https://github.com/mattpocock/sandcastle/blob/HEAD/README.md)). The published package is **`@ai-hero/sandcastle` v0.12.0**, MIT, with essentially one runtime dependency, `@clack/prompts` ([npm](https://www.npmjs.com/package/@ai-hero/sandcastle)). Do not install bare `sandcastle`: that is `bcoe/sandcastle` v1.3.3, a 2022 sandbox for untrusted JavaScript ([npm](https://www.npmjs.com/package/sandcastle)). The work item is a `Task`, “a work item from the issue tracker that the agent selects and works on during an iteration,” and an `Iteration` is “a single invocation of the agent inside the sandbox, producing at most one commit against one task” ([CONTEXT.md](https://github.com/mattpocock/sandcastle/blob/HEAD/CONTEXT.md)).

**Design.** The strongest part is that the TS file is the orchestrator and the agents are steps. The `parallel-planner-with-review` template runs a planner (`claudeCode("claude-opus-4-8")`, `maxIterations: 1`, Zod-validated `Output.object`), fans out per issue to an implementer (`claude-sonnet-4-6`, `maxIterations: 100`) and a reviewer that runs only if `implement.commits.length > 0`, then a single merger, all inside `MAX_ITERATIONS = 10` outer rounds ([main.mts](https://github.com/mattpocock/sandcastle/blob/HEAD/src/templates/parallel-planner-with-review/main.mts)). Task selection and dependency analysis are LLM work: the planner prompt says “Analyze the open issues and build a dependency graph” and requires a deterministic branch name `sandcastle/issue-{id}` “so that re-planning the same issue always produces the same branch name and accumulated progress is preserved” ([plan-prompt.md](https://github.com/mattpocock/sandcastle/blob/HEAD/src/templates/parallel-planner-with-review/plan-prompt.md)). The reviewer’s evidence is a diff and its rubric is a repo file: `git diff {{TARGET_BRANCH}}...{{BRANCH}}`, `git log`, tests, typecheck, and `@.sandcastle/CODING_STANDARDS.md` ([review-prompt.md](https://github.com/mattpocock/sandcastle/blob/HEAD/src/templates/parallel-planner-with-review/review-prompt.md)). The minimal loop enforces one issue per iteration, a priority order, red-green-refactor, `npm run typecheck` / `npm run test`, one commit prefixed `RALPH:`, and closing the issue with `{{CLOSE_TASK_COMMAND}}` ([simple-loop](https://github.com/mattpocock/sandcastle/blob/HEAD/src/templates/simple-loop/main.mts)).

The tracker seam is literally two shell strings injected by `sandcastle init`: `LIST_TASKS_COMMAND` and `CLOSE_TASK_COMMAND`, with `github-issues` using `gh issue list …` / `gh issue close …` and **`beads` using `bd ready --json` / `bd close <ID> --reason="Completed by Sandcastle"`** ([InitService.ts](https://raw.githubusercontent.com/mattpocock/sandcastle/HEAD/src/InitService.ts)). Durable state is git plus filesystem, not a database: worktrees under `.sandcastle/worktrees/`, logs under `.sandcastle/logs/`, and Claude session JSONL captured under `~/.claude/projects/…` ([README](https://github.com/mattpocock/sandcastle/blob/HEAD/README.md)). Human-in-the-loop is thin and permission-mediated: `permissionMode` (`default|acceptEdits|plan|auto|dontAsk|bypassPermissions`) was added to `claudeCode()`, and AFK runs otherwise default to `--dangerously-skip-permissions` ([releases](https://github.com/mattpocock/sandcastle/releases)); a first-class “Ask a human” request, issue #505, is still open ([issue](https://github.com/mattpocock/sandcastle/issues/505)). Cost control is reporting, not capping: each iteration carries `IterationUsage {inputTokens, cacheCreationInputTokens, cacheReadInputTokens, outputTokens}`, with `maxIterations`, `idleTimeoutSeconds` (600), `completionTimeoutSeconds` (60) and per-step timeouts, but no budget field in `RunOptions` ([README](https://github.com/mattpocock/sandcastle/blob/HEAD/README.md)).

**Maturity.** 8,622 stars, 919 forks, 182 open issues/PRs, MIT, created 2026-03-17, last pushed 2026-10-20, latest release v0.12.0 published 2026-06-29 ([repo](https://github.com/mattpocock/sandcastle)). It is production-shaped for a personal tool — 20 numbered ADRs, co-located tests, changesets, husky and CI — but still 0.x, with roughly four months between the latest release and the last push ([ADRs](https://github.com/mattpocock/sandcastle/tree/main/docs/adr)). It is effectively a one-human-maintainer project with agent co-authorship.

**Worth stealing.** (1) **Harness in code, judgement in prompt** — loop, fan-out, gating and merge order are typed code; a prompt describes one work item. (2) **The two-command tracker seam** — replace `bd ready --json` with a Postgres `SELECT … FOR UPDATE SKIP LOCKED` and the engine shape survives. (3) **Deterministic branch-per-task identity** — `sandcastle/issue-{id}` makes re-planning resume rather than redo. (4) **Structured output as the agent→orchestrator contract**, with `maxIterations: 1` for reasoning-only roles and idle-timeout distinct from completion-timeout. Note the direct lesson for Beads: the planner LLM re-derives the dependency graph from issue data rather than trusting `bd ready`’s resolution, which sidesteps the inert cross-repo dependency problem you already hit.

## (c) OrchestratorInc/agent-orchestrator

**Summary.** “Orchestrator.inc” is a local desktop workspace — Electron plus React, with Expo mobile — on top of a long-running Go daemon; “a worker is one task, one coding agent, and one isolated workspace,” and the desktop app runs the daemon so no CLI is required ([README](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/README.md)). Above workers sits a persistent “project orchestrator,” which “owns planning and delegation; workers own implementation, tests, commits, and pull requests” ([README](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/README.md)). **Design.** Isolation is a git worktree per project session at `worktrees/<project-id>/<session-id>`, created on temporary branch `ao/<session-id>/root` and later renamed to `ao/<slug>/root`; standalone workers get plain-directory workspaces ([architecture](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/architecture.md)). Durable local state is SQLite with goose migrations and sqlc, plus “DB triggers → change_log table → CDC Poller → Event Broadcaster → SSE,” and a load-bearing rule: “Never store display status: Status is derived from durable facts at read time” ([architecture](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/architecture.md)). Observation loops have explicit cadence: SCM observer “Poll PRs every 30s,” Runtime Reaper “Poll every 5s,” and termination only when runtime and process are both dead and no recent activity exists — “Failed probes are NOT proof of death” ([architecture](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/architecture.md)).

Gates are explicit rather than automatic: Chat persists approvals and structured input; `autoReview` is a project default copied to new worker sessions and “waits for an eligible pull-request revision and an idle worker” but “does not merge”; merging is always explicit with `ao pr merge` ([lifecycle automation](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/frontend/src/docs/content/configuration/lifecycle-automation.mdx)). Verification is observation of external CI and review, with signature-deduplicated nudges carrying failing check names and links; it does not run your test suite itself ([lifecycle automation](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/frontend/src/docs/content/configuration/lifecycle-automation.mdx)). The agent layer is harness-agnostic: 23+ agent adapters, ports for `Runtime`, `Workspace`, `Agent`, `SCM`, `Tracker`, `AgentMessenger` and `PRWriter` ([backend structure](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/backend-code-structure.md)). TUI runs the agent in native PTY/ConPTY with tmux as “legacy or fallback”; Chat runs an ACP-style protocol controller, with a capability-gated handoff between them ([architecture](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/architecture.md)). AO does not bundle or proxy provider CLIs; you bring agents and credentials ([docs](https://docs.orchestrator.inc)). Local parallelism is not capped in the pages read, while Cloud enforces a per-organization concurrent-sandbox limit reported as `SANDBOX_QUOTA_EXCEEDED` ([cloud README](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/cloud/README.md)); no token-budget key appears in those pages.

**Maturity.** 13,572 stars, 1,862 forks, 1,002 open issues, created 2026-02-13, last pushed 2026-10-24, latest release v0.14.6 on 2026-10-24 ([repo](https://github.com/OrchestratorInc/agent-orchestrator)). The published manual is pinned to v0.13.3 (1 October 2026) while the repo is at v0.14.6 — the docs lag the code ([docs](https://docs.orchestrator.inc)). The company identity behind it could not be verified from a primary page.

**Worth stealing.** (1) **Durable facts plus derived status** — store events and raw state; compute `working`, `needs_input`, `ci_failed`, `mergeable` at read time. (2) **`change_log` → CDC → SSE** — in Postgres, triggers plus `LISTEN/NOTIFY` or an outbox table give the same single event source. (3) **Worktree born on a temporary session branch then renamed to a slug** — the workspace path never changes and agent-made branches stay attributed. (4) **Observer/action split with conservative death detection**, plus `ao report --done`’s five-minute settlement window and `--stuck` interrupt “at most once per worker every three minutes” ([CLI docs](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/cli/README.md)) — a direct upgrade over fixed 5-minute leases.

It is not a person’s private workflow or a SaaS. The README identifies the author as an engineer who has worked at Meta, Netflix and Cursor and is on the React core team, and says “these are the same skills i use every day to ship high quality code at Cursor” ([README](https://github.com/cursor/plugins/blob/HEAD/pstack/README.md)). The entry point is `/poteto-mode`, which matches a request to one of twenty-three playbooks and copies that playbook’s steps into a todo list verbatim, leaving skipped steps in place with a one-line reason; it ships twenty-four one-rule principles ([SKILL.md](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/SKILL.md)).

**Workflow.** The load-bearing innovation is a **project-generated verification skill**: `/create-verification-skill` builds an agent-friendly CLI (CDP/simulator/`--dry-run`/JSON) plus a markdown Feature Map, and `/maintain-verification-skill` keeps it fresh ([SKILL.md](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/SKILL.md)). Parallelism is Cursor cloud agents, explicitly **not** git worktrees: “I would recommend against doing this [worktrees]… You may be able to get away with running up to 10 agents in parallel with worktrees depending on the size of your repo” ([Tan](https://x.com/poteto/article/2094457600259842065)). `/swarm` fans out workers that report PASS/ISSUES/BLOCKED, and “A gap does not count as a pass” ([swarm](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/swarm/SKILL.md)). Model routing is by role: Grok for code delegates and swarm workers, Claude Opus for judgment and prose ([SKILL.md](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/SKILL.md)).

Conflict avoidance is explicit: “Run owners in parallel off trunk, never stacked, so each PR lands on its own”; one owner per PR; “Green CI alone never authorizes a merge”; never push a fix yourself “because each branch has one writer” ([autopilot-full](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/autopilot-full.md)). The durable-ledger design is in `orchestrate`: `units.tsv` (id, track, state, branch, PR, head SHA, brief), `frontier.json` (computed merge frontier), `ledger.tsv` (one verdict row per PR number plus head SHA with grades `live-ui-verified` / `unit-test-verified` / `type-check-only` / `verifier-blocked` / `verifier-failed`), `inbox/`, `gates.md`, `decisions.tsv`, and standing orders pasted into every spawn and resume; “A new head SHA voids the row” and “CI green is an input to a verdict, not a verdict” ([orchestrate](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/orchestrate.md)). In-flight children are capped “at what one drain can process, roughly ten,” nesting works to depth 3, and “Run a unit’s verifier on a different model family from its worker” ([orchestrate](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/orchestrate.md)). Shipping lands only a contiguous verified run from the bottom up, walks up from the lowest unmerged PR, stops at the first without PASS, and compares `git patch-id` at the verdict SHA with the current head before trusting an older verdict; “Only a verdict from an agent that did not write the code counts” ([shipping](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/shipping.md)). Babysit works only the lowest unmerged PR, in order conflicts → review threads → CI, with one retry for suspected flake CI, and “Babysitting never authorizes merging” ([babysit](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/babysit.md)). PR reviewability rules: “Prefer five narrow PRs to one large PR,” Conventional Commits, PR body with Why/What/Scope/Tradeoffs/Blast Radius/Verification, squash body under about 40 lines, always open ready, never draft ([opening a PR](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/opening-a-pr.md)).

**Numbers and maturity.** All throughput figures are self-reported: “2,000 PRs a month to production,” a screenshot captioned “Ending the month of August with 2,462 PRs in production,” and “2,500 PRs last month” in a later video ([Tan](https://x.com/poteto/article/2097732320606507506); [folkfox](https://folkfox.com/pstack-2500-ai-agent-prs-verification/)). An independent write-up notes that “nobody outside her team has audited either” and that a PR count “does not tell you how much stayed merged”; no cost-per-PR or revert rate is published ([folkfox](https://folkfox.com/pstack-2500-ai-agent-prs-verification/)). A second independent write-up attributes the method to verification-first design rather than prompt tricks ([thakicloud](https://thakicloud.com/tech-blog/en/agentops/pstack-poteto-mode/)). Counts drift by version — secondary sources report 21/22/23 principles and 22/23 playbooks, while the live manifest is 0.15.32 ([plugin.json](https://github.com/cursor/plugins/blob/HEAD/pstack/.cursor-plugin/plugin.json)). The host `cursor/plugins` repo has 13,894 stars and 1,379 forks and was last pushed 2026-10-24 ([repo](https://github.com/cursor/plugins)). Credible as an opinionated workflow; unverified as a throughput claim.

**Worth stealing.** (1) **The brief as the product** — goal/scope/context/acceptance/verify/timebox/forbidden/report standing orders, pasted on every spawn and every resume. (2) **A verdict ledger keyed by (PR, head SHA)** where a new head voids the row and CI green is an input, not a verdict — your Postgres ledger. (3) **One writer per branch, one stacker per stack**, with workers forbidden to rebase, retarget or merge. (4) **Cheap verifiers in parallel, strong models for judgment**, with the verifier on a different model family and a project-local verify CLI so “done” is executable.

## Wider landscape: what is actually verified

Only **OpenHands** and **Claude Code** were covered from primary documentation here; aider, SWE-agent/SWE-bench, OpenAI Codex cloud, Devin/Cognition, Factory.ai droids, Google Jules, Cursor background agents, Agentless, CodeR, MetaGPT and ChatDev remain unverified in this report. Their absence is not evidence about them.

| Dimension | OpenHands | Claude Code |
|---|---|---|
| Work item | Conversation | Session / subagent / task hooks |
| Loop | One `step()`: resolve confirmations → condense → LLM → parse actions → confirm → execute observations | `claude -p` runs the same agent loop via the Agent SDK |
| Deterministic glue | `SecurityAnalyzer` before every action; typed event partitioning | CLI exit codes, hooks, worktree isolation, `--json-schema` |
| Human gate | Direct vs Confirmation tool modes; high-risk actions blocked | Permission modes, hook `ask`/deny, auto-mode classifier |
| Verification | Risk tiers and confirmation; tests are external | Hook exit 2 on `Stop` bounces the agent; prompt/agent hooks; reviewer subagents |
| Durable state | Append-only immutable event log | Session JSONL transcript; `--continue` / `--resume` |
| Cost | Not documented in the pages read | `--max-budget-usd`, model tiering, prompt-cache reuse |

OpenHands’ Agent is stateless and event-driven: each `step()` resolves pending confirmations, runs condensation, queries the LLM, parses into `ActionEvent`s or a `MessageEvent`, performs a confirmation check that sets `WAITING_FOR_CONFIRMATION`, then executes to `ObservationEvent` ([agent architecture](https://docs.openhands.dev/sdk/arch/agent)). Its event log is append-only, immutable and typed, partitioned into LLM-convertible events versus internal control events so orchestration traffic never enters model context ([events](https://docs.openhands.dev/sdk/arch/events)). It defines two error classes with opposite semantics: `AgentErrorEvent` is LLM-visible and the conversation continues; `ConversationErrorEvent` is not LLM-convertible and raises `ConversationRunError` ([events](https://docs.openhands.dev/sdk/arch/events)). `Event.source` is deliberately orthogonal to LLM role ([events](https://docs.openhands.dev/sdk/arch/events)).

Claude Code’s headless mode exits 0/non-zero for scripting, supports `--output-format json|stream-json`, and `--json-schema` returns `structured_output`, which is absent if the run ends without valid structured output ([headless](https://code.claude.com/docs/en/headless)). Resume is a file: `--continue`, or `--resume <session-id|.jsonl path>` ([headless](https://code.claude.com/docs/en/headless)). Hooks are the verification spine but **fail open by default**; a timed-out `PreToolUse` does not block unless `onFailure: "block"` is set (v2.1.295+) ([hooks](https://code.claude.com/docs/en/hooks)). Exit 2 on `Stop` or `SubagentStop` prevents Claude from stopping and continues the conversation rather than failing the run ([hooks](https://code.claude.com/docs/en/hooks)). Subagents support `model`, `maxTurns`, `isolation: worktree`, and model tiering is documented explicitly as a cost-control reason to use them ([subagents](https://code.claude.com/docs/en/sub-agents)). The strongest transferable shape is therefore: **stateless step function over an append-only event log, deterministic gates around every tool call, and a resumable transcript as the only durable state.**

## Target stack: concrete capabilities and limits

**Claude Code.** Current registry versions are `@anthropic-ai/claude-code` **2.1.310** on `latest` (`stable` at 2.1.308), published 2026-10-23 and requiring Node ≥22; the TypeScript Agent SDK is `@anthropic-ai/claude-agent-sdk` **0.3.310** ([npm](https://www.npmjs.com/package/@anthropic-ai/claude-code); [SDK](https://www.npmjs.com/package/@anthropic-ai/claude-agent-sdk)). The docs live at `code.claude.com/docs/en/*`; `claude -p` runs the same agent loop via the SDK ([SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)). `--output-format` accepts `text`, `json` and `stream-json`; `--json-schema` returns validated output in `structured_output` ([headless](https://code.claude.com/docs/en/headless)). `--max-turns` and `--max-budget-usd` exist, and subagent spend counts toward the budget ([headless](https://code.claude.com/docs/en/headless)). `--bare` skips hooks, skills, subagents, plugins, MCP servers, auto memory and CLAUDE.md; without `--bare`, a `-p` run loads a project’s `.claude/settings.json` hooks and `.mcp.json` servers even in a folder you have never trusted ([headless](https://code.claude.com/docs/en/headless)).

Crash semantics matter: SIGTERM exits **143**, leaves the in-progress turn unfinished and records no result; SIGINT ends the turn properly, and `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` continues an interrupted turn on resume ([headless](https://code.claude.com/docs/en/headless)). From v2.1.302, a `-p` or SDK run with no permission mode set starts in Manual, so gated calls are **denied** unless allowed ([permission modes](https://code.claude.com/docs/en/permission-modes)). The auto-mode classifier explicitly blocks “Sending keystrokes to Claude Code’s own tmux pane to drive its own interface” ([permission modes](https://code.claude.com/docs/en/permission-modes)) — a direct constraint on `tmux send-keys` orchestration. The official CLI exposes `--worktree`/`-w`, `--tmux` requiring `--worktree`, `--teammate-mode in-process|auto|tmux|iterm2`, and `--bg` background sessions ([CLI reference](https://code.claude.com/docs/en/CLI-reference)). Subagents can spawn up to three layers below the main conversation, and spawning fails with “Concurrent subagent limit reached” at 20 running subagents ([subagents](https://code.claude.com/docs/en/sub-agents)).

*Implications (inference, not doc-stated):* (1) use `-p`/SDK as the worker boundary and read stdout/JSON; use tmux for visibility, not control. (2) Treat exit 143 as “outcome unknown” and reconcile from the Postgres ledger, because no result is recorded. (3) Hard gates must be fail-closed: set `onFailure: "block"` and use exit 2 on `Stop`; do not rely on hooks in `--bare` reproducibility mode.

**OpenCode.** The repo resolves to `anomalyco/opencode` with **221,021 stars**, MIT, latest release **v1.19.4** on 2026-10-22; npm `opencode-ai` is 1.19.4 ([repo](https://github.com/sst/opencode); [npm](https://www.npmjs.com/package/opencode-ai)). Plugins are JS/TS modules exporting a function over `{project, client, $, directory, worktree}` and returning hooks including `tool.execute.before`, which can mutate `output.args`; custom tools use the `Plugin` type from `@opencode-ai/plugin` ([plugins](https://opencode.ai/docs/plugins)). Role-based primary/subagent model configuration and the HTTP server surface are documented in OpenCode’s own docs, but the exact config keys and endpoints were not independently retrieved here.

*Implications:* (1) use `tool.execute.before` for policy and cheap-model triage, and keep the orchestration loop outside OpenCode. (2) Use its per-role agent/model configuration for a cheap triage role and a stronger worker role; treat model tiering as configuration, not code. (3) Do not treat OpenCode’s local session store as your lease or source of truth — the ledger belongs in Postgres. Exact durability semantics remain unverified.

**Postgres.** `SKIP LOCKED` “skips any selected rows that cannot be immediately locked,” is documented as unsuitable for general work but apt for “a queue-like table,” and applies only to row-level locks ([PostgreSQL 17 SELECT](https://www.postgresql.org/docs/17/sql-select.html#SQL-FOR-UPDATE-SHARE)). Advisory locks are session-level — held until explicit release or session end, surviving rollback — or transaction-level, released automatically at transaction end; `pg_try_advisory_lock` and `pg_try_advisory_xact_lock` return false rather than waiting ([advisory locks](https://www.postgresql.org/docs/17/explicit-locking.html#ADVISORY-LOCKS); [functions](https://www.postgresql.org/docs/17/functions-admin.html#FUNCTIONS-ADVISORY-LOCKS)).

*Implications (inference from those primitives):* (1) claim work with one short transaction: `UPDATE … RETURNING` under `FOR UPDATE SKIP LOCKED`, never holding the transaction across an LLM call. (2) Reclaim with `lease_expires_at < now()` plus a heartbeat column; use `pg_try_advisory_xact_lock` for singleton maintenance jobs. (3) Add an outbox or `change_log` table and a unique key on `(task_id, step)` so a 143-exit retry cannot double-apply or double-charge.

## The 4–6 concepts with the strongest evidence

1. **Postgres as the ledger, not the agent.** Store immutable facts, events and receipts; derive status at read time; use triggers → outbox/`LISTEN/NOTIFY` for events. This is the common spine of Agent Orchestrator’s `change_log`/CDC design and oh-my-hermes’s append-only receipts ([architecture](https://github.com/OrchestratorInc/agent-orchestrator/blob/HEAD/docs/architecture.md); [ARCHITECTURE](https://github.com/rlaope/oh-my-hermes/blob/HEAD/docs/ARCHITECTURE.md)).
2. **Harness in code, judgement in a prompt or YAML.** Sandcastle’s TS orchestrator and Swamp’s type/definition split both make the loop deterministic and the work item declarative ([main.mts](https://github.com/mattpocock/sandcastle/blob/HEAD/src/templates/parallel-planner-with-review/main.mts); [how Swamp works](https://swamp-club.com/manual/explanation/how-swamp-works)).
3. **One work item, one worktree, one writer.** Deterministic branch identity (`sandcastle/issue-{id}`, `ao/<session-id>/root`) plus one writer per branch prevents duplicate and conflicting work ([plan-prompt.md](https://github.com/mattpocock/sandcastle/blob/HEAD/src/templates/parallel-planner-with-review/plan-prompt.md); [autopilot-full](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/autopilot-full.md)).
4. **Verification is a separate, executable gate.** A project-local verify CLI, `assert` steps, hook exit 2, and a verifier that did not write the code are all variations of the same rule: “done” must be observed, not asserted ([shipping](https://github.com/cursor/plugins/blob/HEAD/pstack/skills/poteto-mode/playbooks/shipping.md); [workflow reference](https://swamp-club.com/manual/reference/workflows); [hooks](https://code.claude.com/docs/en/hooks)).
5. **Fail-closed boundaries and unknown-outcome handling.** Set `onFailure: "block"`, treat SIGTERM 143 as unknown, and make retries idempotent with `(task_id, step)` keys ([hooks](https://code.claude.com/docs/en/hooks); [headless](https://code.claude.com/docs/en/headless)).
6. **Model tiering with explicit budgets and failover.** Cheap models for triage, strong models for implementation, a different family for verification, `maxTurns`, `--max-budget-usd`, category chains that fail over, and `cost_usd` only at terminal state ([subagents](https://code.claude.com/docs/en/sub-agents); [README](https://github.com/rlaope/oh-my-hermes/blob/HEAD/README.md); [FANOUT](https://raw.githubusercontent.com/rlaope/oh-my-hermes/main/docs/FANOUT.md)).

## Gas Town and Beads

No primary Gas Town or Beads source was assessed for this report, so the mechanics of molecules, convoys, hooks, and witness stall detection remain unverified here. Your background establishes the role taxonomy (Mayor, Polecats, Witness, Refinery, Deacon), Beads as a git-backed issue tracker with a ready queue and 5-minute fixed leases, and the finding that cross-repo dependencies behaved inertly in your spike. Sandcastle’s Beads integration at least corroborates that Beads is a real CLI with `bd ready --json` and `bd close` ([InitService.ts](https://raw.githubusercontent.com/mattpocock/sandcastle/HEAD/src/InitService.ts)).

What is portable from that background: **the ready-queue abstraction** (claim the next unblocked issue), **role-separated supervision** (planner/worker/reviewer as distinct prompts with distinct permissions), and **lease-based claiming** — but only if the fixed 5-minute lease is replaced by heartbeat plus `lease_expires_at` reclaim. What is not worth copying: the fixed lease as a correctness mechanism, and reliance on Beads’ cross-repo dependency resolution, which your spike already found inert. Molecules and convoys cannot be ranked without a verified definition; on current evidence, a Postgres work-item table with explicit dependencies and a derived ready view covers the same ground.
