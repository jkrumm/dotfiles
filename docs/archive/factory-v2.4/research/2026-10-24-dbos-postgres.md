## Bottom line

- **Versioning/recovery:** DBOS registers an application version on every launch (default: an MD5 of the registered workflows' *function text*), recovers only workflows whose stamped version matches the running process, and dequeues with the same match plus a NULL-version branch reserved for the executor running the *latest registered* version — so on one host you must pin a version string that is identical on both sides of the redeploy (TS `applicationVersion` / Python `application_version`, or `DBOS__APPVERSION`), which is exactly why the pinned configuration passed 5/5; `setLatestApplicationVersion` / `set_latest_application_version` are **OSS SDK APIs, not Conductor-only**, and move the "latest" pointer; `DBOS.patch`/`deprecatePatch` (needs `enablePatching`, which pins the version to the literal `PATCHING_ENABLED` when no version is set) is the intended in-flight replay tool; fork/rewind retarget already-stranded runs; and the official single-host procedure is blue-green draining with `listWorkflows({applicationVersion, status:[ENQUEUED,DELAYED,PENDING]})` — there is **no `dbos start` flag** for the version.
- **Bun:** No — the TypeScript SDK is officially Node-only (`engines: node >= 20`; CI on Node 20/22/24; no Bun support statement anywhere), the current package is **`@dbos-inc/dbos-sdk` 5.3.0** (single CommonJS build), and although Bun users exist and a Bun-specific production crash was fixed reactively, the two real risks are Bun's partial `node:async_hooks` (which DBOS's workflow context is built on) and Bun's missing `http.server.*` diagnostics channels (which break OTel HTTP server spans).
- **Control-loop features:** All of them exist in both SDKs — durable queues with global/worker/partition concurrency, rate limits, dedup, priority and partitioning; DB-backed cron schedules with a name+time idempotency key and backfill; durable `send`/`recv`/`setEvent`/`getEvent` with a 60 s default timeout that returns `null` and leaves the workflow running; `cancel`/`resume`/`fork`/`rewind`; `maxRecoveryAttempts` default 100 → `MAX_RECOVERY_ATTEMPTS_EXCEEDED` dead-letter (per-workflow only); and yes, DBOS can share one Postgres database with your app tables (`dbos` schema alongside `public`), with per-datasource co-commit checkpoint tables rather than a single cross-schema transaction.
- **Footprint:** It is a library, not a server — no broker, no extra daemon; one connection pool per process (TypeScript default 10, Python hard-capped at 20), LISTEN/NOTIFY by default with a handful of background pollers (queue poll 1 s, scheduler 30 s, notification listener 1 s), OTel via `@dbos-inc/otel` / `dbos[otel]`, MIT licence, and the Console UI, Prometheus metrics and retention policies are Conductor-only.
- **Comparison:** Absurd is the closest in spirit but has no version model at all (cached steps replay; renaming steps is the migration tool) and only lease-based at-least-once with possible brief step overlap; Hatchet is the closest *drop-in*, Postgres-backed, MIT replacement (at the cost of three components and no patching equivalent); Temporal and Restate out-class DBOS on versioning but each costs a daemon (and Temporal does not list PG 18, Restate abandons Postgres entirely); pg-boss and Graphile Worker are job queues rather than durable execution; pgflow is a richer workflow model but drags Supabase in even in Bun process mode.

## 1. Application versioning and recovery across redeploys

**All the ways a version gets set (four, verified).** (1) Config: TS `DBOSConfig.applicationVersion?: string`, Python `application_version: Optional[str]`. (2) Env vars: `DBOS__APPVERSION` and `DBOS__VMID` — in the TS source these are read directly at launch, `globalParams.appVersion = process.env.DBOS__APPVERSION || ''` and `globalParams.executorID = process.env.DBOS__VMID || 'local'`, with the env var described in-code as "The one true source of appVersion"; the docs note that in DBOS Cloud/Conductor the version and executor ID come from the platform, so `applicationVersion`/`executorID` are ignored there ([configuration](https://docs.dbos.dev/typescript/reference/configuration), [src/dbos.ts](https://raw.githubusercontent.com/dbos-inc/dbos-transact-ts/main/src/dbos.ts), [src/utils.ts](https://github.com/dbos-inc/dbos-transact-ts/blob/v5.3/src/utils.ts)). Config **overrides** the env var when both are present, in both SDKs ([src/utils.ts](https://github.com/dbos-inc/dbos-transact-ts/blob/v5.3/src/utils.ts), [3.3.0 _dbos.py](https://raw.githubusercontent.com/dbos-inc/dbos-transact-py/3.3.0/dbos/_dbos.py)). (3) Per-enqueue: TS `EnqueueOptions.applicationVersion`, Python `SetEnqueueOptions(app_version=...)`, plus `applicationVersion`/`application_version` on fork and rewind. (4) The version-pointer APIs, below.

**There is no CLI flag.** `npx dbos start` declares exactly one option, `-l, --loglevel`, and the Python `start()` in 3.3.0 has no click options at all ([cli.ts](https://github.com/dbos-inc/dbos-transact-ts/blob/HEAD/src/cli/cli.ts), [3.3.0 cli.py](https://github.com/dbos-inc/dbos-transact-py/blob/3.3.0/dbos/cli/cli.py), [TS CLI reference](https://docs.dbos.dev/typescript/reference/cli), [Python CLI reference](https://docs.dbos.dev/python/reference/cli)). `-v/--application-version` appears only as a *filter* on `workflow list` and as a *tag* on `workflow fork`. `dbos-config.yaml` cannot carry it either — the schema sets `additionalProperties: false` over name/language/system DB/telemetry/runtimeConfig/env ([dbos-config.schema.json](https://github.com/dbos-inc/dbos-transact-ts/blob/HEAD/dbos-config.schema.json)). So exporting `DBOS__APPVERSION` in the Mac mini's launchd/supervisor environment is the only CLI-adjacent route.

**`setLatestApplicationVersion` is not Conductor-only.** It shipped in the OSS libraries — TS `DBOS.setLatestApplicationVersion(versionName: string, options?: { applicationName?: string }): Promise<void>` ("Promote a version to latest by updating its timestamp to the current time. This is useful when rolling back to a previous application version"), Python `DBOS.set_latest_application_version("1.0.0")` — alongside `listApplicationVersions`/`list_application_versions` and `getLatestApplicationVersion`/`get_latest_application_version` ([TS methods](https://docs.dbos.dev/typescript/reference/methods), [Python upgrading](https://docs.dbos.dev/python/tutorials/upgrading-workflows), [April 2026 release note](https://www.dbos.dev/blog/dbos-new-features-april-2026), which adds "Go and Java support coming soon"). Versions are rows in the `application_versions` system table with `VersionInfo { versionId, versionName, versionTimestamp, createdAt, applicationName? }`, latest = highest `versionTimestamp`, and "Each time DBOS launches, it registers the current application version in the system database". Promotion is an `UPDATE` that re-timestamps the row ([system_database.ts](https://raw.githubusercontent.com/dbos-inc/dbos-transact-ts/main/src/system_database.ts)). (A Conductor CLI form also exists — `dbosctl app set-version <name> <version>` — but it is not required.)

**What a new process may recover and dequeue.** Recovery is version-matched: "When DBOS tries to recover workflows, it only recovers workflows whose version matches the current application version" ([upgrading-workflows](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)). Dequeue adds one nuance in source: the query is `application_version = $3` unless the dequeueing process *is* the latest registered version, in which case `(application_version = $3 OR application_version IS NULL)` — the NULL branch exists for workflows enqueued on behalf of a *different* application, whose version is deliberately left unset "so the workflow is only dequeued by an executor of that application running its latest registered version" ([system_database.ts](https://raw.githubusercontent.com/dbos-inc/dbos-transact-ts/main/src/system_database.ts), [TS methods](https://docs.dbos.dev/typescript/reference/methods)). Net effect for your case: rows stamped with an old non-NULL version are dequeued **only** by a process of exactly that version. "Latest" self-hosted is simply the highest-timestamp row, and every launch registers a version — so an unpinned deploy becomes latest and then refuses its predecessor's stamped work. The v4.24 release note states the same contract: "No-version workflows are only dequeued by latest-version executors" ([releases](https://github.com/dbos-inc/dbos-transact-ts/releases)).

This is why the spike's pin worked: a pinned, *unchanged* string makes the post-redeploy process simultaneously latest (so its dequeue filter tolerates NULLs) and version-matched to its own earlier rows. Changing the pin value on each deploy reproduces the strand — the version filter is exact-match with no ordering.

**Default (unpinned) version = MD5 of workflow function text.** `DBOSExecutor.init()` computes a version only when none was supplied, and `computeAppVersion()` uses `crypto.createHash('md5')` over `.map((i) => i.origFunction.toString())` — `Function.prototype.toString()` of the registered workflows, with the comment "This is guaranteed to be stable given identical source code because it uses an MD5 hash" ([v5.3 dbos-executor.ts](https://raw.githubusercontent.com/dbos-inc/dbos-transact-ts/v5.3/src/dbos-executor.ts)). The only `package.json` read in that path supplies `dbosVersion` (the SDK's own version) or, in `readConfigFile()`, a fallback *application name* ([v5.3 utils.ts](https://github.com/dbos-inc/dbos-transact-ts/blob/v5.3/src/utils.ts), [v5.3 config.ts](https://github.com/dbos-inc/dbos-transact-ts/blob/v5.3/src/config.ts)) — so a third-party summary attributing the version to `package.json` is wrong on this point. Operational consequence: because the hash is over the *emitted* function text, a rebuild that changes emitted bodies (different tsconfig target, a wrapper, a minifier) changes the version even if the logic did not — although DBOS cannot be bundled anyway ("cannot be bundled with … Webpack, Vite, Rollup, esbuild, Parcel … must be treated as an external library", [integrating-dbos](https://docs.dbos.dev/typescript/integrating-dbos)). Python's default *appears* to be the same shape (MD5 over workflow source, sorted order) — one search-result snippet of `_dbos.py` says so and was not read in full.

**Patching (`DBOS.patch`) — the replay-branch tool.** TS `DBOS.patch(patchName: string): Promise<boolean>` returns `true` if the marker was inserted *or already present*, `false` if a different checkpoint already occupies that history position ("the workflow should run unpatched"); `DBOS.deprecatePatch(patchName)` "safely bypass[es] a patch marker … Always returns `true`" ([workflows-steps](https://github.com/dbos-inc/dbos-docs/blob/HEAD/docs/typescript/reference/workflows-steps.md)). Both require `enablePatching`/`enable_patching`, otherwise `DBOSException` ([Python configuration](https://github.com/dbos-inc/dbos-docs/blob/HEAD/docs/python/reference/configuration.md)). Python adds async forms: use `await DBOS.patch_async()` / `deprecate_patch_async()` in coroutine workflows, because the sync versions raise inside a running loop ([Python upgrading](https://docs.dbos.dev/python/tutorials/upgrading-workflows)). Mechanics are **positional, not version-range based**: `patch()` "attempts to insert a 'patch marker' at its current point in your workflow history (this is a new row in the `operation_outputs` table)"; deprecated markers stop new inserts while old runs "continue past that patch marker, safely ignoring it"; removing a patch too early (or missing one) throws `DBOSUnexpectedStepError` ([TS upgrading](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)). There are no branch IDs and no version ranges — the difference from Temporal is that DBOS keys off history position plus a durable marker row rather than worker build IDs or a versioned branch API. And the pinning side effect matters here: "If you enable patching and don't set `applicationVersion`, DBOS uses the fixed application version `PATCHING_ENABLED`" (same page, corroborated by `globalParams.appVersion = 'PATCHING_ENABLED'` in [src/dbos.ts](https://raw.githubusercontent.com/dbos-inc/dbos-transact-ts/main/src/dbos.ts)) — i.e. enabling patching is itself a coarse pin that lets newer code recover older runs.

**fork / rewind for already-stranded work.** TS: `DBOS.forkWorkflow<T>(workflowID, startStep, options?: { newWorkflowID?, applicationVersion?, timeoutMS?, queueName?, queuePartitionKey?, replacementChildren? })`, where "any steps whose ID is less than `startStep` will not be re-executed" and `applicationVersion` "Defaults to the original workflow's application version. Useful for 'patching' workflows that failed due to a bug in the previous application version" ([TS methods](https://docs.dbos.dev/typescript/reference/methods)). Python: `DBOS.fork_workflow(workflow_id, start_step, *, application_version=None, queue_name=None, queue_partition_key=None, replacement_children=None, timeout_seconds=None)` — **no `newWorkflowID` argument**; the new ID comes from `with SetWorkflowID("..."):` ([Python contexts](https://docs.dbos.dev/python/reference/contexts)). `rewindWorkflow` / `rewind_workflow` is the in-place twin: same ID, discards steps ≥ `startStep`, only terminal workflows (SUCCESS/ERROR/CANCELLED/MAX_RECOVERY_ATTEMPTS_EXCEEDED), child workflows untouched, streams append-only. Portability trap: Python's `StepInfo.function_id` is one-indexed, TypeScript's `functionID` is zero-indexed with `startStep` defaulting to 0, so step numbers are not interchangeable ([Python contexts](https://docs.dbos.dev/python/reference/contexts)). Fork lineage is queryable — `WorkflowStatus.forkedFrom`/`wasForkedFrom`, and `listWorkflows` accepts `forkedFrom`/`wasForkedFrom`/`isFork`/`parentWorkflowID`.

**Official single-host rollout without Conductor.** Blue-green by version: "launch new processes running your new code version, but retain some processes running your old code version. Direct new traffic to your new processes while your old processes 'drain' and complete all workflows of the old code version." Directed enqueue uses `getLatestApplicationVersion()`; draining is checked with `DBOS.listWorkflows({ applicationVersion: "1.0.0", status: ["ENQUEUED","DELAYED","PENDING"] })`; "scheduled workflows are automatically enqueued to their owning application's latest version"; rollback is `setLatestApplicationVersion("1.0.0")` ([TS upgrading](https://docs.dbos.dev/typescript/tutorials/upgrading-workflows)). Python publishes the identical procedure with `get_latest_application_version()`, `SetEnqueueOptions(app_version=...)`, `list_workflows(app_version=..., status=[...])`, `set_latest_application_version(...)` ([Python upgrading](https://docs.dbos.dev/python/tutorials/upgrading-workflows)). On a genuinely single host without a second machine, "retain old processes" means two processes side by side for the drain window, or fork/rewind the residue onto the new version. Recovery scoping is documented: single server, no Conductor — "each time you restart your application's process, DBOS recovers all workflows that were executing before the restart (all PENDING workflows)"; distributed — set an executor ID so a restart "only recovers pending workflows assigned to that executor ID and owned by that application" ([workflow-recovery](https://docs.dbos.dev/production/workflow-recovery)).

**Dead-letter.** `maxRecoveryAttempts`/`max_recovery_attempts` is a *workflow* option, default **100**: "If a workflow exceeds this limit, its status is set to `MAX_RECOVERY_ATTEMPTS_EXCEEDED` and it is no longer automatically recovered" ([workflows-steps](https://github.com/dbos-inc/dbos-docs/blob/HEAD/docs/typescript/reference/workflows-steps.md)). There is no recovery key in `DBOSConfig` and no per-queue attempt setting on the pages read; inspection is by status filter, not a dedicated DLQ endpoint. Recovery is the right remedy and exists: `resumeWorkflow` works on `MAX_RECOVERY_ATTEMPTS_EXCEEDED` runs.

## 3. Agent-orchestration control-loop features

**Queues.** Declaration happens after `launch()`. TypeScript: `await DBOS.registerQueue(name, { globalConcurrency, workerConcurrency, rateLimit: { limitPerPeriod, periodSec }, partitionConcurrency, partitionWorkerConcurrency, partitionRateLimit, minPollingIntervalMs (default 1000), onConflict: 'update_if_latest_version' | 'always_update' | 'never_update' })` → `Promise<WorkflowQueue>` ([TS queues reference](https://docs.dbos.dev/typescript/reference/queues)). Python: `DBOS.register_queue(name, global_concurrency=…, worker_concurrency=…, limiter={"limit":…, "period":…}, partition_concurrency=…, partition_limiter=…, polling_interval_sec=1.0, on_conflict=…)`; `Queue` cannot be constructed directly — 3.3.0 raises `DBOSException("Queue objects cannot be constructed directly. Declare a queue with DBOS.register_queue(...)")`, and `concurrency=` is deprecated in favour of `global_concurrency` ([Python queues](https://docs.dbos.dev/python/reference/queues), [3.3.0 _queue.py](https://github.com/dbos-inc/dbos-transact-py/blob/3.3.0/dbos/_queue.py)). Queue names starting `_dbos_` are reserved, and queues are owned per application — only the owner dequeues.

**Enqueue.** TS: `DBOS.startWorkflow(fn, { queueName, enqueueOptions: { deduplicationID, duplicationPolicy, priority, delaySeconds, queuePartitionKey } })(args)`, plus `DBOS.enqueueWorkflowWithOptions` (+`…Portable`), `DBOSClient.enqueue`, and the PL/pgSQL `dbos.enqueue_workflow(...)`. Python: `DBOS.enqueue_workflow("queue", fn, *args)` or `queue.enqueue(...)`, with per-enqueue options via the **context manager** `with SetEnqueueOptions(deduplication_id=…, duplication_policy=…, priority=…, delay_seconds=…, app_version=…, queue_partition_key=…)` — a real ergonomic split between the SDKs. Enqueuing to an unregistered queue leaves the workflow `ENQUEUED`. Dedup (TS): only one workflow per dedup ID at a time; a second enqueue while one is `ENQUEUED`/`DELAYED`/`PENDING` raises `DBOSQueueDuplicatedError`, and `duplicationPolicy: 'return-existing'` returns a handle instead — good for "one control-loop tick per repo" semantics.

**Ordering, limits, partitions.** FIFO within a priority. Rate limit = "N starts per period", global across processes. Partitioning is *declarative*: registering any `partition*` limit makes the queue partitioned and every enqueue must pass a key, else the workflow stays `ENQUEUED`; queue-wide limits still apply across partitions ([TS queue tutorial](https://docs.dbos.dev/typescript/tutorials/queue-tutorial)). Two documented disagreements to be aware of: priority numbering (TS `0` default/highest vs Python docs' 1…2,147,483,647 with unprioritized first) and dedup on partitioned queues (**Python source raises** "Deduplication is not supported for partitioned queues", while the TS reference describes dedup IDs as unique across all partitions).

**Persistence and re-pick.** Queue config lives in `dbos.queues`; each queued workflow is a `dbos.workflow_status` row carrying `queue_name`, `priority`, `deduplication_id`, `queue_partition_key`, `executor_id`, `recovery_attempts`, `owner_xid`, `rate_limited`, `schedule_name`, `started_at_epoch_ms` ([system-tables](https://docs.dbos.dev/explanations/system-tables)). Crucially for redeploys, both tutorials warn that `globalConcurrency` counts "any PENDING workflow on the queue … including workflows from previous application versions" — that plus version-matched dequeue is the mechanism your spike hit, and it is documented behaviour ([TS queue tutorial](https://docs.dbos.dev/typescript/tutorials/queue-tutorial), [Python queues](https://docs.dbos.dev/python/reference/queues): "an unset app_version is only dequeued by an executor running the latest registered application version").

**Scheduled workflows (cron).** The decorator is gone in both (Python 3.0, TS 5.0); schedules are rows in `dbos.workflow_schedules`. Python: `DBOS.create_schedule(schedule_name=…, workflow_fn=…, schedule="*/5 * * * *", context=…, queue_name=…, cron_timezone=…, automatic_backfill=…)`, `apply_schedules([...])`, plus `pause_schedule`, `resume_schedule`, `delete_schedule`, `get_schedule`, `list_schedules`, `backfill_schedule`, `trigger_schedule` — all after `launch()`; scheduled workflows must be plain functions/staticmethods, not bound methods ([Python scheduled](https://docs.dbos.dev/python/tutorials/scheduled-workflows)). TypeScript adds `updateSchedule(name, {…})` (changes only passed fields) alongside `createSchedule`/`applySchedules` (which *replaces* the whole definition) ([TS scheduled](https://docs.dbos.dev/typescript/tutorials/scheduled-workflows)). Cron dialect differs: Python uses **croniter** with `second_at_beginning` (5 or 6 fields) and evaluates **in UTC by default** (`cron_timezone`); TypeScript uses **node-cron** and evaluates **in the system's local timezone by default** (`cronTimezone`). Exactly-once is by idempotency key = schedule name + scheduled time, so multiple processes polling the same table cannot double-fire ([TS scheduled](https://docs.dbos.dev/typescript/tutorials/scheduled-workflows), [blog](https://www.dbos.dev/blog/workflows-as-code-dynamic-scheduling)). Missed ticks are replayed via `automaticBackfill: true` / `backfill_schedule`, which replaces the old `SchedulerMode.ExactlyOncePerInterval`; no `SchedulerMode.Immediate` value appears in any official page read, and the legacy enum's exact definition rests on a third-party wiki (`ExactlyOncePerInterval` vs `ExactlyOncePerIntervalWhenActive`) ([DeepWiki](https://deepwiki.com/dbos-inc/dbos-transact-ts/3.5-scheduled-workflows)).

**Human/external-agent signalling.** TypeScript: `DBOS.send<T>(destinationID, message, topic?, idempotencyKey?, options?: SendOptions)`; `recv<T>(topic?, options?: RecvOptions)` with `RecvOptions = { timeoutSeconds?, deadlineEpochMS?, pollingIntervalMs? }`, default 60 s; `setEvent<T>(key, value, options?)`; `getEvent<T>(workflowID, key, options?)` — `recv`/`getEvent` return `null` on timeout ([TS methods](https://docs.dbos.dev/typescript/reference/methods)). Python: `DBOS.send(destination_id, message, topic=None, *, idempotency_key=None, serialization_type=…, send_to_forks=False)`, `recv(topic=None, timeout_seconds=60)`, `set_event(key, value, *, serialization_type=…)`, `get_event(workflow_id, key, timeout_seconds=60)`, plus Python-only `get_all_events`, `send_bulk([SendMessage(...)])` and `*_async` coroutine variants ([Python contexts](https://docs.dbos.dev/python/reference/contexts)). A timed-out wait **returns null/None and the workflow keeps running** — not a failure — and the docs recommend a timeout even for waits that "should eventually complete" ([TS tutorial](https://docs.dbos.dev/typescript/tutorials/workflow-communication)). Delivery: messages are persisted, so "if `send` completes successfully, the destination workflow is guaranteed to be able to `recv` it"; exactly-once when sent from inside a workflow, and exactly-once from ordinary code requires `idempotency_key`. `recv` consumes FIFO per topic; sending from outside the app needs only the destination workflow ID (DBOS Client or `dbos.send_message` PL/pgSQL) — no reconciliation step is documented. Events: latest value always retrievable, and a value read inside a workflow is checkpointed so recovery reuses it even if the event changed. `recv` has one doc inconsistency: the tutorial shows `recv(topic?, timeoutSeconds?)`, the reference shows the nested `RecvOptions` object; the reference is the richer surface. Message storage is `dbos.notifications`; retention policy was not verified.

**Cancel / resume / fork.** `cancelWorkflow(workflowID, { cancelChildren? })` sets **CANCELLED**, removes the workflow from its queue, and interrupts "at the beginning of its next step" — an in-flight step is *not* interrupted, but TS steps can observe `DBOS.stepStatus.cancelSignal` (an AbortSignal, also fired on workflow timeout) and bail early. Python's equivalent is `StepOptions(preemptible=True)` for **async** steps only; `StepStatus` there exposes no cancel signal. `resumeWorkflow(workflowID, { queueName? })` restarts from the last completed step and works for both CANCELLED and `MAX_RECOVERY_ATTEMPTS_EXCEEDED` runs; `resumeWorkflows` is all-or-nothing; missing IDs throw `DBOSNonExistentWorkflowError`. All three (`cancel`/`resume`/`fork`) are also CLI commands — `npx dbos workflow cancel|resume`, `dbos workflow cancel|resume` — so a control loop can shell out instead of importing the SDK ([TS workflow management](https://docs.dbos.dev/typescript/tutorials/workflow-management)).

**Attempt limits and dead letter.** Per-workflow only (`@DBOS.workflow({ maxRecoveryAttempts })` / `registerWorkflow(fn, { maxRecoveryAttempts })`, Python `@DBOS.workflow(max_recovery_attempts=…)`), default 100. No `DBOSConfig` key, and no per-queue attempt setting was found. Inspection is status filtering: `listWorkflows({ status: 'MAX_RECOVERY_ATTEMPTS_EXCEEDED' })` / `list_workflows(status=...)`; the status set is ENQUEUED / DELAYED / PENDING / SUCCESS / ERROR / CANCELLED / MAX_RECOVERY_ATTEMPTS_EXCEEDED. For a control loop this is the practical DLQ: poll that status, then `resumeWorkflow` after fixing code, or `forkWorkflow(..., { applicationVersion })` to move it onto new code.

**Sharing one Postgres database with application tables.** System tables live in schema **`dbos`** (Python `dbos_system_schema`, TS `systemDatabaseSchemaName`, CLI `--schema`). Neither `DBOSConfig` has an application-database URL any more — Python 3.0 removed `database_url`/`application_database_url` along with `@DBOS.transaction` (source rejects them via `REMOVED_DATABASE_URL_KEYS`) and TS never had one; the app DB comes from each datasource's own URL, and docs are explicit that it "does not need to be the same database (or even on the same server)". **Co-commit works differently than "one transaction across two schemas":** each datasource keeps a checkpoint table *in the app database* — `datasource_outputs` (Python) / `transaction_completion` (TS) in a `dbos` schema by default — so your row and the exactly-once record commit in the same transaction, and on workflow completion the checkpoint row is deleted and the outcome recorded in the system DB ([Python transaction tutorial](https://docs.dbos.dev/python/tutorials/transaction-tutorial.md), [TS transaction tutorial](https://docs.dbos.dev/typescript/tutorials/transaction-tutorial.md)). App tables in `public` + DBOS in `dbos` inside one database is therefore exactly the documented shape. Caveat: the PL/pgSQL helpers (`dbos.enqueue_workflow`, `dbos.send_message`) "can only be called from code running in the same database". Pools are separate (`systemDatabasePoolSize` 10 TS, `sys_db_pool_size` 20 Python, datasource manages its own), and transaction isolation defaults **diverge**: Python datasources default to `SERIALIZABLE`, TS to the database default (`read committed`) ([Python datasources](https://docs.dbos.dev/python/reference/datasources.md), [TS datasource](https://docs.dbos.dev/typescript/reference/datasource.md)).

**Migrations.** Numbered and tracked in `dbos.dbos_migrations` (`version` = most recently applied). `run_migrations`/`runMigrations` default true; with it false, launch *verifies* and throws `DBOSInitializationError` if behind, while accepting a database that is ahead of the build. Commands: Python `dbos migrate`, TS `npx dbos schema` (no `npx dbos migrate` documented), code-level `DBOS.migrate`, `dbos migrate --print-migrations [all|NUMBER]` (output includes `CREATE INDEX CONCURRENTLY`, so it must not run inside a transaction block), plus a privileged `dbosctl sysdb migrate`. `dbos migrate` does **not** migrate datasource tables — use `SQLAlchemyDatasource.migrate` / `initializeDBOSSchema`. One hazard to internalise: `dbos reset` "drops the entire system database … including any application data stored in that database" ([Python CLI](https://docs.dbos.dev/python/reference/cli.md)).

## 4. Operational footprint, observability, pitfalls

**No extra server.** DBOS is an in-process library; all state is in Postgres; the only client deps are Postgres drivers. Conductor (WebSocket-connected, own Postgres, three containers) is optional and out of band — "If there is a Conductor outage, your workflows continue running durably and uninterrupted" ([Conductor blog](https://www.dbos.dev/blog/what-is-dbos-conductor)).

**Connections.** One system-DB pool per process: TypeScript `systemDatabasePoolSize` **default 10** (a source comment notes "of which the polling limiter already reserves half"), or inject your own `node-postgres` `Pool`. Python `sys_db_pool_size` → SQLAlchemy `pool_size: 20` with `max_overflow: 0` — a **hard cap of 20 per process** — plus `pool_timeout: 30`, `pool_pre_ping: True`, `application_name="dbos_transact"`, `connect_timeout` 10 ([3.3.0 _dbos_config.py](https://github.com/dbos-inc/dbos-transact-py/blob/HEAD/dbos/_dbos_config.py)). `sys_db_polling_concurrency` defaults to half the pool to stop polling from starving control-plane operations, and DBOS sets `idle_in_transaction_session_timeout` to 60 s. Docs guidance: check `SHOW max_connections`, "We do not recommend setting this to less than 5", and a workflow costs 2–3 writes plus one per step ([production checklist](https://docs.dbos.dev/production/checklist)). For a single Mac mini this is trivial; two processes (blue-green drain) + a `DBOSClient` are still well under 50 connections.

**Background activity.** LISTEN/NOTIFY is on by default (`useListenNotify`/`use_listen_notify` true; `notificationCoalesceMs` 10 ms, min 1) and "determines which notification triggers are created with the system database, so do not change it after the system database is first created" — turning it off falls back to polling with higher latency ([src/config.ts](https://github.com/dbos-inc/dbos-transact-ts/blob/HEAD/src/config.ts)). Named pollers (Python defaults): notification listener `notification_listener_polling_interval_sec` 1.0 s, notifier `notification_coalesce_sec` 0.01 s, scheduler `scheduler_polling_interval_sec` 30.0 s, `auto_upgrade_interval_sec` 30.0 s. Queues poll rather than LISTEN: `polling_interval_sec` 1.0 s with jitter and backoff under contention, and TS caps concurrent dequeuers with `maxConcurrentQueueDispatches` 3. Concurrency safety is a per-workflow `owner_xid` token re-checked inside every checkpoint transaction — no advisory locks. **No idle CPU/RAM figures are published anywhere**; DBOS sizes Postgres (4 vCPUs per 1000 actions/s), not the app.

**Observability.** Python: `pip install dbos[otel]` + `enable_otlp: True`, or register a global `TracerProvider` before constructing `DBOS` and DBOS spans join your traces; direct export via `otlp_traces_endpoints`/`otlp_logs_endpoints`. TypeScript: `@dbos-inc/otel` + `tracingEnabled: true` (external provider) or `enableOTLP: true` with `otlpTracesEndpoints`/`otlpLogsEndpoints`, wiring `new NodeSDK({ traceExporter: new OTLPTraceExporter({ url }) }).start()` **before** `DBOS.launch()` ([TS logging](https://docs.dbos.dev/typescript/tutorials/logging), [Python logging-and-tracing](https://docs.dbos.dev/python/tutorials/logging-and-tracing)). Coverage: one span per workflow and per step, hierarchical; enqueued workflows start a *new* trace unless wrapped in `PropagateOtelContext` (durably stored under `dbos.otelContext`); attribute naming switch `otel_attribute_format`/`otelAttributeFormat` = `"legacy"` (default: `operationUUID`, `applicationID`, `executorID`) or `"semconv"` (`dbos.operation.workflow_id`, `dbos.application.id`); custom spans via `DBOS.span`. Logs: `log_level` default INFO, `otlp_log_level`, `console_log_level`; TS `logLevel` default `info`, custom `DLogger` (which then owns level filtering), `addContextMetadata` default false.

**OSS vs Conductor.** Open source: the SDKs, `listWorkflows`, `listWorkflowSteps`, `getWorkflowStatus`, the CLI, fork/rewind/cancel/resume, OTel export. Conductor-only: Console UI and trace timelines, Prometheus metrics scraping, retention policies ("If you use Conductor, you can configure a retention policy … implying an OSS-only deployment must prune workflow history itself"), distributed/automatic recovery, `setAlertHandler` alerts. Licences: `dbos` 3.3.0, `@dbos-inc/dbos-sdk` 5.3.0 and `@dbos-inc/otel` are **MIT**; self-hosted Conductor ships under a proprietary, licence-key-gated licence.

**Pitfalls worth pre-empting.** (1) Redeploy stranding — documented behaviour, not a bug (see §1). (2) Version-string semantics: minting a new pinned string per deploy on one host reproduces the strand. (3) Hash fragility: the default version tracks emitted function text. (4) Mixed-major upgrades: DBOS 3.0 can process 2.x workflows but not vice versa — "Don't run DBOS 2.x and 3.0 processes concurrently with the same application version"; same for TS 5.0/4.x ([Python upgrading](https://docs.dbos.dev/python/upgrading)). (5) `globalConcurrency` counting prior-version PENDING work; docs recommend worker concurrency instead. (6) `deleteQueue` orphans: already-enqueued workflows "can no longer be dequeued, executed, or recovered", and a later same-named queue will pick them up. (7) Rewind does not re-run or roll back child workflows, and streams are append-only. (8) Long synchronous steps delay cancellation/shutdown because `preemptible` applies to async steps only. (9) `observabilityQueryTimeoutSec` 30 s — `listWorkflows` against an unpruned history fails rather than hangs. (10) Connection poolers must be used in **session** mode (LISTEN/NOTIFY is incompatible with transaction mode). (11) Python silently falls back to `sqlite:///{app_name}.sqlite` when no `system_database_url` is set — exactly the dev-only path the spike outgrew.

## 5. Comparison for a solo dev on one always-on Mac mini with Postgres 18, TypeScript on Bun

First, the important asymmetry the query's framing hides: **only DBOS transact has a documented per-version dequeue filter.** Absurd and pgflow have no version registry, Hatchet explicitly has "no equivalent" to patching, Restate versions by immutable deployments, and Temporal has the most rigorous model. DBOS's closest *replacement* is Hatchet; its closest *philosophical* peer is Absurd.

| Axis | Strongest for this setup | Where DBOS wins / loses |
|---|---|---|
| Footprint on one mini | **Restate** (one binary, but its own store) → **Hatchet Lite** | DBOS wins outright: in-process library, zero new daemons |
| Reusing existing PG 18 | **Hatchet** / DBOS (PG is source of truth); **Temporal documents PG only to 16.6** | Restate N/A (own storage); Absurd states "PostgreSQL (14 or later)" and never names 18 |
| Licence | **Hatchet**/**Temporal**/DBOS (MIT) | Restate is BSL 1.1, not OSI open source |
| Versioning / redeploy safety | **Temporal** (build-ID + patching), **Restate** (immutable deployments) | DBOS is out-classed on safety *and* ergonomics unless pinned; Hatchet offers only "new task definition + drain" |
| Queues / concurrency / rate limits / partitioning | **Hatchet** (CEL keys, five cancel strategies, static+dynamic rate limits) | DBOS has global/worker/partition concurrency + rate limits + dedup, but no CEL keying; Restate's virtual objects add per-key single-writer ordering DBOS lacks |
| Cron | **Hatchet** / Temporal (depth unverified here) | DBOS schedules are durable DB rows with name+time idempotency — structurally comparable |
| Durable sleep / wait-for-signal | **Hatchet** (`ctx.aio_wait_for_event`, slot released while sleeping), **Restate** (awakeables) | DBOS holds the workflow's process context and has no UI for waiting runs; `recv` timeouts are coarser than CEL lookback waits |
| Cancel / DLQ | **Hatchet** (retry semantics, cancel strategies) | DBOS: `cancel`/`resume` + `MAX_RECOVERY_ATTEMPTS_EXCEEDED` status filter — adequate, no dedicated DLQ API |
| TS SDK + Bun | **Restate**/**Hatchet** (JS/TS runtimes) | DBOS TS SDK is Node-only (`engines >=20`, CI Node-only); Temporal workers are explicitly Node-only in practice |
| OTel | **Hatchet** (auto spans + W3C propagation into metadata) | DBOS emits hierarchical workflow/step spans and logs; Hatchet's built-in collector + Prometheus is more turnkey |
| Ops cost / upgrade cadence | **Restate** (1 binary) vs **Hatchet** (3 components, frequent releases) | DBOS wins: library upgrades ride your own deploys |

**Absurd** (`earendil-works/absurd`, Apache-2.0, **0.5.1**, 2026-10-20; npm `absurd-sdk` 0.5.1, peer `pg ^8.0.0`, `engines node >=18`) is a *SQL engine* — "one SQL schema as the engine", "thin SDKs with most of the durable behavior in stored procedures" — with per-queue tables (`t_` tasks, `r_` runs, `c_` checkpoints, `e_` events, `w_` waits, `i_` idempotency for partitioned queues). A step is a checkpoint whose result "will never execute again"; workers claim with a lease (default `claimTimeout` 120 s) extended on every checkpoint, and docs state "brief overlapping execution is possible", i.e. **at-least-once with cached-step idempotence**. Versioning: none. "A completed step returns its cached value forever", and the prescribed migration is renaming the step (`process-payment:v2`), normalizing old results, or registering a new task name — with the explicit warning that an old suspended task "would however then invoke process-payment:v2", so side effects need dedup keys. Because any worker claims any task on the queue, the DBOS "new version won't dequeue old version's rows" failure mode has no analogue — at the cost of no deterministic replay and no per-run code pin. Install burden is one `.sql` file plus `absurdctl init/migrate` (`--dump-sql` to fold into your own migrator); **no required extensions**, `pg_cron` optional; docs prerequisite "PostgreSQL (14 or later)" with **no PG-18 statement**; 0.5.0 dropped `uuid-ossp` and uses "PostgreSQL's native UUIDv7 function when available". Bun is not mentioned in its TypeScript SDK docs (install docs describe "modern Node.js" with native type stripping).

**pgflow** (`pgflow-dev/pgflow`, Apache-2.0, CLI `pgflow` 0.17.2, public beta) is the richest workflow model — DAG steps with `dependsOn`, map fan-out with per-element retries, per-step attempts/backoff/`startDelay`/conditions, per-step private queues — but it is Supabase-shaped: migrations install/upgrade **pgmq** (1.5.1+), add **Supabase Realtime** broadcasts (`step:started/completed/failed`) and rely on cron (`ensure_workers()` runs every second, stalled-task requeue via cron). Even the documented Node/**Bun** long-lived worker mode requires `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in addition to `DATABASE_URL`, has no built-in HTTP health endpoint, and expects the host to restart crashed workers because `ensure_workers()` "never invokes process workers". Redeploys are a documented manual dance — disable `pgflow.worker_functions.enabled`, set `pgflow.workers.deprecated_at`, drain by polling `pgflow.step_tasks`, deploy, re-enable — because `ensure_workers()` would otherwise restart old code within a second; queue mode is immutable per slug (change it → new flow slug) and `delete_flow_and_data()` destroys all runs. There is also an unrelated Elixir project of the same name (`agoodway/pgflow`).

**pg-boss** and **Graphile Worker** were verified only at the registry level this run — behaviour (archiving, partitioning, cron, singleton keys, LISTEN/NOTIFY, pool footprint, PG 18) is **unverified**. Registry: pg-boss **12.38.0** (2026-10-13, MIT, deps `pg ^8.23.1`, `cron-parser`, `rrule-temporal`, peer `@opentelemetry/api`, `engines node >=22.12.0`); Graphile Worker **0.18.0** (2026-09-08, MIT, deps `pg ^8.11.3`, `graphile-config`, `engines node >=22.18.0`; its `rc`/`next`/`canary` dist-tags are stale at 0.17.0-rc.0). Neither is a durable-execution engine with replay semantics, so they are job queues for a control loop rather than workflow runtimes.

**Hatchet** (MIT, engine v0.110.5) is the closest drop-in: "PostgreSQL is the source of truth", transactional state transitions, RabbitMQ optional, self-hosting = API server + engine + Postgres + dashboard with **Hatchet Lite** as a single docker image intended for "development, testing, or low-throughput production" (exactly your shape). Durable tasks checkpoint on every wait or child spawn and are evicted while waiting, so a sleep holds no worker slot. Flow control beats DBOS for a control loop: CEL-keyed concurrency with `max_runs` and strategies `GROUP_ROUND_ROBIN`/`CANCEL_IN_PROGRESS`/`CANCEL_NEWEST`/`CANCEL_QUEUED_EXCEPT_NEWEST`/`CANCEL_QUEUED_EXCEPT_OLDEST` (shared strategies and CEL `max_runs` need engine ≥ 0.106.0), dynamic (CEL-keyed, globally shared) and static (`put_rate_limit(key, units, duration)`) rate limits that re-queue when exceeded, per-task-definition queues routed by worker affinity, and `slots` per worker. Its weak axis is exactly your spike's concern: "Temporal gives you patching APIs … Hatchet has no equivalent: for breaking changes to durable tasks, we recommend deploying a new durable task definition and letting the old work drain" — coarse but honest, and structurally the same shape as DBOS's pinned `applicationVersion`. OTel is first-class (`hatchet-sdk[otel]`, `HatchetInstrumentor()`, `hatchet.start_step_run` / `hatchet.durable.wait_for` spans, W3C traceparent in `additionalMetadata`). PG 18 is not documented either way ("names PostgreSQL, no version range"). Your prior note from the 2026-09-24 spike recorded a compose pin of `postgres:15.6`, a `btree_gist` extension requirement for v0.87.6+ and `DATABASE_ENFORCE_UTC_TIMEZONE=true`; this run's read of the self-hosting page does not state a version range or extensions, so PG 18 remains undocumented in both accounts.

**Restate** (server v1.8.1, **BSL 1.1** — "not an Open Source license", Additional Use Grant permits private production self-hosting, change date 4 years, change licence Apache-2.0) has the strongest execution and versioning model and the wrong storage bet for you: one Rust binary carrying a Raft metadata store, the Bifrost durable log and a RocksDB partition store in `restate-data` — **no Postgres at all**, so PG 18 is moot and you gain a second stateful thing to back up (single-node backup = stop server + copy/snapshot the directory; cluster restore "would currently require manual intervention"). Versioning is immutable deployments: requests start and end on the same version because retries always hit the same endpoint, "no version compatibility logic is needed in your code"; journal-breaking changes (reordering/adding/removing SDK ops, changed inputs, changed control flow) fail with RT0016, and the fix for in-flight invocations is pause-and-resume on the new deployment. Virtual Objects give at-most-one write handler per key with concurrent shared read handlers — a natural partitioned queue with concurrency 1 for a heavy global step.

**Temporal** (server v1.32.1, MIT) is the heavyweight and the most correct on redeploy: Worker Versioning with deployment name + Build ID, Pinned vs Auto-Upgrade (with ramp percentages), Inactive/Active/Draining/Drained, and version inheritance for pinned children/continue-as-new/certain retries (cron never inherits), plus `patched`/`deprecatePatch` retained as the manual escape hatch for auto-upgrade workflows. Two decisive negatives for you: its actively tested Postgres versions are **13.18, 14.15, 15.10 and 16.6 — PG 18 is not listed** (and SQLite is "meant only for development and testing"), and the TypeScript SDK is officially supported only on Node 20/22/24 — `@temporalio/client` is merely "believed to work properly on … Bun" while workers need Node-API native modules, `worker_threads`, `vm`, `AsyncLocalStorage` and `async_hooks`, and the maintainers "strongly discourage running Temporal Workers in anything except authentic Node.js at this time".

**Practical read for your stack.** If the decision is "keep this shape, move the ledger to Postgres", DBOS is the cheapest fit: it is the only candidate that is simultaneously a library (no daemon on the mini), Postgres-backed, MIT, cron-capable, and equipped with the exact control-loop primitives you listed — and its redeploy failure is now a known, mechanically understood configuration issue rather than a surprise. The cost is that the TypeScript SDK is Node-only, so the Bun-first services would either run DBOS under Node or take the risk on Bun with a known OTel-span gap and a track record of Bun-specific breakage being fixed after the fact. If Bun support is non-negotiable, Hatchet is the strongest Postgres-native alternative (MIT, CEL flow control, drain-based redeploys); if correct versioning is the top priority, Temporal or Restate win, at the price of a daemon, and for Temporal an unsupported Postgres 18.

**What remains open.** `pg` under Bun has no authoritative statement either way; the Python scheduler implementation and the `3.3.0`-tag fork/rewind source were not read (signatures verified against current docs and default-branch source); `dbos.notifications` / `dbos.workflow_events` columns and retention are unverified; DBOS's docs never name a supported PostgreSQL version, so PG 18 support rests on "any Postgres" wording rather than an explicit statement; pg-boss and Graphile Worker behaviour, including any PG-18 statements, was not verified in this run.
