## Bottom line

- **Learning from corrections:** PagerDuty is the only vendor whose docs describe a grouper trained by operator corrections — manual merge and "move alert to a different incident" in the web app, explicitly *not* via API — and it publishes no cadence, no metric, no label export and no inspectable learner state beyond a "Reset Learner Cache" button; BigPanda records Splits and Merges as per-pattern dashboard counters for human review, Datadog calls manual removal of alerts from an intelligently correlated case "feedback for model retraining", and Rootly/incident.io/Keep disclose no verified corrective-training loop in the pages retrieved.
- **Similarity retrieval:** Similarity over past incidents is, everywhere it exists, an investigator-facing layer fused with deterministic keys — never the grouping gate — and no vendor publishes a vector store, the embedded text spec, or a numeric similarity cutoff; the deterministic layers that *do* gate grouping are Keep's fingerprint fields (subset or full, no score at all), Datadog Incident AI's 20-minute declaration window, incident.io's fixed product-wide 10-minute dedupe window, and PagerDuty's rolling window plus 24-hour incident-age and 5-minute dependency rules.
- **LLM restricted to ambiguous residue with calibrated confidence:** no vendor documents this architecture — incident.io ships deterministic grouping with similarity grouping as a separate opt-in beta and degrades on wall-clock timeouts and rate limits rather than on confidence; Rootly's LLM is an investigation agent whose confidence bands and explicit "Inconclusive — needs human" abstention live in AI SRE, not grouping; PagerDuty's grouping model publishes no confidence score; and no vendor publishes calibration method, token budget for grouping, or LLM grouping decisions logged and reused as labels.
- **Mid-investigation merge/split:** PagerDuty has the most complete documented semantics (target must be open, sources resolved with reason "Merged", 1,000-alert combined cap, responders not carried over, no unmerge — reversal is per-alert "Move → Create new incident"), BigPanda and PagerDuty both expose machine merge calls, incident.io hosts its own OAuth MCP server, and nothing anywhere emits a merge as a structured labelled alert-pair feed.

## 1. What actually feeds back into grouping

**PagerDuty — the only documented closed loop.** The Intelligent Alert Grouping doc states: "The algorithm also reacts to feedback from you and your team. The best way for the algorithm to learn and adapt is to manually merge related incidents and to manually move alerts to a different incident when they are not related." The exclusion matters for any automated pipeline: "Merging and unmerging alerts through the API does not factor into the Intelligent Alert Grouping algorithm. Only manual merges and unmerges in the PagerDuty web app influence the algorithm." The vendor also warns against seeding it: "PagerDuty strongly recommends against sending test data to try to influence the algorithm, as this can result in unpredictable behavior."

Operator-exposed state is thin. The only controls are **Advanced Options → Configure Grouping Fields** (up to five PD-CEF/custom fields, max 1,000 characters across all selected fields, Summary the only required field) and **Reset Learner Cache** (to be used after significant data-structure changes or a test period). No cadence, no evaluation metric, no label export, no way to inspect what was learned. Thresholds that *are* exposed: a per-service rolling grouping window measured from the most recently grouped alert, with a "Recommended" value computed from historical average inter-alert time (the doc warns a larger window raises overgrouping risk); incident age < 24 h; content-based window 5 min–24 h. Content-based grouping is deterministic and matches only on exact field equality (Class, Component, Group, Severity, Source, Summary or a Custom Details field, with an All/Any aggregate) and keeps no accumulated state: "Content-Based Alert Grouping will ignore any previously-saved criteria and will start grouping alerts into a new incident every time you save." Four methods are selectable — Intelligent, Alert Content, Intelligent + Alert Content, Time only. Grouping-setting API type values (`intelligent`/`time`/`contentBased`/`contentBasedIntelligent`, aggregate `any|all`) appear only in the Terraform/Pulumi provider docs.

**BigPanda — corrections are a KPI, not a training signal.** Correlation is a deterministic pattern engine over four properties (source system, tags, time window, optional filter), up to five tags, default 120-minute window, evaluated in under 100 ms. Split/Merge is described as "a direct feedback mechanism in the tool for immediate feedback – review this in a dashboard" — human review, with continuous stakeholder validation recommended instead of automatic retraining. The evaluation surface is Unified Analytics → *Correlation Patterns*, which reports per pattern: Correlation %, Alert Count, Incident Count, Actioned/Non-Actioned Incidents, "Splits - The number of splits that occurred on incidents created by the correlation pattern", Merges, plus Total Splits, Total Merges and a Splits & Merges Trend graph. No automatic re-weighting is described anywhere on either page.

**Datadog** — manual removal of alerts from intelligently correlated cases is described as "feedback for model retraining"; no mechanism, cadence or storage is documented. **Rootly, incident.io, Keep** — no corrective-training loop could be verified. Rootly's docs index describes leader-driven Alert Grouping (time windows, fields, attributes), Marking-as-Duplicate via web/Slack/API, Sub-Incidents as the split affordance, and AI SRE "outcome labels … accuracy ratings" plus "Atlas Memory" notes learned from investigations, but no corrective-training loop is documented on those pages, so the learning behaviour is unconfirmed. incident.io's index enumerates API tag groups only. Keep's docs index separates "Manual Correlation Rules", "Topology Correlation", "Fingerprints" and "Deduplication" from "AI Correlation" and "AI Semi Automatic Correlation" — distinct surfaces, but page bodies unverified.

**Practical consequence:** no platform retrieved exposes a correction as a machine-readable labelled pair (fingerprint-A ↔ fingerprint-B, actor, timestamp). If you want supervised signal you must harvest it from audit/timeline events per vendor — and PagerDuty will not accept it from an automation at all.

## 2. Similarity retrieval of past incidents

**Keep (open source, v0.54.3)** is the only codebase inspected. Grouping is deterministic: "Partial" mode groups alerts whose specified fingerprint fields match (examples: `service` + `error_message`), "Full" mode treats alerts as identical when all fields match except ignore fields; no similarity score or threshold. `pyproject.toml` contains **no pgvector or any other vector-DB dependency** — only `openai`. The AI path is `keep/api/bl/ai_suggestion_bl.py`: `suggest_incidents` builds a prompt from the full alert JSON plus topology JSON, calls an OpenAI chat completion with a JSON-schema response format, and asks for a 0.0–1.0 `confidence_score` and `confidence_explanation`. That is LLM clustering with a self-reported confidence, not embedding retrieval over past incidents; suggestions are cached by a sha256 hash of the alert fingerprints (a cache, not a label store). Repo also carries `logmine` template mining and an `alert_deduplicator` module.

**PagerDuty** keeps two clearly separated, investigator-facing features, neither in the paging decision. *Past Incidents* is ML similarity restricted to **the same service**, driven by four factors: semantics of the incident title, which responders responded to past incidents, past incident duration, and creation date/time; results sort by Recent or Relevant; six-month heat map; no store or numeric cutoff published. *Related Incidents* uses "a completely online and real-time machine learning algorithm **and service dependency data**"; ML relations weigh creation-time proximity, alert-metadata relatedness and human thumbs up/down, while dependency relations are declared when incidents fire within five minutes and one service depends on the other or they share a parent business service — similarity explicitly fused with topology and a time bound.

**Rootly** matches by meaning, not keyword, over 180 days by default, excluding cancelled incidents; "Similar wording alone doesn't qualify"; matches are weighted by shared services, comparable severity, same owning team and recency. Fields read are title, summary, severity, services, plus resolution notes/retrospectives for "what fixed it". Match cards offer Mark as related / Not related, which trains the model for that team. AI SRE retrieves up to **3** similar incidents for initial hypotheses even when the toggle is off; past *alerts* are matched by keyword across summary, labels, source and description over 180 days — a separate lexical path. No vector store or threshold published.

**Datadog** — Incident AI's related-incident detection is purely temporal ("automatically flags related incidents if they are declared within 20 minutes of each other"); finding related incidents is otherwise natural-language chat over incident history. Bits Investigation knowledge sources are runbooks, a `bits.md` context file and post-investigation "memories" that Bits "dynamically selects … in future investigations" and applies "in similar contexts" — semantic reuse claimed, no index or threshold documented.

**incident.io** — duplicate prevention is a fixed 10-minute window over Triage/Active incidents and is not personalised: "the 10-minute time window is a product-wide setting and cannot be customized." Nexus "past incidents" matches on symptoms, systems involved and "the shape of the failure" — mechanism-free prose, no store or cutoff published.

Grafana Sift and BigPanda similarity mechanisms could not be verified.

## 3. LLM confined to the ambiguous residue, with calibrated confidence

Nobody documents it. What exists is deterministic grouping, optionally plus a separate ML/AI layer that always runs when enabled.

**incident.io** is explicitly deterministic-first: group by time window (fixed or extending, up to 48 h) or by matching attributes on a route; AI ("Alerts that look similar") is a **separate, opt-in beta** third option, not a fallback for alerts the rules failed on. The documented degradation paths are operational, not confidence-based: an alert waiting more than 30 seconds for AI grouping is handled on its own and routed immediately, and above a rate limit of **120 alerts per minute for a single team** the excess is routed as if there were no group; AI grouping only spans one team and optional required-shared attributes such as service. The alert timeline shows "why we grouped the alerts together". No confidence score, threshold, calibration, token budget or decision-logging-as-label is described. Their editorial blog names "confidence thresholds, route low-confidence to humans" as the standard industry mitigation and recommends measuring false-negative rate on P0/P1 plus override rate against a customer's own historical incidents — presented as guidance, not a shipped mechanism.

**Rootly** keeps grouping fully deterministic: destinations (service/team/escalation-policy scope), a rolling window of 5 minutes to 7 days anchored to the last alert, and content matching on title/description/urgency/external_url/JSONPath fields with operators such as contains, regex, starts-with; a leader alert pages and members join silently. Where confidence *is* documented is AI SRE, not grouping: outcome bands "High confidence, Medium confidence or Low confidence", the abstention state **"Inconclusive — needs human"**, "Suspected area, marked Suspected, not confirmed", plus "Blocked" and "Failed", with "The final outcome depends on checks Rootly runs against the recorded evidence, so the model can't declare a root cause on its own." Investigation Rules are the human gate — Manual / Auto-run / Paused with a match preview and guidance to "Keep noisy or experimental alert classes on Manual until the rule's match preview and completed results look reliable"; results can be rated, but "A rating doesn't change the report."

**PagerDuty** uses an ML textual-similarity model gated by deterministic criteria (most recent alert inside the rolling window, incident < 24 h old, algorithm judges similar), analysing up to five configurable fields capped at 1,000 characters total — an input-cost cap — with no numeric confidence score or calibration published. Its one headline number is an internal case study without methodology: "PagerDuty's DataOps team uses Intelligent Alert Grouping … they achieved a 37% reduction in incidents and increased efficiency two to three times, allowing 10 FTEs to support a workload that would typically require 20–30 FTEs."

**Datadog** documents pattern-based correlation you configure (grouping tags, minimum alert count, correlation window, deduplication window) plus ML enrichment on top: "Datadog also uses machine learning to automatically enrich your pattern with related Datadog Monitor events", while *Intelligent Correlation* is a separate no-configuration ML model reasoning over topology, tags, attributes and trigger time. The two descriptions sit awkwardly together (enrichment layer vs standalone model), and neither documents a confidence score, abstention path, token/latency budget or label storage.

**Keep** advertises "AIOps 2.0 - AI-powered correlation and summarization" with pluggable backends for "Enrichments, Correlations and Incident Context Gathering" (Anthropic, OpenAI, DeepSeek, Ollama, LlamaCPP, Grok, Gemini); its index distinguishes deterministic surfaces from "AI Correlation" and "AI Semi Automatic Correlation", implying a human-in-the-loop AI path, but the code inspected shows only whole-alert LLM clustering (section 2) with a model-reported confidence.

No vendor in this set publishes precision/recall/framework-level evaluation of grouping, methodology included — so there is nothing to benchmark your 0.889 deterministic F1 or 60.1% golden grouping agreement against.

## 4. Merge/split mid-investigation, reversibility, audit

**PagerDuty** is the richest: merge from the Incidents list, an incident's details page, a service's details page, or mobile; the target must be open (you cannot merge into a resolved incident); source incidents resolve with resolution reason listed as **Merged** and reference the target; the alert dedup key does not change, the alerts relocate; combined alerts are capped — "An incident cannot have more than 1,000 alerts. You cannot merge incidents if their combined total exceeds 1,000 alerts." Responders and subscribers of source incidents are **not** carried over (they must be re-added; the target's responders receive all alerts and appear in the Timeline tab); bidirectional integrations show merged incidents as resolved and referencing the new target; cross-service merges create impacted services. Webhooks: the source resolves with `resolve_reason` type `merge_resolve_reason` carrying a reference to the target, and subsequent updates are sent only for the target's service. There is **no documented unmerge** — reversal is per-alert via Move → "Create new incident", or an alert's "Move to Another Incident". The grouping model is documented as learning from prior incident merges, which is the only vendor-captured learning signal from this affordance. A third-party API mirror documents the merge as `PUT https://api.pagerduty.com/incidents/{id}/merge` (target open; only incidents with alerts or manually created in the UI; write permission required); PagerDuty's own reference was not retrieved, so treat endpoint semantics as provisional.

**BigPanda** is the cleanest machine surface: `POST /resources/v2.0/environments/{environment_id}/incidents/{incident_id}/merge` with `source_incidents[]` and `comment` (202 Accepted, 5 req/s, max 300 alerts correlated into one incident), a Split Incident endpoint alongside it, and full CRUD plus ordering for Correlation Patterns.

**Rootly** treats grouping as configuration, not an operator action: rule-driven destinations and windows produce a leader alert plus silent members that inherit leader status changes and appear on the group timeline; non-paging alerts are never grouped; no manual mid-investigation merge or split control appears in the grouping docs (Sub-Incidents is the split affordance per the docs index, unconfirmed at page level).

**Datadog**: the retrieved portion of the Incidents API v2 index lists create/get/update/delete, search, postmortem attachments, incident impacts (`/api/v2/incidents/{incident_id}/impacts`), integration metadata, todos, config and import — no merge or split endpoint; the index was truncated (first 80,000 of 115,603 characters), so absence is not established.

**incident.io**: hosts its own MCP server at `https://mcp.incident.io/mcp` authenticated over OAuth, with the tool surface owned by incident.io and re-discovered on each resync rather than published as a fixed list; a 2026-08-18 changelog states operators "can now merge a private incident into another private incident from the dashboard, without the previous public-first workaround"; `incident-alerts-v2` create exists to "Attach an alert to an incident, creating the connection between them"; API keys are scoped per permission and incident creation takes an `idempotency_key`. Merge/unmerge endpoint names were not verified. Grafana and Keep merge/split surfaces are unverified.

## How this maps onto your pipeline

Your deterministic-first result is consistent with what vendors ship: every documented gating layer is deterministic (Keep fingerprints, Datadog's 20-minute window, incident.io's 10-minute product-wide window, PagerDuty's window + 24 h + 5-minute dependency rule), and similarity is added *after* it, investigator-facing, fused with service/team/topology/recency. Concretely: persist `(alert_a, alert_b, related|unrelated, actor, timestamp)` yourself, since no vendor emits it; copy BigPanda's per-pattern Splits/Merges counters and trend graph as your evaluation surface; note that PagerDuty's learner refuses API-sourced corrections, so its model cannot be automated even if you mirror its behaviour. For the calibrated-confidence residue layer there is nothing to copy: the closest documented pattern is Rootly's evidence-gated verdict plus a named "Inconclusive — needs human" outcome, and it lives in investigation, not grouping — and its ratings explicitly do not change the report.
